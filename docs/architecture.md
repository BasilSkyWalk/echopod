# Architecture

EchoPod, replacement firmware for the Snowsky Echo Mini. The app layer is portable C. It runs in a desktop simulator (macOS and Windows) during development and on the device on top of a thin hardware layer.

## Layers

```
platform/sim        platform/device
        \                  /
         implement  hal  (interfaces only)
                     |
                    app          composition root: theme, screens, player, stores, main step
           /     /       \        \
         ui   fonts    settings   hal
           \   /           |
            gfx        playback
              \            |
               \        library
                \         |    \
                 \        |   image
                   \      |    /
                      core
```

| Layer | Path | May depend on | Purpose |
|---|---|---|---|
| core | `src/core` | nothing | Pure logic: deadlines, key gestures, frame stats, UTF-8, string building, formatting, hashing, seeded random, the power policy |
| gfx | `src/gfx` | core | RGB565 colors and blending, rectangles, clipped canvases, strip rendering, 4-bit anti-aliased text, images drawn into perspective quads |
| fonts | `src/fonts` | gfx | Generated glyph tables (see Generated code) |
| ui | `src/ui` | core, gfx | Screen interface and stack, navigation intents, list view, menus, choice screens, messages, toasts, header and status icons, labels, marquee, fades, Cover Flow layout and motion, theme type |
| image | `src/image` | core | Cover decoding for the rescan: a bump arena, a buffered reader, the 112 px area-average grid, inflate, PNG and JPEG (see Covers on the device) |
| library | `src/library` | core, image | Byte sources, a 4×512 B block cache, the library database reader, browse queries, the favorites set and the covers file reader (see `docs/library-format.md`) |
| codec | `src/codec` | core | FLAC decoding (up to 2 channels, 24 bits, blocks up to 16,384 samples into sample buffers its user hands over, `flac_set_buffers`) from a read callback, with header and frame CRC checks, and seeking by bisection on frame headers; ALAC decoding (up to 2 channels, 16/20/24 bits, frames up to 4,608 samples); and an MP4 reader that finds the sound track and turns its sample tables into a stream of length-prefixed records (see Device playback) |
| playback | `src/playback` | core, library | Play queue (list order, songs shuffle, album shuffle, repeat, gapless look-ahead) and the resume file format |
| settings | `src/settings` | core, playback | The settings values, their defaults and option tables, and the settings file format |
| dsp | `src/dsp` | nothing | The equalizer: fixed-point peaking and shelf filters, their design for a sample rate, the automatic preamp and the headroom check (see Equalizer) |
| sound | `src/sound` | core, dsp | The equalizer presets, the Custom bands and the `equalizer.bin` format |
| hal | `src/hal` | core, dsp (types only) | Hardware interfaces: display (with power and brightness), input, clock, files, audio (with gain and output), power (battery, power off), system (firmware tag, CPU clock), Bluetooth (module power, scan, pair, disconnect, status) |
| app | `src/app` | core, gfx, fonts, ui, library, playback, settings, sound, hal | Default theme, screen tree, library, settings and favorites stores, cover cache, player controller, browse, Cover Flow, Settings and Now Playing screens, frame overlay, the main step |
| platform | `platform/*` | app, hal, codec, the OS or SDL | Implements hal and owns `main()` |

The CMake targets enforce these rules. Each module exposes only its own `include/<module>/` directory, and a module can only include headers from targets it links. Anything in a module's own directory, outside `include/`, is private.

## Screens and input

- A `Screen` is a title plus callbacks: `enter`, `handle_key`, `update` and `draw`. `handle_key` returns a `ScreenAction` (none, push, pop, or pop to root), and the app applies it to the `ScreenStack`. Screens never reach into the stack themselves.
- Raw key transitions come from `hal`. `core/key_tracker` turns them into gestures (press, long press, repeat), and `ui/navigation` maps gestures to intents (previous, next, select, back, home). Remapping buttons is a change in one place.
- Each key has a gesture type: tap-or-hold, repeat (press on down, then repeats), or tap-hold-repeat (tap on release, long press, then repeats). The volume keys repeat, except on screens that set `hold_volume_keys` (Now Playing), where they're tap-hold-repeat so a hold can skip tracks. The app switches the type whenever the top screen changes.
- Screen instances are static and owned by the app's `AppScreens`. There is no heap.
- A long Play is `NAVIGATION_OPTIONS`. Lists hand it to their `hold` action; in browse lists it toggles an album's favorite.
- Smart Play: in a browse list, ▶‖ on the track the player already has loaded (playing or paused) pushes Now Playing without restarting it. ≡ pushes Now Playing from any screen while the player has a track, and does nothing on Now Playing itself.
- Lists draw the selected row as a highlight line over a gradient, a › chevron on rows that open another screen (`ListModel.opens`), and a slim inset scrollbar thumb. Menu items can be hidden by a `shown` callback, and a menu can give the right of its content to a side panel (`MenuPanel`). Home uses that for `home_art`: the playing album's cover with a reflection, or library covers cycling every 5 s when nothing is loaded; Home lists Now Playing last and only while the player has a track.
- **Lyrics** (`playback/lyrics`, `test_lyrics`). A streaming LRC parser with fixed memory (`Lyrics`, about 4.6 KB inside `NowPlayingScreen`): bytes go in any chunk size, whole lines (up to 240 bytes, cut at a whole UTF-8 character) are parsed as they end. Leading `[mm:ss]`, `[mm:ss.x…]` or `[mm:ss:xx]` tags give a line its times (up to 16), `[offset:±ms]` shifts every time by −offset, other `[name:value]` lines (ti, ar, length…) are skipped, and `<mm:ss.xx>` word times are dropped from the text. The text goes into a 3 KB buffer and each time into a 160-entry table (time, text offset); when either fills, `lyrics_full` stops the reading. `lyrics_finish` keeps only the timed entries if any line had a time (synced) and sorts them stably by time, otherwise keeps every line in file order minus leading and trailing blanks. `lyrics_current` is the last line at or before the position (synced), or position × lines / duration (plain text). Now Playing (`OPTION_LYRICS`, On by default) loads the lyrics when the track's texts load: it swaps the track path's extension for `.lrc`, then `.LRC`, opens it through `hal_file_open` and reads it at once in 512-byte reads (at most 64 KB) with `hal_audio_service` between reads, so nothing stays open across frames. `update` follows the position; `draw` shows five rows centred on the current line (title font, text colour; the others body font, tertiary colour), the current line scrolling sideways (`draw_moving_line`, the title's marquee) when too long and the others cut with an ellipsis: landscape below the title in place of the artist, album, format and detail lines, portrait in the cover's square. While seeking the usual layout returns. `app_now_playing_lyric` reports the current line for `test_app`.
- **Theme.** Settings → Theme (`OPTION_THEME`, Dark by default) picks the colours `default_theme_styled` starts from: the dark set in `DEFAULT_THEME` or `LIGHT_COLORS` (light background and header, dark text). The accent and highlight settings only replace the three selection shades, so they apply to both. The app rebuilds the theme when the key of orientation, accent, highlight and theme changes. Cover Flow always gets a dark copy (`AppScreensContext.stage_theme`), since it draws on a black stage with reflections; the Home cover panel stays dark for the same reason.
- Settings (`app/settings_screens`, `test_settings_screens`) is a menu whose rows show their current value. Every choice row opens the same `ChoiceScreen`, re-initialized from a table of `SettingChoice` entries (title, options, current, choose), and the current option gets a ✓. The top level lists Shuffle, Repeat, Bluetooth, Equalizer and Sleep timer, then five groups: Sound, Display, Library, Buttons and System. One table, `ROWS`, holds the top level's rows followed by each group's, as codes: a `CHOICES` index, one of the screen rows (`LINKS`: Bluetooth, Equalizer, Date & time, Music folders, and Rescan library, which only sets the rescan flag), or a group; `GROUPS` gives each group's title, first row and count. To save RAM the groups share one `MenuScreen` (`SettingsScreens.group`) and a 10-item `MenuItem` array (`rows`): opening a group fills the array from `ROWS`, re-initializes the menu with the group's title and selects the row that group last had (`selected`, one byte per group, zeroed by `settings_screens_init`, so an app restart forgets it). Back pops the group to the top level, whose own `MenuScreen` (`SettingsScreens.menu`, the one Home and a long ≡ push, and the one `settings_open` looks for) keeps its selection. A new setting gets its `OPTION_*` slot, an `OPTION_CHOICE` entry appended to `CHOICES` (the order there no longer decides where it shows) and its code appended at the end of the right group in `ROWS`, with that group's count in `GROUPS` raised and the later groups' first rows moved up; `test_settings_screens` lists every group's rows and `test_app` opens settings by group and row (`open_setting(SETTINGS_DISPLAY, DISPLAY_CLOCK_ROW)`). A group holds at most `SETTINGS_GROUP_ROWS_MAX` (10) rows; Display is full.

## Power

- `core/power_policy` decides what keys mean for power. A tap of Power turns the screen off or on, and a long Power asks for shutdown. With the screen off (after a tap or a timeout), ▶‖ and vol± are background keys: the app maps them as on Now Playing (tap vol± for volume, hold vol± to skip, ▶‖ to pause) and runs them without waking the screen. ≡ and ↩ do nothing. While the screen is off, the volume keys use tap-hold-repeat on every screen, so a hold skips. The policy also owns the screen timeout and the sleep timer.
- The app runs each key event through the policy before the screen sees it. When the policy turns the display on or off, the app calls `hal_display_set_power` and stops rendering while the screen is off. Settings are saved each time the screen goes off.
- Shutdown (long Power, or the sleep timer running out) saves the resume file and settings, turns the screen off and calls `hal_power_off()`. The simulator then quits; the device cuts power.
- Battery level (`device/battery_gauge`): the battery is read once a second, and the percent comes from the average of the last 64 readings (about a minute) through RECHO's 11-point curve (3450 mV = 0 %, 4200 mV = 100 %; stock shows only 5 bars, full above 3830 mV), so short dips under load (a song starting, card reads, the backlight) don't show. While charging it reads 50 mV lower and never shows more than 99 %, since the charging current lifts the terminal voltage most near full (stock shows full on the cable only at 4250 mV or once the charger reports done). The average restarts from the latest reading when USB power comes or goes, so the charger's lift doesn't linger after unplugging. The low-battery check and Diagnostics → Battery use the last 8 readings. The shown percent follows the power source: on USB power it rises and on battery it falls one point at a time, a point each 10 s while the averaged level stays beyond it (`BATTERY_DISPLAY_STEP_MS`), and it moves the other way only on a jump of 10 points or more, which it then shows at once. For 30 s after USB power comes or goes the shown percent holds still (`BATTERY_DISPLAY_HOLD_MS`) while the restarted average settles. Plugging in or unplugging therefore can't make the number jump; earlier builds used a 100 mV correction made it drop about 10 % on plugging in.
- Low battery (`core/low_battery`, stock's rule): every 250 ms the app reads the battery, and if it stays below 3450 mV for 2 s without USB power, it shuts down the same way with "Battery low" in place of "Goodbye".
- CPU clock (stock's rule: the clock follows the work, never the screen): while the audio output is idle (`HalAudioStatus.idle`: output and core 1 down, 3 s after playback stops or 30 s into a pause), the app runs 200 MHz with the screen on and 96 MHz (stock's floor) with it off. While audio is up the app leaves the clock to the audio HAL and only tells it whether the screen is off (`hal_audio_allow_slow_clock`). The device's audio HAL picks the clock each time a stream starts (play, skip, seek, resume after a long pause), with the source closed and the transfer stopped first so core 1 is never cut off mid-stream: 96 MHz when the screen is off, the slow-clock saving is on, the equalizer is flat and the track is light, 200 MHz otherwise. A light track is FLAC (rate from STREAMINFO), WAV with `fmt ` first, ALAC, or MP3, at 48 kHz or less: at 96 MHz core 1 runs undivided at 96 MHz, against 100 MHz at 200 MHz, so FLAC, ALAC and MP3 decode as fast as before, while AAC, Opus and the core 1 equalizer need 200 MHz; core 0's copy work doubles in time, which the 48 kHz limit keeps small (the ring is about 300 ms there). When the next track is queued, the HAL reads its first 28 bytes (ALAC through `mp4_probe`) with its own file handle. If the clock that track wants differs from the current one (the screen went off since the stream started, the screen came back on, or the next track is heavy), the engine gets no next track: the current one plays out, then the HAL starts the next with `hal_audio_play` from `hal_audio_status`/`hal_audio_service` before the player can see the stop, so that one track change has a short gap (core 1 restart and prefill, about as long as a skip) instead of being gapless; a screen change before the engine opens the next track re-decides. Turning the equalizer on at 96 MHz restarts the stream at 200 MHz at once. With the screen on at 96 MHz, the menus run at 96 MHz until the current track ends. Nothing else on the device depends on 200 MHz: MCLK comes from the ACODEC PLL, the Bluetooth UART's divisor 13 doesn't follow the core PLL (it runs at 96 MHz whenever the player idles with a link up), I2C sets its divider from `board_pclk_hz` when a port starts (the DAC's 100 kHz bus comes out 4 % fast if the clock rises while the path stays up), eMMC runs at 24 MHz, SysTick, the watchdog and the backlight PWM are rescaled after every switch, and USB holds 96 MHz or more. A USB session runs at 96 MHz at least.
- Waking draws the first frame before the backlight comes on (stock waits for 4 frames), and on the device the backlight then fades in over 200 ms (`device/backlight` ramp, from 1 % to the level's duty on the PWM, advanced by the main loop), so the backlight's switch-on current doesn't land at once on top of the drawing and the audio load.
- With the panel-sleep saving on, turning the screen off also sends the panel DISPOFF (`0x28`) and SLPIN (`0x10`) after the backlight goes off (`device/panel` `panel_sleep`; both panel variants start with the same SLPOUT/DISPON commands in their init streams). The first write or backlight-on after that sends SLPOUT (`0x11`), waits 120 ms, then DISPON (`0x29`); every wait keeps 120 ms from the previous SLPIN or SLPOUT and calls `hal_audio_service` while it waits, so the ring stays fed. Waking forgets the frame hashes (`frame_diff_forget`), so the first frame redraws every row in case the panel didn't keep its memory while asleep. The stall and fault screen wakes the panel with a fixed spin instead (`board_display_wake_now`), since SysTick doesn't advance there. Whether these panels draw correctly after SLPOUT hasn't been seen on hardware yet; Diagnostics → Power shows `P`/`p` and Savings → No panel sleep turns it off.
- With the screen off, the device's main loop runs WFI once per pass, as stock does; SysTick (1 ms) wakes it, and the audio ring holds over 80 ms.
- Auto off (Settings, stock's options: Off, 1, 5, 10 min, default 5): `core/power_policy` counts from the last key press; the app holds it off each step while a track plays or USB power is present. When it runs out, the app shuts down as for a long Power press. Settings file version 2 adds the option at byte 14; version 1 files still load, with the default. Version 3 adds USB mode (Storage or DAC, see USB DAC mode) at byte 15; version 1 and 2 files load with Storage.
- Brightness 1–10 maps to a backlight duty of 8, 12, 17, 23, 30, 39, 50, 63, 80 and 100 % (`device/backlight`). Below 100 % GPIO2.4 runs stock's 10 kHz PWM, whose period follows PCLK and is reprogrammed after every clock switch. The PWM runs as the Rockchip SDK sets it up (`PWM_CTRL` `0x10003`: continuous, duty polarity negative), so the duty register counts the part of the period the pin is **low**: `backlight_duty` writes `period − period × percent / 100`. The SDK's own backlight table works the same way (rate 10 is its brightest, 85 its dimmest). Writing the lit share there instead inverted the levels (level 1 lit the panel at 92 %, level 9 at 20 %), which is why brightness looked broken in 0.1.0.

## Settings and favorites

- Without a mounted card (`hal_storage_card_ready`: on the device, the file HAL's card mount, which is tried again only after a restart or a USB session) the Home art panel shows "No microSD card", the Music lists' empty screen says "No microSD card" instead of "No library", and a failed settings save says "Insert a microSD card to save settings" instead of "Could not save settings".
- `app/settings_store` loads `/.echo/settings.bin` (defaults if it's missing or invalid), applies brightness, gain and output through the HAL, and only writes when the encoded bytes changed. It reads up to the first 48 bytes of the file, so a 32-byte file left by an older simulator still loads.
- **Settings file:** `settings/settings.c`, little-endian. Bytes 0–3 `EMST`, 4 the version (now 9), 5 zero, 6–19 one byte each for brightness, screen timeout, gain, output, start screen, shuffle, repeat, volume, auto off, USB mode, DAC volume, orientation, language, and filter (top 3 bits) with balance (low 5 bits). Version 9 is 48 bytes: bytes 20–43 are 24 option slots indexed by `SettingOption` (`OPTION_*`, each 0 = the default), and bytes 44–47 a checksum (`hash_update`) of bytes 0–43. Slot 18 (byte 38) is `OPTION_RETIRED_INTERNAL_STORAGE`: it held the Settings → Internal storage switch of 0.11 test builds, is still range-checked (0 or 1) and kept, so their files load, but nothing reads it; a new option shouldn't reuse it. A new option takes the next free slot without a new version: its default is 0, an older firmware ignores slots it doesn't know, and only known slots are range-checked. Version 8 was 32 bytes with 8 option slots at 20–27 and the checksum at 28; versions 1–7 had the checksum at 20 and no options. Older versions still load, with the default for every field they didn't have, and are saved again as version 9. A file with a wrong checksum, an unknown version, a value out of range or too short for its version is ignored and the defaults are used. Going back to a firmware that only knows version 8 or earlier makes it ignore the file and start from defaults.
- `hal_dir_open`, `hal_dir_next` and `hal_dir_close` list a folder: name (UTF-8, up to 767 bytes), folder or file, size, and a hidden flag (the FAT/exFAT hidden attribute on the device, a leading dot in the simulator). `.` and `..` are never listed. On the device, `fat_open_directory` and `fat_next_entry` walk FAT16/FAT32 entries (long names, or 8.3 names with the lowercase flags) and exFAT entry sets; up to 16 folders can be open at once. macOS's `._` files are listed like any other file.
- Folder entries are read in runs of up to 8 sectors, like file data, and writes of whole sectors go out as one multi-block write without reading them first. `fat_open` remembers the last folder it found (path and entry, up to 255 bytes of path) and starts the next lookup there when the parent path matches, so opening the tracks of one album walks only the album's folder. Mounting or reserving a file forgets it. On a 1,563-track card this took opening files from 40 s to 1.8 s, and the track scan from 61 s to 19 s.
- On the device, `hal_file_write` overwrites an existing file in place from offset 0 (`fat_write`, FAT16, FAT32 and exFAT) and fails if the file is missing or too short; it never allocates clusters or changes a directory entry. Every reader checks its magic and accepts a longer file, so a zero-filled file reads as missing.
- The player makes its own files. On every `app_start`, before the first frame, `app/card_files` calls `hal_file_reserve` for `/.echo/settings.bin`, `resume.bin` and `favorites.bin` (4 KB each), `library.db` (4 MB) `covers.bin` (80 MB) `scan.bin` (4 KB, the music fingerprint), `folders.bin` (4 KB, Settings → Music folders) and the other stores' files, among them `history.bin` (1 MiB, the listen history), in the order of `CARD_FILES`. A file that exists is left alone, whatever its size (only `covers.bin` grows, at a rescan; see Covers on the device). A missing one is created at its size, along with `/.echo` if needed; its first 4 KB read as zero and the rest is left as the card had it, so creating 80 MB costs a few hundred writes rather than 163,840. When `library.db` was just created the app asks for a rescan, so a new card is scanned on its first start. If any file doesn't fit, the app toasts "The card is full". `tools/save_files.py` is now only a development helper. The first time one of them is created, the app shows "Setting up the card..." (`app_show_notice`, which turns the backlight on), so a slow first start on a large card never looks like a dead screen.
- On the device, `fat_reserve` (`device/fat_reserve.c`, `fat_create.c`, `exfat_create.c`) creates the missing folders and the file as one contiguous run of clusters, first fit from where the last search on this mount ended (on FAT16/FAT32 the first search starts at FSInfo's next-free hint), wrapping to the start of the card only if nothing fits further on. Searching from cluster 2 every time made a FAT32 card full of music re-read most of its FAT for each of the twelve player files, so a first start on a 64–128 GB FAT32 card sat dark for minutes; `test_fat_create` counts the reads (552 before, 99 with the hint and 155 without, on the fixture card half filled). exFAT keeps its first-fit bitmap search, which is 32 times smaller. Names are printable ASCII up to 64 characters. FAT16/FAT32 get an 8.3 entry with the lowercase flags when the name fits (`settings.bin`), otherwise long-name entries plus a `~N` short name that's unique in the folder (`.echo` → `ECHO~1`, `favorites.bin` → `FAVORI~1.BIN`); the chain goes into every FAT copy and FAT32's FSInfo free count and next-free hint are updated. exFAT gets a File, Stream (NoFatChain, valid length = size) and Name entry set with its name hash and set checksum, and the clusters are marked in the allocation bitmap. The write order keeps a cut-off write harmless: clusters are marked used first, then the start of the data is cleared (a new folder's whole cluster, with `.` and `..` on FAT), and the directory entry goes last (on exFAT the secondary entries before the File entry). A folder whose entries are full isn't grown; that reserve fails. Dates come from the clock chip when it answers with a valid time: `board/storage.c` reads it once per boot before the first `hal_file_reserve` and gives `fat_set_new_stamp` the DOS date and time (FAT entries get it as creation and write stamps, exFAT entries as their three timestamps with no UTC offset, so local time), otherwise the stamp stays 2026-01-01 00:00 as before. While it runs, every card read beats the stall watch. `test_fat_create` creates files on all three fixture cards and saves them, and `created_cards_pass_fsck` checks the results with macOS's `fsck_msdos` and `fsck_exfat` (through `diskutil image attach --noMount`).
- At start-up the saved volume, shuffle and repeat go to the player first, and then a valid resume file overrides them. The current volume, shuffle and repeat are copied back into the settings before every save.
- The start screen setting pushes the matching path at start-up (for example Home → Music → Albums), so Back still leads home.
- `app/favorites_store` loads and saves `/.echo/favorites.bin` and toggles albums by key, and counts a revision on every load and toggle. Music → Favorites is a browse screen over the Albums view that only shows the positions of favorite albums, collected in album order. The browse pool keeps the collected list and only collects again when the revision changed. Collecting reads every album's key from the card, so it calls a `between_albums` hook every 8 albums (`favorites_collect`), and the browse screen uses it to run `hal_audio_service`: before this, opening Favorites while playing starved the DMA ring for a second or two and the ring's last 0.3 s played over and over. Favorite albums show ★ before their year.
- Toasts are app-owned. Screens get a pointer to the one `Toast` and show short messages such as "Added to Favorites". The app draws the toast on top of every screen.

## Languages

- **Catalogue.** Every user-visible English text is a `STRING(STR_NAME, "English")` line in `src/core/include/core/strings_*.def` (aggregated by `strings_all.def`), which `core/strings.h` turns into the `StringId` enum. Code calls `i18n_text(STR_NAME)` and never holds a literal. A text built around a variable is a whole pattern with `{0}`..`{9}` placeholders that `i18n_format` fills, so a language can reorder the words; singular and plural forms are separate ids. Library data (the indexer's `Unknown Artist`, tag text, the ID3 genre table), codec and unit names, product names and the debug mnemonics in Diagnostics stay literals.
- **Packs.** `assets/lang/languages.json` lists the languages in the order of the `Language` enum in `settings/settings.h` (English, Simplified Chinese, Japanese, Korean, German, French, Spanish, Italian, Portuguese, Dutch, Swedish, Danish, Norwegian, Finnish, Russian, Ukrainian, Polish, Indonesian). Each language except English is a text file `assets/lang/<code>.txt` of `STR_NAME = translation` lines, and `tools/lang_pack.py` builds `src/lang/packs/<code>.bin` for every language, English included: a 12-byte header (`ELNG`, version, string count, size), one u16 offset per string, then NUL-terminated UTF-8. A missing translation is filled with the English text, so every pack is complete. The tool rejects an unknown id, a repeated id, a different set of placeholders from the English text, a character no glyph pack draws, and a pack over 12 KB. `language_packs_up_to_date` fails if the committed packs differ from a fresh build.
- **Loading.** `app_start` asks `hal_language_pack` for the English pack, then for the saved language once `settings_store_load` has run, and `i18n_attach` validates it (magic, version, string count, every offset inside the pack, every string terminated). The language is fixed until the next start: the Language row in Settings saves the choice and shows `Restart to apply`, because menus keep pointers to their labels. If a pack is missing or invalid, host builds fall back to the English text compiled into `core/i18n.c` (only when `ECHO_BUILTIN_ENGLISH` is defined, which cross builds do not); a device build then shows no text, so the pack table and the packs are part of the image CRC the updater checks.
- **Device.** Language packs sit in the image beside the glyph faces (above). `board/language.c` reads the pack into `.language_ram` (`0x0308F000`, 12 KB, between the rescan overlay's window and the glyph cache) with one multi-sector eMMC read. The Battery low notice at boot (before the pack is read) and the panic screen use built-in English.
- **Simulator and tests.** `platform/sim/sim_language.c` reads the packs from `src/lang/packs` through paths CMake passes in. `tests/app/fake_hal.c` returns no pack unless a test sets one, so tests run on the built-in English. `test_language_packs` attaches every committed pack.
- `string_builder_append` cuts at a whole UTF-8 character when a buffer fills up, so a long translated text never leaves half a character.

## Audiobooks and podcasts

- `playback/spoken` decides what is spoken word from the path alone: a track whose first folder is `Audiobooks`/`Audiobook` or `Podcasts`/`Podcast` (ASCII case-insensitive). Both indexers sort spoken word after the music and record music counts in the library header (format version 3, see `docs/library-format.md`), so the Music lists leave it out while the shelves browse its folders. The rule itself lives in `library/spoken_path`. `spoken_shelf_folder` finds those folders among the root folder's children.
- Bookmarks are keyed by FNV-1a hashes of paths, so they outlive a rescan, like favorites: a book's key is its folder's path (`Audiobooks/<Book>`), and a book that is a single file, or a podcast episode, is keyed by its own path. Each bookmark also keeps the track's path hash, its chapter (its place among its folder's tracks), the position and a finished flag. `playback/bookmarks` keeps the 128 most recent, newest first, in `/.echo/bookmarks.bin` (4 KB, reserved by `card_files`; see `docs/library-format.md`).
- The player marks a track spoken when it starts it (`player->spoken`), after a gapless hand-over and after a restore. For a spoken track:
  - a start from 0 asks `PlayerResume.position_for`, which `app/spoken_store` answers from the bookmark when its track hash matches and it isn't finished;
  - `player_skip` becomes `player_jump`: +30 s or −15 s, and a jump past the end starts the next track. Now Playing's hold-vol± and the screen-off keys go through `player_skip`, so both follow;
  - the queue is built in order (`PlayerListStart.in_order`), and `player_set_shuffle` keeps it in order, while `player->shuffle` keeps the music setting.
- `app/spoken_store` follows the player every step: when a spoken track starts it notes its keys and chapter, puts the bookmark every 5 s and on every play/pause change, and when the track ends or changes it marks the bookmark finished if it was in its last tenth (at most 30 s). The file is written when playback stops, when the track changes, every 30 s while playing, at shutdown and before a USB session.
- Home lists Audiobooks and Podcasts after Music, shown only when the folder exists (checked once when the screens are built). Both are browse screens in shelf mode over the folder: rows get "N chapters"/"Chapter n of N"/"Finished" or "N episodes", and tracks "mm:ss left"/"Played". In Audiobooks, ▶ on a book plays its folder from the bookmarked chapter (the chapter is checked against the track hash and looked up again if the files moved); a book that is already loaded is resumed and Now Playing opens. Hold ▶ on a book or show opens its tracks.

## Listen history

- `app/listen_history` follows the player every step, after `spoken_store_follow` and with the same `PlayerStatus`, and logs each song played to `/.echo/history.bin` (format in `docs/library-format.md`) for `tools/echo_history.py`. It doesn't hook into `player.c`: a play begins when the player is playing a track that isn't spoken word, and it ends when the track index changes (a skip, a gapless hand-over, a jump), when the position falls back under 3 s from at least 3 s further on (repeat one, Previous after 3 s, a seek to the start), when the player has no track or plays spoken word, or when it is closed from outside. Listening time adds up the steps that began with the player playing, so pauses and the part skipped by a seek don't count. Audiobooks and podcasts (`status.spoken`) are never logged.
- When a play begins, the artist (the track's `LIBRARY_ARTISTS` group), album title and track title are copied into the record's 512-byte buffer (`ListenHistory.slot`), with its track number, length and starting position, so a rescan or an index change can't alter it. When it ends, the end time, end position and listening time are filled in; a play shorter than 1 s of listening is dropped, and anything longer is written at once with one `hal_file_write_at` of a whole aligned slot (one sector), so a power cut can tear at most that record, which the checksum then rejects. The first write after a start finds the ring's newest record (slot 0 and a bisection, about 12 reads) to get the next sequence number and the session. The whole thing is a small, deferred write in the app step like the other stores; it never touches the audio path.
- Closing: `save_session` (power off, sleep timer, auto off, low battery) and `run_rescan` close the open play. `app_release_audio` (the start of a USB drive or DAC session) closes it and writes a "connected to a computer" record, the time anchor the PC tool counts back from. When playback carries on after USB or a restart, the rest of the song is a new record that starts at the old position; the PC tool joins the two (same song, the second starting where the first stopped) and counts the song once.
- `app/scrobbler_log` (`scrobbler_log_write`, called by `app_release_audio` right after the computer record, so before the drives are shown to the computer) turns the plays since the last export into `/.scrobbler.log` lines, the AudioScrobbler 1.1 log Rockbox writes, so no PC tool is needed. It ports `tools/echo_history.py` exactly (`test_scrobbler_log` compares its output byte for byte with the tool's for the shared ring in `tests/fixtures/history`): a play counts as listened (`L`) when the track is over 30 s and the time listened, joined across a power-off or USB session when the next record is the same song starting within 5 s of where it stopped, reaches half the track or 4 minutes; the last part of a chain that never got there is written as skipped (`S`). Like Rockbox it writes both; uploaders skip `S` lines. Times are UTC, from the session's newest timed record; a session without one is placed so its last record ends where the next session starts, counted from the next session that has a time. Plays that can't be dated that way (no timed record in their session or any later one: the clock wasn't set) are left in the history, not written; a later connection dates them once a session with a set clock follows, or `echo_history.py` dates them by counting back from when it runs. `/.echo/history-exported.txt` holds the newest exported sequence number (ten digits and a newline), shared with the PC tool. The export reads from there: it walks back over records the first new play continues (they decide its rating and its start time, but aren't written again), then goes forward record by record, finding each session's offset by reading ahead to its newest timed record once per session (sessions without a time take the previous offset plus its last end), and holds each play until the next song record says whether it was continued. Lines go to a 1.5 KB buffer (on the stack, with one of the two 512-byte slot buffers; the other is `ListenHistory.slot`), written out whenever it holds more than one line's worth: the first time with `hal_file_reserve` at exactly the header and lines (a missing log; an empty one gets the header through `hal_file_grow`), then `hal_file_grow` to the new exact length and one `hal_file_write_at` at the old end, so the file is always exactly its text, never padded. Before the first write it makes sure the marker file is 11 bytes, so writing the number later can't run out of space; after the last write it writes the number of the newest record whose lines are all on the card. A grow or write that fails (a full card) stops the export: what was written stays and is marked, the rest is written at the next connection, and a play is never written twice. With nothing new to write it touches no file. Reading is one sector per record, about two reads per record (`hal_system_keep_alive` between them), so the first connection with a full 2,048-record ring and no marker reads about 2 MB; after that only the records since the last connection. Settings → Listen history Off means no computer record and no export.
- `ListenHistory` lives in `AppState` and isn't reset by `app_start`, so a rescan, which restarts the app on the same running clock, stays in the same session. The session number comes from the ring rather than `StartRecord.starts`, which lives in RAM and restarts at 1 after a real power-off.
- Settings → Listen history (`OPTION_LISTEN_HISTORY`, On by default) gates it in one place, `follow_history` in `app.c`: while it's Off the follower only closes, and no computer record is written. `ListenHistory.clock` points at the app's `WallClock`; when a record is stored, its Unix-time field gets `wall_clock_unix` at the record's end (the local clock minus the time zone), or 0 while the clock or the zone is unknown, and the tool dates a session from its newest timed record (see Clock below).

## Clock

- `core/wall_clock` (host-tested, `test_wall_clock`) is the calendar: days from civil dates and back (the 400-year era arithmetic, shared in spirit with `exfat.c`'s stamp conversion), `WallCivil` ↔ seconds since 1970, weekday, calendar validity for 2000–2099, the time zone as a settings option (0 = unset, then −12:00 to +14:00 in 15-minute steps, `wall_clock_zone_of`/`wall_clock_zone_minutes`), and the texts `HH:MM`, `YYYY-MM-DD HH:MM` and `UTC±hh:mm`. A `WallClock` is an anchor (local seconds at a millisecond tick): `wall_clock_local` adds the wrap-safe tick difference, so the clock runs on SysTick between chip reads and survives the 49.7-day wrap as long as it is re-anchored more often than that.
- `app/clock_store` (`test_clock_store`) owns the clock. `clock_store_start` (every `app_start`) reads the chip and adopts its time when `valid`, in 2000–2099 and no earlier than the day before the firmware was built (`hal_system_build_day`, days since 1970; 0 = unknown, no check). A chip that kept running but was never set properly (one player's said 14 January 2026, with VL clear) would otherwise date the listen history wrongly, so a date before the build counts as not set: no status-bar time, Date & time says "Not set", history records get Unix time 0. The day of slack covers the builder's time zone. On the device the build day is the image header's date (`tools/make_image.py --date`, default the build machine's date; offset 0, BCD `MMDDYYYY`), read with the build tag by `board/system.c` and decoded by `device/image_date` (`test_image_date`); the simulator uses the date CMake configured it on, and the fake HAL whatever `fake_hal_set_build_day` set (0 by default). A chip that doesn't answer, or answers with VL or STOP, leaves whatever the software clock already had (unknown after a power-off). `clock_store_step` reads it again every 10 minutes from `app_step` (an absent chip only re-anchors the software clock), and `app_wake` (the end of every USB session, among others) makes the next step read it. The time zone is `Settings.options[OPTION_TIME_ZONE]`; it is copied into the clock at start and whenever the clock is set.
- Sources that set the clock, both through `adopt`: set the zone, anchor the software clock, and `hal_time_write` the local civil time (seconds included, weekday computed) to the chip, which clears VL. The chip not taking the write (no reply) leaves the software clock running until power-off.
  1. echo-sync writes `/.echo/clock.bin` (format in `docs/library-format.md`) as the last step of a sync. `clock_store_start` remembers the record's Unix time on the first start of a boot (`started` stays set across the restarts a rescan or a card change cause); after a USB session in which the computer wrote to the card, `app_request_rescan_if_music_changed` also sets `usb_written`, and the next `app_step` calls `clock_store_after_usb`, which applies the record only if it decodes (magic, version 1, checksum, 2024 ≤ time < 2100) and its time differs from the one seen at start; then it saves the settings and toasts "Clock set from the computer". A record found at boot (a card synced in a reader) is never applied: the time it holds has aged by an unknown amount. The same record is never applied twice.
  2. Settings → Date & time (`screens/date_time_screen`, `test_date_time_screen`): six rows (year, month, day, hour, minute, time zone), vol± pick a row, ▶ switches to adjusting it (vol± change it, wrapping in range; the day is pulled back to the month's last day when saved), ▶ or Back ends adjusting, Back or a long Back leaves and, if anything changed, sets the clock with seconds at 0 and saves the settings, toasting "Clock set" or "Clock set until the player is off" when the chip didn't take it. The editor starts from the current time, or the build date at 00:00 when unknown (2026-01-01 when the build date is unknown), so a time set without touching the date still passes the check above, and from UTC+00:00 when the zone is unset. The row's value in Settings is the current date and time or "Not set". A time set by hand before the build date runs until the next chip read, ten minutes later, keeps running from the software clock, and is dropped at the next power-on.
- One-time question: the first start after a firmware change (`music_check_firmware_is_new` in `report_card_files`, the same test that triggers the music check) sets `clock_question`. It survives the `app_start` a rescan causes. Once the start-up fade has finished and no music check is pending (a rescan returns from `app_step` before it), `follow_clock_prompt` clears it and, if the clock is still unknown (so not after echo-sync just set it at the end of a USB session), pushes a choice screen, "Set the date and time?" with Set now and Later (Back is Later). Set now pops it and pushes Date & time. It isn't asked again because the music check writes the new firmware version to `scan.bin` (`test_app`: `a_new_firmware_asks_once_for_the_clock_after_the_start_up_screen`).
- Display: Settings → Clock (`OPTION_CLOCK`, Off by default) puts `HH:MM` (24-hour only) in the status bar (`StatusBarState.clock`, drawn by `status_bar_draw` in the small font). In landscape it sits right of the Bluetooth icon's slot and is drawn only when it ends inside the header inset, so it never meets the title; in portrait (a status band of its own) it is centred, or placed right after the left icons when centring would meet the battery, bolt and a `100%` on the right; when it fits neither way, `status_bar_draw` drops the battery percentage to make room, and leaves the clock out only if it doesn't fit even then. Settings → Portrait status bar (`OPTION_STATUS_BAR`, Standard or Large) applies `default_theme_enlarge_status` to the portrait theme: a 22 px status band instead of 16 (the header grows by 6 px), 14 px icons instead of 10, and Inter 16 instead of Inter 12 for the percentage and the clock (`ThemeFonts.status`, which falls back to the small font when unset). Now Playing in portrait keeps its cover at y = 52 by taking the extra height from the gap under the header (at least 6 px). Unknown time shows nothing.
- Not done: a card written in a reader or over USB without echo-sync doesn't set the clock from file modification times (FAT stamps are host-local, exFAT's are UTC, and the fingerprint walk would need to carry the newest one); 12-hour display; daylight-saving changes (the zone is whatever the last sync or edit left).

## Equalizer

- **Presets.** Off, Retro, Bass, Heavy, Pop, Jazz, Unique and Custom, in the order and with the names of FiiO's menu. The bands and gains come from the tables in stock 3.7.0's music overlay (scatter row 66, data row 67: eight 62-byte entries at `0x030464A8`, IMG `0xC11B4`), values only. Stock runs a 31-band graphic EQ on the ISO third-octave centres (20 Hz to 20 kHz, 25 levels per band, level 12 flat, 1 dB steps) and each preset sets a few bands: Retro +1 dB at 100, 315 Hz and 1 kHz, −6 dB at 10 kHz; Bass +5 dB at 63 Hz, +3 dB at 125 Hz; Heavy +3 dB at 315 Hz and 1 kHz, −3 dB at 3.15 kHz; Pop +4 dB at 100 Hz, −3 dB at 3.15 kHz, +3 dB at 10 kHz; Jazz +4 dB at 100 Hz, −6 dB at 315 Hz, +4 dB at 1 kHz, +1 dB at 3.15 kHz, +6 dB at 10 kHz; Unique +3 dB at 100 Hz, −3 dB at 1 kHz, +3 dB at 3.15 kHz. Stock's filter coefficients live in a resource (#36) that wasn't extracted, so EchoPod uses its own filters at those centres, one octave wide (Q 1.4). Stock's Custom has 5 bands (100, 315 Hz, 1, 3.15 and 10 kHz, ±12 dB); EchoPod's has 7, 1⅓ octaves apart (63, 160, 400 Hz, 1, 2.5, 6.3 and 16 kHz, Q 1.0, ±12 dB in 1 dB steps). Separately, `.txt` presets in `/EQ` are listed after Custom (see File presets). Stock applies its EQ only to sources under 24 bits; EchoPod applies it at any depth.
- **Filters** (`dsp/equalizer`). One filter per band that isn't flat, as Andrew Simper's linear trapezoidal state-variable filter. A bell (`EQUALIZER_PEAK`): g = tan(πf/fs), k = 1/(Q·A), a1 = 1/(1 + g(g + k)), m1 = k(A² − 1), and per sample `v1 = a1·(band + g·(x − low))`, `v2 = low + g·v1`, `band = 2v1 − band`, `low = 2v2 − low`, `y = x + m1·v1`: four products. A low shelf (`EQUALIZER_LOW_SHELF`) uses the same states with g = tan(πf/fs)/√A, k = 1/Q, m1 = k(A − 1), m2 = A² − 1 and `y = x + m1·v1 + m2·v2`: one product more. A high shelf (`EQUALIZER_HIGH_SHELF`) of +G dB is A² times a low shelf of −G dB at the same corner, so the design builds that low shelf and adds G to the preamp: it costs the same as a low shelf. The shelves are the RBJ cookbook shelves with that Q; `test_equalizer` checks both, and a ten-band AutoEQ-style curve, against the cookbook response within 0.2–0.3 dB at 44.1–96 kHz. Its coefficients map to frequency, width and gain with unit sensitivity, so Q14 (16-bit) `g` and `a1` hold every band centre within 0.12 dB (0.21 dB off centre) of the exact design at 44.1–96 kHz, where the direct-form biquad it replaced needed Q30 and 64-bit multiply-accumulates. Every product splits the 32-bit signal so the Cortex-M3's 1-cycle `MUL`/`MLA` give it exactly: 14 low and 18 high bits for `g`, `a1` and `m2` (Q14, below 4), 13 and 19 for `m1` (Q13, below 32, since a Q 0.1 bell at ±12 dB needs about 15). The long multiplies (`SMULL`, up to 7 cycles) aren't used in the loop. In the device build the bell loop is 30 instructions per sample (8 `MUL`/`MLA`, one load, one store, one stack load), one more than 0.10's, and the shelf loop 37; the two are separate functions so each keeps its own registers. The two integrator products carry their dropped low bits into the next sample (first-order error feedback), so silence after loud bass comes out as exact zeros and the filter's own noise stays near −128 dBFS at worst (−145 dBFS typical) with a −60 dBFS tone; the biquad left up to −66 dBFS of DC after boosted bass at 96 kHz. Samples enter as 24-bit values shifted up 4 bits, so the loop has 16× (24 dB) of headroom over full scale, and the result is rounded back to 24 bits and saturated (`SSAT`, helped by `-fno-move-loop-invariants` on `equalizer.c`). m1 is computed from the quantised a1 and g so the centre gain is exact. Q is 0.1 to 10 (`EQUALIZER_Q_MIN_HUNDREDTHS`, `EQUALIZER_Q_MAX_HUNDREDTHS`), kept in hundredths; g and a1 are capped below 4, so a band above about 0.42 of the rate sits a little lower than asked. Gain and preamp are stored in tenths of a dB; gain is interpolated between the 1 dB table entries. Up to ten bands (`EQUALIZER_MAX_BANDS`). The design needs no maths library: sine and cosine of half the angle come from Taylor series in Q30, and 10^(dB/40) from a 37-entry table. A band is skipped when its centre is at or above 0.45 of the sample rate, on its own: the rest of the curve still plays. Changing the set of centres or filter types fades the old curve out and the new one in over 256 frames each way (5.8 ms at 44.1 kHz); a change while a fade runs carries on from the level reached (a fade-in turns into a fade-out from there, a fade-out just gets the newer curve), so scrolling through presets never steps the level. Changing only gains keeps each band's state. Above 96 kHz (`EQUALIZER_MAX_RATE`) no band runs. Audio goes through the equalizer in chunks of 32 frames, one band and one channel at a time, so coefficients and state stay in registers.
- **Preamp and headroom.** The preamp scales the input before the first band. Built-in and Custom curves use minus the largest audible boost (0 to −12 dB); a file preset uses the smaller of its own `Preamp:` and that automatic value; high shelves then add their gain (see above), and the total never boosts (it is capped at 0 dB). **Invariant: no value the loop multiplies ever leaves the 32-bit range, so the loop needs no clamp.** The largest is the input of the `a1` product, `band + g·(x − low)` = v1/a1, which reaches about (1 + g + (1 + g²)/k) times the band's input at its centre: Q·A at low frequencies, but 60× for a Q 10 bell at 16 kHz and 44.1 kHz. Q 20 broke this: a Q 20 bell boosted 2–4 dB wrapped its state on a full-scale tone at its centre, so Q stops at 10, and after designing the stages `within_headroom` evaluates the cascade's exact gain (the analog prototype at the bilinear-warped frequency, `|H(jΩ)|²` from g, k, m1 and m2) at each band's centre and at DC, multiplies the gain of the bands before each one by that band's peak, and lowers the preamp 1 dB at a time until all of it, times the preamp, stays within 12× full scale (16× less a margin for a full-scale square wave's fundamental). Ordinary curves never trigger it: the Custom curve with every band at +12 dB keeps −12 dB at 44.1–96 kHz, and the AutoEQ-style test curve keeps its own preamp. Narrow bands near the top of the range do: a Q 10 bell at 16 kHz costs about 15 dB at 44.1 kHz and about 2 dB at 96 kHz. `test_equalizer` plays a full-scale tone at the centre of a Q 10 bell (+0.1 to +12 and −12 dB, 20 Hz to 40 kHz, 44.1/48/96 kHz), of Q 10 shelves and of three stacked Q 10 boosts, and checks every output sample against a double-precision model of the same coefficients: no sample is more than 16 LSB off for the bells and 256 for the shelves (at 30 Hz, where rounding adds up in the resonance); a wrap would be millions off. The cascade can still reach the 24-bit saturator at the output when boosts overlap, which clips but never wraps.
- **Where it runs.** FLAC, ALAC, MP3, AAC and Opus go through core 1's programs, which run the equalizer themselves: core 0 writes the curve into the shared block at `CORE1_SHARED_EQUALIZER` (`Core1EqualizerShare`: a version, an enable flag and the `EqualizerCurve`, written by `board_core1_set_equalizer` at every change and before core 1 starts), core 1 designs the filters for the stream's rate whenever the version changes, and `core1_stream` widens each decoded block to 24 bits and filters it in its slot before marking the slot full, with `StreamSlot.equalized` set. Core 0 hands such a block on as a 24-bit `AudioFrame` with `equalized` set, and `device/audio_engine` skips its own equalizer for it. The enable flag is set only when core 1 runs at the full 200 MHz: `board/core1.c` starts the program at divider 1 whenever the curve has a band away from 0 dB (as it already does for AAC and Opus), and a track start with a different speed wanted restarts core 1, so turning the equalizer on or off moves the work at the next track. WAV has no core 1 program, so `device/audio_engine` runs its equalizer on core 0 as it copies each 32-frame chunk into the music ring, after `to_output`; both paths hear Bluetooth too. A rate change redesigns it. A change reaches the ears once the slots and the ring have played out (up to about 300 ms at 44.1 kHz). Measured on core 0 with the frame overlay on a 96 kHz 24-bit FLAC with all 7 Custom bands moved (0.10's loop), before the move to core 1: the audio share (`L`) went from 29 % (equalizer off) to 72 % with either filter (about 60 cycles per band per channel-sample: the Loop cycles diagnostic reads `r4.00 m14.02` during playback, against about 3 and 9–10 for a Cortex-M3 with no wait states, so memory adds 1.3–1.5× to every instruction), and the frame time from 28 to 66 ms. Core 1 at 100 MHz showed 45 % (`c`) decoding the same track, so at 200 MHz decoding plus the equalizer should fit with room to spare; not yet measured. Ten bands aren't measured on the device either. Scaled from those numbers by instruction count (bell loop 30 against 29 instructions, shelf 37), ten bells at 96 kHz on core 0 would take about 29 % + 10 × 6.4 % ≈ 93 % (`L`), an AutoEQ file with two shelves about 96 %, so a 96 kHz WAV, or a 96 kHz FLAC for the rest of the track in which the equalizer was switched on, may not keep up with ten bands; at 44.1/48 kHz the same curve costs about half as much. On core 1 at 200 MHz ten bands at 96 kHz come to roughly 120 M cycles a second, about 60 % of the core, on top of about 22 % for decoding (estimates, not measured). Diagnostics → Frame time shows `L` and `c`. With the equalizer off, batching the engine copy and the unity-gain fast path took the same track from 61 % to 29 %. `test_core1_stream` checks that core 1's output is bit-identical to `equalizer_process` on the same samples. The simulator runs the same code on its float chunks at the track's own rate. USB DAC mode bypasses the engine and has no equalizer.
- **Saving.** `app/equalizer_store` keeps the choice in `/.echo/equalizer.bin` (reserved at 4 KB by `card_files`): `EMEQ`, version 2, the preset at byte 6, the seven Custom gains + 12 at bytes 7–13, the selected `/EQ` file name at bytes 14–79, and an FNV-1a checksum of bytes 0–79 at byte 80. Version 1 files still load. A missing or invalid file means Off and flat; if a remembered preset file is missing, the choice falls back to Off. It is written when an Equalizer screen is left and with the settings (screen off, shutdown), only when the bytes changed, and applied through `hal_audio_set_equalizer` at start-up. It is a separate file so the settings format doesn't change.
- **File presets** (`sound/equalizer_text`, `app/equalizer_files`, `app/equalizer_store`). Up to eight `.txt` files in `/EQ`, listed each time the preset list opens (Settings → Equalizer or a long ≡), so files copied over USB appear without a restart; hidden files and names starting with `.` are left out, and the list shows names without `.txt` (the scan keeps the extension behind the name's terminator for the path). `equalizer_text_parse_from` reads a file a line at a time through a 164-byte window (no 4 KB buffer: the app's static RAM is at its budget, and the HAL scratch stops playback). Accepted: one `Preamp: <dB> dB` line (−24 to +12 dB) and `Filter <n>: ON|OFF <type> Fc <Hz> Hz Gain <dB> dB Q <Q>` lines, with Fc rounded to 1 Hz (below 43.2 kHz), Gain to 0.1 dB (±12 dB) and Q to 0.01 (0.1 to 10); `PK`, `PEQ` and `Modal` are bells, `LSC`/`LS` low shelves and `HSC`/`HS` high shelves. Blank lines, `#` comments, LF or CRLF, a UTF-8 BOM, `:` with spaces around it and any letter case are fine; lines may be up to 160 characters, files up to 4 KB, filter numbers unique up to 999, at most 32 filter lines and ten filters that play. Filters that can't be played as written are skipped and counted (`EqualizerTextError.skipped`), and the list shows "2 filters skipped": other types (`LP`, `HP`, `BP`, `NO`, `AP`, ...), shelves given a slope (`LSC 10.8 dB`, `LS 12dB`) or no Q, and `BW Oct` widths. `OFF` filters are ignored. Anything else rejects the file and the toast says why ("Line 4: gain over 12 dB", "Line 2: Q not 0.1 to 10", "More than 10 filters", "Preset is over 4 KB", "No filters in the preset", "Can't read line 3"); the previous sound keeps playing. AutoEQ's Equalizer APO export (`ParametricEQ.txt`: a Preamp line and ten `LSC`, `PK` and `HSC` filters with Q in hundredths) loads whole; `test_equalizer_text` reads a file written in that format. The device build lists them; only WAV at a high rate, which equalizes on core 0, is still limited by the ten-band cost.
- **Screens** (`screens/equalizer_screen`). Settings → Equalizer (value: the preset name) and a long ≡ on Now Playing open the preset list. The equalizer follows the highlighted row, so each preset plays as the selection moves; ↩ or ▶ keeps it and saves. `.txt` files in `/EQ` appear after Custom in the same list (up to eight, without `.txt`) and preview as the highlight moves; a rejected file leaves the previous sound playing and says why. ▶ on Custom opens the editor: seven columns with a track, a bar from the 0 dB line and a knob, the selected column highlighted, "1 kHz   +3 dB" and "Preamp −3 dB" above, the band labels and a key hint below (or "EQ is off for tracks above 96 kHz"). It has two modes, so a band missed is one press away in either direction: picking, where Vol± move the highlighted column (stopping at the ends), and adjusting, entered with ▶, where the column turns blue and Vol± change its level by 1 dB (the volume keys repeat here). ▶ or ↩ leaves adjusting; ↩ while picking leaves the screen, and a long ↩ always saves and goes home. A long ▶ sets the highlighted band to 0 dB in either mode. The editor always opens in picking.

## Library rescan on the device

- Settings → Rescan library sets a flag; on the device, the end of a USB session in which the computer wrote to the card or to internal storage sets a second flag that first runs a music check, under a "Music / Checking for changes..." notice. The first start after a firmware change sets the same flag (`music_check_firmware_is_new`: bytes 16–31 of `scan.bin` hold the version of the firmware that last checked, and `music_check_note_firmware` updates them when nothing changed); a requested check waits until the start-up fade has finished, so the walk never hides it. macOS writes `.fseventsd` and `.Spotlight-V100` on every mount, so a write alone means little: `library/music_fingerprint` walks the card from `/` with one open folder per level (each folder is opened and listed once; a folder that can't be opened counts as empty; a card deeper than 32 levels gives an incomplete fingerprint), skipping names that start with `.`, and folds every entry's path, kind, size and modification stamp into two FNV-1a hashes plus a count. On FAT the stamp is the raw write date and time and the size is the directory entry's. On exFAT the stamp is the last-modified time converted to UTC with the entry's own UTC offset byte (`fat_exfat_utc_stamp`, in 2-second units since 1970; no valid offset counts as UTC), and the size is the stream's data length, not its valid data length; files of 4 GiB or more aren't listed. That is what Windows, macOS and Linux report for the same file, so `tools/echo_sync.py` can match it without guessing time zones: on one card, 9 files written with a wrong offset (−5:30 instead of +5:30) and 3 incompletely copied files (valid length short of the size) had made every PC fingerprint differ. It is compared with the fingerprint kept in `/.echo/scan.bin` (4 KB, made by `card_files`; the bytes `MESC`, the two hashes, the count), and only a difference (or no record, or a walk that failed) asks for a rescan. Every successful rescan stores the fingerprint taken just before it. A requested rescan the next `app_step` runs `library_rescan_run`, shows "Scanning library" with the track count every 250 ms and once more with the final count when the walk ends (`library_scan` reports `files` = 0 then, before the playlists and the library are written), then restarts the app on the new library and toasts "Library: N tracks" or the reason it failed (no card, no room, couldn't read the card, too big, a folder too big, a path too long, a write failure, or missing rescan code). "No room for the library on the card" means a real space problem: the library doesn't fit `library.db`, or `library.db` or `build.tmp` can't be opened and `card_files_reserve` then gets `HAL_RESERVE_NO_SPACE` making it. If such a file exists but won't open (a card read error, or all 8 of the file HAL's open files taken), the toast is "Couldn't read the card". The app keeps `library.db` and `covers.bin` open while it runs; `app_start` closes both before it opens them again (`cover_cache_close`, then `library_store_open`, which closes the previous handle), and so does the music check's `library_store_open`. Before 2026-11-07 every successful rescan left the previous two open, so after three rescans in one boot the next one found no free file slot and said "No room for the library on the card".
- `app/library_rescan` checks for a music root (`/`) and a reserved `/.echo/library.db` (its size is the capacity), then asks `hal_system_load_rescan_code` for the indexer's `LibraryScanEntry` and `hal_system_borrow_scratch` for working memory, and runs the scan with the HAL adapted to `ScanFileSystem`. The database goes out through `hal_file_write_at` and is never written unless it fits.
- The indexer is its own library (`echo_library_scan`). The simulator and the tests link it and return its entry table directly. On the device it doesn't fit the 157 KB code window, so it's built as `echo_rescan_overlay`: linked at `0x0307A000` against the main ELF's symbols (`--just-symbols`, plus libgcc for the double helpers), with a 16-byte header (magic `EOVL`, size, CRC of the rest, CRC of the main image's `.code` section) before the entry table. `tools/make_image.py --overlay` stores it at image offset `0x200000`, beyond the `fw1 end` the header records and inside the area the trailer CRC covers and our updater writes. `board/overlay.c` (`board_overlay_load`, shared with the USB overlay and the resident tables) checks the magic, the size and the CRC before calling it: if HIGHRAM0 still holds an intact copy (the same checks on the RAM copy) it is used as it is, otherwise the overlay is read from firmware slot 1, and from slot 2 if slot 1's copy fails a check; the rest of the window up to `0x15000` is then zeroed. It also checks the header's code CRC against the code actually running (`0x03050000` to the linker's `device_code_end`, about 16 ms at 96 MHz, worked out once per start and then remembered): the overlay is linked against one build's symbol addresses, and an overlay from another build would call into the wrong places. That can happen when slot 1 holds a different image from the one that booted (the boot ROM is assumed to fall back to slot 2 when slot 1 is incomplete, and an install writes slot 2 first, then slot 1 with chunk 0 last, so an interrupted copy leaves slot 1 with the old overlay at `0x200000` and a valid CRC). Slot 2 usually holds the same image (an install writes slot 2 and then copies it into slot 1), so a slot 1 copy that fails the check is replaced from slot 2; a mismatch in both slots refuses the rescan with "Rescan code missing: reinstall the update". The loader no longer refuses outright after an install (`library_rescan_run` still does, before it asks): the code CRC is what keeps another build's overlay out. It may be at most `0x15000` bytes: above it HIGHRAM0 holds the language pack (`0x0308F000`, 12 KB), the glyph cache and the resident tables (see Code size).
- On the device the scratch memory is core 1's RAM (`0x01000000–0x0105FFFF`, 384 KB): playback is stopped, core 1's domain is powered up with the core held in reset, and it's powered down again afterwards.

## Covers on the device

- **Growing the file.** Before the cover pass, `library_rescan` reads the new library's album count and `card_files_fit_covers` grows `covers.bin` when it has fewer slots than albums: to 1.25 × the albums rounded up to 256 slots (3,000 albums: 3,840 slots, 120 MB), at most 8,192 slots (257 MB); if the card has no room for that, to exactly the albums. A file with enough slots, made by the player or by echo-sync, is never shrunk or touched. Growing changes the layout, so that rescan decodes every cover again (a file made too small reads as "another layout", below). The limit keeps the index out of the decoder's way: each indexed album takes about 10 bytes of the scan's scratch, so 8,192 take about 83 KB and leave about 265 KB of arena: enough for any JPEG the decoder takes and for PNG rows up to about 33 KB (11,000 RGB pixels); a wider PNG leaves its album without a cover. `hal_file_grow` (device: `fat_grow` in `device/fat_reserve.c`) keeps the file's data. On FAT16/FAT32 it chains new clusters to the end of the file, first fit from the free-cluster hint and in as many runs as the free space comes in, writing every FAT copy and FSInfo, and sets the directory entry's size last. On exFAT a NoFatChain file whose following clusters are free is extended in place and stays contiguous; otherwise the file's clusters are written into the FAT as a chain, the new clusters (from the allocation bitmap, any number of runs) are chained after them, and the stream entry loses NoFatChain and gets the new lengths and set checksum, written last. An empty file (size 0, no cluster, as a PC leaves a file it truncated) grows the same way with nothing to link to: the new chain's first cluster goes into the directory entry (FAT16/FAT32) or the stream entry (exFAT, as a FAT chain) along with the size. The new clusters aren't cleared: the cover pass rewrites the header and only reads records the index points at. `test_fat_create` grows files on all three fixture cards past a file that follows them, in place on exFAT, and into single free clusters scattered over a full card, and checks that the data stays and that a grow beyond the free space fails without changing the size; `an_empty_file_grows_from_nothing` empties a file's entry by hand on all three cards and grows it from nothing.
- After a rescan writes `library.db`, `library_rescan_run` asks the same entry table for `covers` (`library/cover_build`) and passes the scan's scratch memory, the file adapters, `library.db` to read back and `/.echo/covers.bin` to write in place. It shows "Finding covers" with "N of M albums". The toast then reads "Library: N tracks, M covers", or ", no covers" if `covers.bin` is missing or the cover pass failed.
- For each album (in album order) it takes the first art it finds, as `tools/cover_export.py` does: the embedded picture of the first of the album's first four tracks (in track order) that has one (within a track a front cover wins over any other picture, `track_tags_read`), otherwise `cover`, `folder`, `front` or `albumart` with `.jpg`, `.jpeg` or `.png` (any case, the first by name when several share a stem) in the album's folders in track order. Looking past the first track matters when several albums share one folder: an album whose first track has no art still gets the art of a later track instead of the folder's image. An embedded picture that fails to decode leaves the album without a cover, as on the PC. A key already stored is skipped.
- Covers are kept between rescans. Before the pass, the builder reads the old index and its art stamps into the scratch memory, keeps the entries whose album key is still in the library and frees the records of the rest. For each album it then finds the art as above and hashes where it came from into a stamp: FNV-1a over the path (`/` plus the library's path for embedded art, the folder plus the listed name for a cover file), then three little-endian `u32`s: for embedded art the track's size, the picture's length (for Ogg, the decoded image's length) and 1; for a cover file its size, its modification stamp (the same value the music fingerprint uses, from the folder listing it already reads) and 2. A stored stamp of 0 means unknown and never matches. An album whose stamp matches keeps its record without decoding; changed art is decoded again into the album's own record, and a new album goes to the first free record. A rescan after adding a few albums therefore decodes only those albums.
- The file has a fixed layout for its size: the 16-byte header, an index with room for every record (`(capacity − 16) / (8 + 4 + 31,360)`, 2,673 for 80 MB; a 32 MB file made by an earlier build keeps working with 1,069), a table of 4-byte stamps parallel to the index, then the records. Header bytes 12–15 hold the stamp table's offset. echo-sync writes the same layout and stamps (see `docs/library-format.md`), so the first rescan after it keeps its covers. A file without stamps (made by an earlier build or an older echo-sync), with another layout, or with an index that isn't sorted or points outside the records is ignored, and every cover is decoded again. The header is zeroed before the first record is written, and the sorted index, the stamps and the `EMCV` header go last, so an interrupted pass reads as no covers and the next rescan decodes everything.
- Ogg pictures (Opus and Vorbis) are base64 FLAC picture blocks inside the comment packet, which can span many Ogg pages. `tags_open_picture` (`library/tags_vorbis.c`) walks the pages from the comment packet's first page, decodes the base64 as it reads (decoded byte `d` is in the 4 characters at `4 × (d / 3)`), skips the block's type, MIME type, description and dimensions, and hands the image bytes to the decoder as an ordinary `ByteSource`, so nothing is copied into RAM. A read before the current page starts again from the comment packet's first page. A picture whose header can't be read counts as no picture in that track; bad base64 later in the image fails the decode. The same page walk lets the tag reader read a comment that crosses a page boundary.
- `image/cover_image` sniffs JPEG or PNG and decodes into `image/cover_grid`: the centred square crop is area-averaged into 112 × 112 cells per channel with 9-bit fractional weights (each source sample adds `value × wx × wy`, sums wrap without undefined behaviour), and the 56 px half is the exact average of 2 × 2 cells. Per-channel sample sizes let chroma at half resolution sit on the same grid; YCbCr converts to RGB (JFIF) per cell, then to RGB565 like the PC.
- PNG: every colour type and depth (1–16 bits, palette, grey, alpha ignored as Pillow's `convert("RGB")` does), Adam7, all five filters, IDAT across chunks, zlib through `image/inflate` (32 KB window, 9-bit fast tables). Rows below the crop stop the decode. A row up to 64 KB is allowed.
- JPEG: baseline and progressive Huffman (SOF0, 1, 2), 1 or 3 components, sampling factors that divide the maximum, restart intervals, Adobe RGB. It decodes at 1/1, 1/2, 1/4 or 1/8 scale (the largest that keeps the crop at 112 px or more); each reduced sample is the exact area average of its pixels (cosines averaged over the sample, all 64 coefficients), and 1/8 is the DC term alone. Baseline scans stop below the crop. Progressive decoding needs no coefficient store: every scan's contribution is linear, so DC first and refinement scans and AC first scans add straight into the grid; AC refinement scans, and AC bands that can't change the reduced samples, are skipped. CMYK, 12-bit, lossless and arithmetic-coded files are refused. More than 8 bytes of padding past a marker fail the scan, so a truncated or lying file can't spin through millions of empty blocks.
- Memory comes from the scan's scratch (384 KB): the builder's state with one record (about 35 KB), the index (a key, a stamp, a 16-bit record number and a claimed bit per entry, for the larger of the album count and the old file's count, plus a bit per record: about 27 KB at 2,673 albums), then the decoder's arena: the grid (154 KB), a 4 KB reader and up to 168 KB for PNG rows, the inflate window and tables (JPEG needs about 13 KB). The worst PNG (64 KB rows) needs about 327 KB of arena, which still fits beside a full index. Nothing is static, so it runs from the overlay.
- `test_cover_grid` checks the averaging, `cover_decode_matches_pillow` (`tools/check_cover_decode.py`) makes 28 images with Pillow and a hand-written PNG encoder and compares the decoder with an exact area average of Pillow's decode (PNG within one RGB565 step; JPEG mean ≤ 3 and 99 % ≤ 40, the rest is libjpeg's smoothed chroma upsampling against our block chroma), checks that broken and unsupported files are refused, and fuzzes every image (truncations and byte changes) under UBSan. `cover_build_matches_reference` builds a music folder with each art rule and checks `covers.bin` end to end, then writes `covers.bin` as echo-sync does and checks that the player's cover pass keeps every cover. `test_cover_build` runs the scan and the cover pass over an in-memory card with generated PNG covers and checks what a rescan reuses: everything when nothing changed, only the new album, a replaced cover file, a removed album's record going to a new one, and a full rebuild for a file without stamps or with a damaged index. It also builds Opus files with base64 pictures across many small Ogg pages: the front cover wins, the art is kept on the next rescan, and albums sharing one folder find art in their second or fourth track, while a fifth track isn't read and a damaged picture header moves on to the next track.

## Internal storage music

The library always holds the music on the internal storage's user volume (the 8 GB eMMC's FAT volume that USB shows as LUN 0) next to the card's. There is no switch: Settings → Music folders (below) leaves its top-level folders out like the card's. The card stays the music root and keeps every `/.echo` file; the player never writes to internal storage.

- **One namespace.** The file HAL serves both volumes. A path that starts with `/:internal` (`core/volume_path`: exactly `/:internal` or `/:internal/…`) is on internal storage, with the rest of the path inside that volume; every other path is on the card. FAT and exFAT names can't contain `:`, so no card path can collide with it. `hal_file_open`, `hal_file_read` and `hal_dir_*` follow the prefix; `hal_file_write`, `hal_file_write_at`, `hal_file_reserve` and `hal_file_grow` only ever use the card, so a write to `/:internal/…` fails.
- **The internal folder.** A listing of the card root `/` ends with one more folder, `:internal` (size 0, stamp 0), whenever the internal volume mounts (`owes_internal` in `board/storage.c` and `sim_storage.c`). Everything that walks the music goes through that listing: `library_scan` (which sorts it among the root's names by its bytes, so it comes after names starting with digits and before letters), the cover pass and `music_fingerprint` (in listing order, so last). A track on internal storage therefore has the library path `:internal/Artist/Album/01.flac`, playback opens `/` + that path as for any track, and nothing in the library format changed: card paths, album keys (favorites, covers), bookmark keys and listen-history records of the card's tracks are what they were. Where the internal volume doesn't mount, the scan, the library and the fingerprint are byte for byte a card-only player's. The first start of a firmware that lists internal storage finds the `:internal` entry new in the fingerprint and rescans once. Files the scan doesn't index (`HIFIECnn.IMG`, `.bin`, anything not audio, playlist or folder art) don't count in the fingerprint either, so copying an update image to internal storage doesn't ask for a rescan. An album on both drives with the same album and album artist tags becomes one album holding both copies of its tracks (the album key has no drive in it); unticking one copy's folder in Music folders is the user's way out.
- **Display.** The Folders view, folder titles and the folder Cover Flow show the root's `:internal` folder as "Internal storage" (`browse_folder_name`, `STR_LIBRARY_INTERNAL_STORAGE`). A track directly in the internal root with no album tag gets "Unknown Album", like a track in the card root (`track_fields`, `folder_album` in the indexer), not `:internal`. Spoken word is still only the card's top-level `Audiobooks`/`Podcasts` folders: `:internal/Audiobooks/…` is music (its first folder is `:internal`), because the shelves read one top-level folder each.
- **Device.** `board/storage.c` keeps two `FatVolume`s (about 5.5 KB of RAM each) with their own mount state; the internal one mounts on first use with `emmc_start` and `emmc_volume_read` (reads only: its `BlockDevice` has no write) and is forgotten by `storage_reset` with the card's. Open files and folders remember their volume. A USB session that wrote to either LUN now counts as a card change, so the HAL forgets both mounts and `app_start` checks the music, which covers music copied to internal storage. The 512 MB model's internal storage (SD NAND, not supported yet) isn't changed: when `emmc_start` or the mount fails, the internal folder is simply not listed. Since the folder is always listed, every root listing (the start-up music check, a rescan, the Music folders screen) mounts the internal volume on first use.
- **Sharing the eMMC.** Glyph faces, the language pack, the overlays, the resident tables and the core 1 programs are read from the firmware slots on the same controller. `emmc_start` only powers up and resets the controller while it hasn't started (`started` is never cleared), so the repeated calls from `board/glyphs.c`, `language.c`, `overlay.c` and `core1.c` never reset it under a track that streams from internal storage. Every eMMC access is a polled transfer on core 0 that finishes before it returns, and no interrupt handler touches storage, so a glyph read between two of the audio engine's reads can't interleave inside a transfer; the FAT cache of each volume is separate from the glyph sector buffer. Writes to internal storage come only from USB (inside the user volume, through `emmc_volume_write`) and the updater (the firmware slots), and `emmc_write` still refuses anything outside `emmc_layout`'s ranges. eMMC reads are single-block (CMD17), which is unmeasured for streaming; the frame overlay's `o` (I2S underruns) shows whether a 192 kHz track from internal storage keeps up.
- **PC.** `tools/library_index.py --internal DIR` and `echo_sync.py --internal DRIVE` index the second drive the same way (`MusicRoots`: files of both drives sorted together by path parts, with the internal ones under `:internal/`; `MusicRoots / path` maps a library path back to its drive for the cover export). echo-sync finds the drive itself (`player_internal_drives`): among the mounted volumes (`mounted_roots`: the drive letters on Windows, `/Volumes` on macOS, `/media/$USER` and `/run/media/$USER` on Linux), the one labelled `ECHO MINI` (`volume_label`: the volume label from `GetVolumeInformationW` on Windows, the mount point's name elsewhere; case and outer spaces ignored) that isn't the card, preferring one without `/.echo` when several match; two left is an error that asks for `--internal`, which overrides the search. It prints the drives it reads. With no drive found (a card reader, a renamed drive) it says so, builds the card alone and clears `scan.bin`, so the player rescans. Its fingerprint appends the same `:internal` entry to the root listing and walks the internal drive with that drive's own file system rules (FAT or exFAT stamps). `two_drives_up_to_date` re-indexes `scan_music` plus `tags` as internal storage into `tests/fixtures/two_drives.db`, and `test_library_scan` scans the same two folders through the simulator's file HAL and must mean the same; `test_music_fingerprint` and `test_echo_sync` share one two-drive fingerprint value.

## Music folders

Settings → Music folders (`screens/folders_screen`) leaves top-level folders of the card or of internal storage out of the library. The choice lives in `/.echo/folders.bin` (`app/folders_store`, reserved at 4 KB with the other card files, layout in `docs/library-format.md`), not in `settings.bin`: up to 32 folder keys, each the FNV-1a hash of the folder's library path (`Rock`, or `:internal/Rock` for internal storage), so the choice follows names, new folders are included, and the file stays 140 bytes.

- **Skipping.** `library/music_folders` decodes the file and answers `music_folders_skips(folders, folder, name)`: true only when `folder` is the card root `/` or the internal root (`/:internal`, with or without the trailing slash) and the name's key is listed. Nothing in the rescan overlay changed for it: `app/library_rescan` loads the file at the start of `library_rescan_run` (onto the stack) and its `ScanFileSystem.next_entry` adapter, which remembers the path `open_dir` was given, drops listed folders before `library_scan` sees them; the cover pass shares that adapter and only opens album folders, which can't be inside a left-out folder. `music_fingerprint` takes the list in `FingerprintFiles.skip` (core 0) and skips a left-out folder's entry and everything under it, so a change in the choice changes the fingerprint (the folder's entry is gone) and changes inside a left-out folder don't ask for a rescan; `music_check_fingerprint` loads the file each time. Files at a root are never skipped. The spoken-word shelves read the card's `Audiobooks`/`Podcasts` folders themselves, and the screen doesn't list those names, so the shelves can't be emptied by it.
- **Screen.** Opening it lists `/` (and `/:internal` when the root listing has the `:internal` folder, i.e. the volume mounted), skipping files, hidden and dot entries, `System Volume Information`, the spoken folders and `:internal` itself. Rows are sorted by their bytes, the card's first, then the internal ones labelled "Internal storage/" + name. Each row keeps its key, its state and its state when the screen opened; the labels go into one 512-byte pool, so at most 32 folders are listed, fewer when the names are long (the rest aren't shown and stay included). ▶ toggles the tick (`✓` in the detail column, the equalizer's mark). Leaving the screen with Back or Home, when a row differs from how it opened, writes the excluded rows' keys plus the stored keys of folders not on the list (internal storage that didn't mount, a folder that is gone), up to 32, and sets the rescan flag; a failed write toasts "Could not save settings" and asks for nothing. The Settings row's value ("All", or "3 of 5" from `STR_SETTINGS_FOLDERS_SHOWN`) lists the folders once, the first time it's drawn after `app_start`. The screen's static RAM is about 0.9 KB (32 eight-byte rows, the 512-byte pool, the list view).
- **PC.** `library_index.MusicRoots` takes the excluded keys and drops files under a left-out top-level folder of either drive (`library_index.py --folders FILE`); echo-sync reads the card's `folders.bin` and passes the keys to the indexer and to its fingerprint walk (`left_out`), so its library and `scan.bin` match the player's. Folder names are hashed as the player lists them: UTF-8, NFC on macOS (`library_index.name_bytes`, which echo-sync's `card_name` uses). `test_music_folders` and `ExcludedFoldersTest` share key values, `test_music_fingerprint` and `PlayerFingerprintTest` share a fingerprint with an internal folder left out, `test_library_scan` must mean the same as `scan_music_folders.db`, and `test_folders_screen` and `test_app` drive the screen, the save, the rescan request and the folders a rescan and the fingerprint open.
- **Scanner fix.** `library_scan` used to leave a listed folder that then failed to open (a damaged directory, say) in the path, so every later sibling was looked up inside it and missed; it now trims the path back (`a_folder_that_cannot_be_opened_leaves_the_next_ones_scanned`).

## Library

- The player builds the database on the card (see Library rescan on the device); `tools/library_index.py` writes the same format on a PC.
- On the device, `app/library_store` opens the database through `hal_file_*`, puts a block cache in front, and validates it with `library_open`.
- Browse queries (`library/library_browse`) answer three questions for any view: how many rows there are, what row N is, and what selecting it opens. They read records and strings on demand and never load the database into RAM.
- Browse screens come from a fixed pool of 6 levels. They share one cache of the visible rows' text, which is refreshed in `update` (never during `draw`) whenever the visible rows change.

## Playback

- `hal/audio.h` is high level: `play(path, start, token)`, `queue_next(path, token)`, pause, resume, seek, volume and status. The backend decodes; on the device that's `board/audio.c` (see Device playback).
- Gapless: when a track starts, the player queues the next one with a new token. The backend switches without a gap and reports the new token, and `player_update` then moves the queue on and queues the following track.
- Shuffle is seeded (`core/random`). The resume file (`/.echo/resume.bin`, `playback/resume_state`) stores the queue plan (source list, anchor track, shuffle mode, seed), the cursor, the track and the position, so the exact same queue is rebuilt after power-off. A library fingerprint rejects resume files from an older index.
- The player saves on start, on track change, on pause, every 15 s while playing, and in `app_stop()`.

## Cover Flow

- Now Playing shows the playing album's full cover (112 px) on the left, below the header, with the text, progress and times in a column to its right. It loads the cover through the same `CoverCache` full slot in `update`. Without a cover it keeps the full-width text layout.

- Albums run by album artist, then by year, the same order as Album Artists. The screen reads each position straight from the album artists' links (`docs/library-format.md`), so it holds no album list and shows every album.
- `ui/cover_flow` holds the geometry and the motion, in fixed point (256 = one cover). The center cover is flat and 112 px. The first neighbours are 46 px wide trapezoids, 104 px tall on the side facing the center and 78 px on the far side, 86 px from the center; each further cover sits 30 px farther out and is a quarter smaller per step (`side_shrink`), so the outer covers recede instead of matching the first neighbours. Portrait stacks them vertically with the same shrink. Between those positions, every measure is interpolated, so a cover grows and flattens as it slides in. Covers past the last side slot fade out over half a cover: from 2 to 2.5 covers out with Settings → Cover Flow → 5 covers, from 1 to 1.5 with 3 covers (`OPTION_COVER_FLOW_COVERS`, read on every frame). The position eases toward the selected album with a 70 ms time constant, at no less than about 4 covers per second, and never overshoots.
- Covers are drawn farthest first, so nearer covers overlap them. `gfx/image` draws a cover column by column with nearest-neighbour sampling, clipped to the current strip.
- `app/cover_cache` holds 7 half-size covers (56 px, 6,272 B each) for the center ±3, in slot `position % 7`, plus one full-size cover (112 px, 25,088 B) for the center, about 69 KB in total.
- Covers load in `update`, one per frame: the nearest missing half cover first, then the full cover once the motion has stopped. A cover is drawn from the full image when that's loaded for its album, otherwise from the half image, otherwise as a placeholder. Beyond ±3, covers that aren't loaded aren't drawn.
- Play opens the album's track list, a long Play toggles the favorite, and Back leaves. The screen is full screen: no header or status icons, and the title (★ for favorites) and album artist go under the cover. The first time it opens, it starts at the playing album, or at the first album.
- **Playlists and folders** (`OPTION_FOLDER_VIEW`, Settings → Folders & playlists). Like Settings → Artist albums for artists, album artists and genres (`OPTION_ARTIST_VIEW`), the browse screen hands a playlist or a folder to `cover_flow_screen_open_group` instead of opening a list. A playlist's links are tracks, so its tiles are its runs of consecutive tracks from one album (a later run of the same album is a tile again); opening counts the runs once, and a tile is found by walking runs from the nearest tile already known. A folder whose links are only subfolders shows them as tiles, each with the cover of the album of the first track in its subtree (folders are depth-first, so that's the first folder from it onwards, while still inside it, that has tracks). No random tile there. ▶ on a folder of folders moves the same screen into it and Back moves it out to the folder it came from, down to the folder it was opened at; a folder with tracks opens as a list. A list opened from Cover Flow, and every list below it, never opens Cover Flow again (`BrowseScreen.in_flow`), since there is one Cover Flow screen. The flow keeps the 7 visible tiles (`CoverFlowTile`: position, album, folder, first link) and fills them in `update` and `enter`, so drawing never reads the library.
- Position 0, before the first album, is **Random album**: its cover is a 48 px shuffle mark drawn once into a static image (white crossing arrows on dark slate), and its text is "Random album" / "Play any album". Play there picks one of the music albums with `core/random` seeded from the microsecond clock, plays it from its first track in track order (shuffle off for that queue), moves the flow to that album and opens Now Playing. The albums sit at positions 1 and up, so the cover cache slots and the playing-album lookup are offset by one.

## Rendering

The panel keeps its own image memory, so we never hold a full framebuffer. The strip renderer clears a 320×34 buffer, asks the current screen to draw into it, pushes it to the display, and moves on to the next strip (notices use 6-row strips, so a USB DAC stream is served between them; the changed rows go out 4 at a time with `hal_audio_service` after each). Before pushing, `gfx/frame_diff` compares a hash of every row (FNV-1a over pixel pairs) with the previous frame's (680 bytes for 170 rows), and only the span of changed rows in each strip goes to the display. An unchanged frame sends nothing, and moving a selection sends a few rows. `app_start` forgets the hashes, so the first frame is always sent whole. After the screen, the app draws the status icons (play state on the left of the header, battery on the right, both inside the header insets), the toast and the frame overlay. The overlay shows the average frame time and its split: u (input, player and screen update, including card reads), d (drawing and hashing) and s (sending to the panel). The renderer clears every strip to the theme background, so screens don't fill it again. Screens marked `full_screen` (the key test) get no status icons. While the start-up or goodbye fade runs, the app draws only the fade (centred text in the title font, blended from the background to the text colour) and drops key events. `app_show_splash` starts the 0.5 s "EchoPod" fade after `app_start`. While a track plays, turning the screen on pushes Now Playing, unless the top screen sets `stays_on_wake`. Idling in a menu never leaves it. Pushing or popping a screen by key slides it (`ui/slide`, 240 ms, cubic ease-out): the title bar stays and switches its title halfway, and both screens are drawn shifted below it through `canvas_shifted`; if either screen is full screen, the whole screen slides. Waking into Now Playing doesn't slide. Browse levels keep two row caches so both sides of a slide have their text. A long Power press saves the session at once, shows "Goodbye" fading out over 1 s, then turns off. With the screen off it turns off straight away. Drawing uses screen coordinates and clips to the strip. Lists skip rows outside the strip, and glyphs outside the clip are culled. This saves ~85 KB of RAM compared with a full framebuffer.

## Responsiveness

- **Animation speed.** Settings → Animations (`OPTION_ANIMATION_SPEED`) scales the slide duration and the Cover Flow time constant through `settings_animation_ms`: Normal ×1 (240 ms, 70 ms), Slower ×1.5 (360 ms, 105 ms), Faster ×0.6 (144 ms, 42 ms). Frames aren't paced: the app renders whenever a slide, fade or motion runs, so a slower animation also gets more frames.
- **Frames.** When the last frame changed no row, `app_step` draws the next one only after a key event, an animation (fade, slide, frame overlay) or 100 ms (`IDLE_RENDER_MS`), or when a scrolling label's next pixel is due: `marquee_offset` notes how long its offset will stay the same (`marquee_wait_ms`) and the frame keeps the soonest, so scrolling text (40 px/s) gets a frame at each 1 px step and moves evenly; before, a frame that showed the same offset counted as unchanged and the next waited 100 ms, so the text alternated between 1 px and 4 px jumps, so a still menu stops redrawing every pass. Updates still run every step. With the screen on and no frame due, `app_idle` is true and the device main loop sleeps with WFI until the next SysTick, as it does with the screen off.
- **Keys.** Screens that set `select_on_press` (menus and choice lists, which have no long-Play action) switch ▶ to `KEY_BEHAVIOR_PRESS`: it acts on the way down instead of waiting for the release, and the release is ignored, even if the screen has changed meanwhile.
- **Saving.** Player changes (start, pause, skip, queue edits, the 15 s timer) only mark the resume file for saving; `player_flush_save` writes it at the end of the step, after the frame is drawn. `player_save` still writes at once (shutdown, USB, release of the output).
- **Browse rows.** A browse level keeps the rows of its last window; scrolling by less than the window moves the kept rows and reads only the new ones.
- **Album keys.** `library_album_key` reads the artist and title in 32-byte pieces up to the end of each string, not 255 bytes each. `favorites_store_contains_album` answers false without reading when there are no favorites, and Favorites collection stops once every saved key is found.
- **Covers.** `covers_find` keeps the first six levels of its binary search in RAM (`top_keys`, 64 nodes) and searches the last 64 entries from one read, so a repeated lookup costs one index read instead of about twelve.

## Generated code

- `src/library/sort_fold_table.{c,h}` is generated by `tools/fold_table.py` from Python's `unicodedata`: for each code point in Latin, IPA, Greek, Cyrillic, Latin Extended Additional, Greek Extended, punctuation, letterlike and number forms, enclosed alphanumerics, kana, CJK compatibility ideographs, ligatures and fullwidth/halfwidth forms, the NFKD-decomposed, mark-stripped, case-folded text the PC indexer's `sort_key` gives it. `library/sort_key` applies it (plus Hangul syllable decomposition and ASCII lowercasing), trims Unicode whitespace and drops a leading "the ". Regenerate with `.venv/bin/python tools/fold_table.py --output src/library --style .clang-format`; `sort_fold_up_to_date` checks it.
- `src/lang/packs/` is generated by `tools/lang_pack.py` from `assets/lang/` and the catalogue (see Languages). Never edit it by hand.
- `src/fonts/` is generated by `tools/font_build.py` from `assets/fonts/fonts.json` and the TTFs in `assets/fonts/`, and `src/fonts/packs/` by `tools/glyph_pack.py` from `assets/fonts/glyph_pack.json`. Never edit either by hand.
- Fonts are Inter (SIL OFL 1.1, license in `assets/fonts/inter/OFL.txt`), pre-rendered to 4-bit coverage. The built-in tables in `fonts.c` hold ASCII and common punctuation only. Everything else comes from glyph packs, read on demand (below). On the device the built-in tables aren't in the code window: they are resident tables, read from the image into their own RAM at boot (see Code size).
- Regenerate with:

  ```sh
  .venv/bin/python tools/font_build.py --config assets/fonts/fonts.json --output src/fonts --style .clang-format
  .venv/bin/python tools/glyph_pack.py --config assets/fonts/glyph_pack.json --output src/fonts/packs
  ```

- The `fonts_up_to_date` and `glyph_packs_up_to_date` tests fail if the committed output differs from a fresh build. `glyph_pack.py` skips a face whose font file is missing (the CJK font isn't in the repository yet), in both modes.
- **Glyph packs:** `assets/fonts/glyph_pack.json` lists the faces in face order (face 1 first): `cjk_16` and `cjk_12` (Noto Sans CJK SC, SIL OFL 1.1: the 2,350 Hangul syllables of KS X 1001, the 6,763 hanzi of GB 2312, the 5,401 hanzi of Big5 level 1 (481 of them not already in GB 2312 or JIS X 0208), the kanji of JIS X 0208, kana, CJK punctuation and fullwidth forms, 12,959 glyphs, about 1.72 MB and 1.06 MB), then the Latin letters of Latin-1 and Latin Extended-A, Romanian ș ț, the Vietnamese Ơ ơ Ư ư and U+1EA0–U+1EF9, Greek (U+0370–U+03FF), Cyrillic (U+0400–U+04FF) and the general punctuation the built-in table lacks (‐ ‑ ‒ ― ‖ ‗ ‚ ‛ „ ‟ † ‡ ‧ ‰ ‱ ′ ″ ‴ ‵ ‶ ‷ ‸ ‹ and ●) of each Inter font (about 34–53 KB each). A codec character set lists its lead-byte range and, when it isn't 0xA1–0xFE, its trail-byte ranges (Big5 uses 0x40–0x7E and 0xA1–0xFE). Big5 level 2 (6,012 more hanzi) would need two more faces of about 830 KB and 510 KB, more than the image has free (about 0.75 MB, split across the regions), so it isn't packed. Cyrillic, Greek and the extended Latin letters draw in track titles and artists as well as in the interface. Each `Font` has two 1-based `pack_faces`: the first for codepoints below U+2E80, the second for the rest (0 for none). `font_find_glyph` tries the built-in table, then that pack face, then `?`.
  - A face is one blob: a 32-byte header (`EGLF`, version 1, entry size 12, 42 entries per index sector, glyph count, directory, index and data offsets, size, and the image CRC of the rest), then at `0x200` a directory with the first codepoint of every index sector, then index sectors of 42 sorted 12-byte entries (codepoint, width, height, left, top, advance, 0, bitmap offset) padded to 512 bytes, then the bitmaps, packed as in `fonts.c`. A glyph whose bitmap passes 144 bytes is dropped (only the vertical kana repeat marks U+3031–U+3035 at 16 px, which the config leaves out anyway).
  - `gfx/font_pack` reads them through a `FontPackReader` (face, byte offset, length) into memory the platform hands over: the face headers and directories (up to 320 index sectors each), one index sector, and a 4-way set-associative cache of 160-byte slots (a glyph plus its bitmap). A lookup costs the index sector and the bitmap on a miss (the header and directory once per face), and nothing on a hit. Misses are cached too, so a character no face has is read once. A glyph from a pack stays valid until the next lookup; text drawing resolves its bitmap once per glyph (`font_glyph_bitmap`), not per pixel. The memory must be 4-byte aligned; the sets fill what is left after the face state (any count).
  - Device: `tools/make_image.py --glyph-face` (one per face, in face order; a missing file is an empty face) places the faces largest first into the image's free space (`0x30000`–`0x200000`, `0x2C0200`–`0x43C000`, `0x23CA00`–`0x240000`, `0x260200`–`0x280000`; `0x43C000`–`0x44C000` holds the USB overlay), sector-aligned, and writes a table at `0x2C0000` (`EGPT`, count, then offset and size per entry). The five faces come first; the language packs follow as entries 5 and up, in language order, and `board/glyphs.c` ignores them (`FONT_PACK_FACES` caps the faces it reads). `board/glyphs.c` reads the table from slot 1 at boot, before `app_start`, and reads faces through a one-sector buffer. Its table, sector buffer and the 33 KB cache memory (3.7 KB of face state, then 46 sets of 4 slots: 184 glyphs) sit in `.glyph_ram` (`0x03092000`–`0x0309A7FF`, above the language pack), and the resident tables take the top of High RAM (`0x0309A800`–`0x0309EFFF`): `board/overlay.c` and `rescan_overlay.ld` cap the rescan overlay at `0x15000` bytes (it is about 80 KB), so a rescan never overwrites either, and the High RAM diagnostic restarts the reader and reloads the tables after its test. After an update, until the restart, reads are refused (glyphs already cached still draw; others show `?`), like the rescan overlay and the core 1 programs.
  - Simulator: `platform/sim/sim_glyphs.c` loads `src/fonts/packs/<face>.bin` (paths from `glyph_pack.json`, through CMake) into memory and hands the same 52 KB of cache over. `test_sim_glyphs` checks the committed packs through it.

## Memory

- No heap in `src/`. Every buffer is static and sized at compile time.
- `src/` is freestanding C11 and includes only `<stdint.h>`, `<stdbool.h>` and `<stddef.h>`.
- The `target_audit` test cross-compiles `src/` for Cortex-M3 and reports flash and static RAM per module. It fails on any heap symbol and when static RAM exceeds `ECHO_APP_RAM_BUDGET_BYTES`.
- No recursion and no VLAs. The device stack is 16 KB (`0x03000000`–`0x03004000`). `board/stack.c` paints the unused part with a pattern at boot (`device/stack_mark`; first it writes and reads back a word at `0x03000000`, and skips the paint if that doesn't hold, since nothing below the stack's lived-in top has been proven on hardware) and Diagnostics → Stack shows the deepest point reached so far, as "used/16384 B" ("Not on this player" when the paint was skipped) (and ", stall n" when the previous run stalled, the depth at that moment). A static walk of the 0.10.0 release ELF and overlay (every function's pushes and `sub sp`, following direct calls plus the scan and cover callbacks) gives a worst case of about 3.1 KB from `board_main` through the cover pass (`cover_build` → `track_tags_read` → `tags_read_mp4`), plus 32 bytes and about 250 bytes for the SysTick frame and the stall screen, so the stack does not overflow on any static path.

## Code rules

- No comments in any code: C, CMake or Python. Names and small functions carry the intent. Prose belongs in `docs/`.
- Names:

  | Kind | Style | Example |
  |---|---|---|
  | Types | `PascalCase` | `KeyTracker`, `FrameStats` |
  | Functions and variables | `snake_case`; public functions prefixed with the module | `key_tracker_update` |
  | Constants and enum values | `UPPER_SNAKE_CASE`, prefixed | `KEY_GESTURE_PRESS`, `FONT_INTER_REGULAR_16` |
  | Files | `snake_case`, named after the module | `key_tracker.c` |

- Functions:
  - do one thing
  - stay short (aim for under 20 lines)
  - take at most 4 parameters; group anything more into a struct (`Label`, `TextStyle`, `MenuConfig`)
- Pass small value types by value and anything larger by pointer. Use `const` wherever data is read-only.
- No mutable globals in `src/`, except state owned by the composition root (`app.c`). Platform singletons live in `platform/`.
- Every rule in `core`, `gfx` and `ui` has a unit test. Test names describe the behaviour.
- `clang-format` (`.clang-format`) defines formatting. Warnings are errors (`cmake/project_options.cmake`).

## Device platform

`docs/hardware.md` summarises the hardware these drivers talk to.

- `platform/device/logic` holds the driver logic that doesn't touch hardware, so it builds and is tested on the host too:
  - `key_ladder`: ADC bands to keys
  - `key_scanner`: debounce over two samples, a transition queue, and ignoring the Power press still held from switching on
  - `panel`: the init streams for both panel variants, and the window and pixel commands, sent through a `PanelBus`
  - `tick_clock`: milliseconds and microseconds from the 24-bit SysTick down-counter
  - `sd_card`: the SD setup protocol (v1 and v2 cards, the ACMD41 retries (100 tries, but no more than 2 s), the RCA, capacity from the CSD register, the 4-bit bus), driven through an `SdHost`, and the wait for the transfer state (`sd_card_wait_transfer`: CMD13 up to 1,000 times, but no more than 2 s, after every write and when resuming), and the retry order for a card transfer (`sd_card_retry`): after a failure, resume the card and try again; after a second failure (or if the card doesn't resume), start it again from scratch and try once more; if starting fails, give up at once. At most three attempts and two restarts, counted in `SdRetryStats`
  - `emmc_layout`: finds the firmware slots (from the IDB's system size) and scans for the user volume on internal storage. It also answers which internal-storage writes are allowed: only the user volume and the two firmware slots, never the IDB, the SAVE block or the gap
  - `bt_module`: the Bluetooth module's command protocol. It waits up to 5 s for the `CV1` ready report, sends `CS00` to scan (once more after 4 s if nothing answers, `CP00` after 30 s), collects `CS` scan results until `CSEN` (dropping unnamed ones; a new scan keeps the earlier results, marks in `found_now` the ones it finds again, and past 6 drops the oldest; `CP00` stops a scan early), and sends `CQ00` every 3 s while ready, scanning or connected, every second while a connect runs and every 0.5 s while a paired reply waits for the link (stock's Bluetooth screen polls in every state). Connecting sends `CL06` + the picked address, from Ready or during a scan (once more as `CH06` after 4 s if nothing but `CQ` answers arrived, `CT00` and a failure after 30 s); `CLOK` means paired, `CLER`/`CHER` failed, `CHOK` connected, `CQO` + address + name connected in any state, including while a connect runs, and `CT`/`CTOK` means the link dropped. A `CQ` answer with another letter while connected only counts as a drop when the same capital letter arrives on two `CQ` answers in a row (one odd answer, or a byte that isn't a capital letter, is ignored: a single garbled frame used to drop the link, so a silent drop the module only reports through `CQ` now shows one poll, 3 s, later than before; `CQO` in between starts the count again). Disconnecting sends `CT00`. While connected, starting the stream sends `CY0` + `1E` + 0 and stopping it `CY0` + `00` + 0. As in stock, the `C` `86`/`87` notices only answer the module's own reports: the play state is what the module last reported (`CP` paused, `CC` playing; nothing on a new link). Starting the stream after a `CP` sends the play notice `C` `86` `30 30` 0 first and `CY0` + `1E` + 0 100 ms later; stopping it after a `CC` sends the pause notice `C` `87` `30 30` 0 first and `CY0` + `00` + 0 100 ms later; otherwise only the `CY0` frame goes out. (Sending a notice on every pause and resume, with the play notice after `CY0` `1E`, left the headphones silent a moment after some resumes.) Every new link first gets `CY0` + `00` + 0. The first stream start on a link that is less than 1 s old and hasn't reported `CP`/`CC` yet is held until the headphones report or the link is 1 s old: a `CC` sends `CY0` `1E` at once, a `CP` the play notice first and `CY0` `1E` 100 ms later (before 2026-11-05 `CY0` `1E` followed `CQO`/`CHOK` within about 1 ms, which the headphones could miss, so audio only started after a tap). A `CP` that arrives within 3 s of a stream start while the stream is on is answered the same way, play notice then `CY0` `1E`, instead of being left alone. The module's `CP`/`CC` (pause/play) and `CA`/`CB` (previous/next) reports count presses in `HalBluetoothRemote`; a `CP`/`CC` after `CLOK` also counts as the link coming up (the Buds send them as soon as they're in the ears), and while connected `CQ00` polling pauses for 50 s after one, as in stock. A dropped link, `CT` or `CTOK` ends the stream and clears the pairing result. While the stream is on, `board/bluetooth.c` holds GPIO2.0 high and GPIO2.14 low on every service pass, as stock does on connect, and restores them when the stream stops or the module powers off. Received bytes are split into frames as soon as a frame is complete; an incomplete frame is dropped after 2 ms of silence. It also keeps the last 12 bytes, counts bytes and frames, and logs the last 12 messages (frames other than `CS` and repeated `CQ` letters, plus the `CS`, `CP`, `CL`, `CH` and `CT` commands it sent) with the seconds between them; a frame whose letter after `C` is a capital the protocol doesn't know is logged too, as that letter and the next byte (a capital or digit, else `.`), then skipped one byte at a time; the log and the devices found survive a power-off and power-on, so a restart keeps the evidence
  - `usb_device`: the descriptors and standard requests for a bulk-only mass-storage device (`1209:0001`, the pid.codes test ID), plus GET_MAX_LUN and the mass-storage reset. Full speed only (64-byte bulk packets; the device qualifier and other-speed configuration stall) until the board allows high speed; then it serves a device qualifier and an other-speed configuration (type 7, the opposite speed's configuration), and the configuration's bulk packet size follows the speed the board reports (512 at high speed, 64 at full speed; EP0 stays 64)
  - `usb_audio`: the USB Audio Class 1.0 device for DAC mode (`1209:0002`, the next pid.codes test ID, so hosts don't mix up its cached descriptors with mass storage's): the device and configuration descriptors, interface alternate settings, the sampling-frequency and feature-unit class requests, and the FIFO split. Everything else (address, configuration, status, strings) goes to `usb_device`. See USB DAC mode
  - `usb_audio_sink` and `stream_drift`: USB audio packets into the music ring, and the ring-level controller that keeps it near 20 ms of audio (see USB DAC mode)
  - `msc`: the bulk-only transport and SCSI commands over up to two LUNs. Failed reads and writes are counted per LUN (`lun_failures`), and the command history keeps internal storage's commands other than reads, writes and ready checks plus every failed read or write on either LUN. A reply shorter than the host asked for is padded with zeros and reported in the residue instead of stalling. Ejecting a LUN marks only that LUN absent. Given a buffer (`msc_use_write_buffer`), WRITE(10) data collects there and reaches the drive in one write call per full buffer, plus one for the rest; a failed call fails the whole command. Without one, each sector is its own write. READ(10) uses the same buffer the other way: when the next sector isn't loaded, one drive read fetches as many sectors as the command still needs, up to the buffer (64 sectors, 32 KB: one multi-block CMD18 on the card), and the bulk IN packets are served from it. Reading one sector per command held reads over USB at about 1.2 MB/s
  - `usb_fallback`: when to give up on high speed: watching starts at the first bus reset of a high-speed session, a working session (configured and through two SCSI commands) stops it, and 10 s without one asks for a full-speed reconnect, once (`fired` records that it did)
  - `vbus_debounce`: when a mass-storage session counts the cable as gone: only after VBUS has read absent for at least 100 ms and on at least 3 readings in a row; a shorter dip is ignored and counted (`dips`)
  - `card_write`: the order of a card write through a `CardWriter`: one block is CMD24 then a wait for the tran state; several are one CMD25, then CMD12 (sent even after a failed transfer, so the card leaves the receive state), then the wait, which is skipped if the stop failed
  - `image_crc` and `updater`: the image check and the slot writer. The check accepts our 5 MiB shape (size, magic, fw size `0x44C000`, header copy, trailer CRC, fits a slot) and reports an image already in slot 1 as installed. It also accepts FiiO's 8 GB stock image as `UPDATE_STOCK` (33,554,436 bytes, magic, brand "Rockchip", a sector-aligned fw size whose header copy fits below 32 MiB and matches, trailer CRC, fits a slot, and the 8 GB marker) and refuses the 512 MB model's. The fw size doesn't tell the models apart: it was `0x01FC4000` for the 8 GB images up to 3.9.0 and `0x01FCC000` for the 512 MB ones, but FiiO's 8 GB 4.0.0 uses `0x01FCC000` too. Instead, each stock image holds the 8.3 names its own updater looks for: the 8 GB images (3.7.0–4.0.0) contain `HIFIEC00IMG` and never `MINIV100IMG`, the 512 MB ones (3.9.0, 4.0.0) the reverse. The CRC pass scans every 8 KiB chunk for both, including a marker split across two chunks, and an image is stock only with the 8 GB marker and without the other; a stock install writes `[0, 32 MiB)` the same way, as stock's own writer does. The install fills slot 2, then copies slot 2 into slot 1. For each slot it first writes `0xFF` over the first 8 KiB, then every other 8 KiB chunk, then the first chunk last. Chunks that already match are skipped, and every write is read back. One slot is complete at every moment
  - `fat`: a read-only FAT16, FAT32 and exFAT reader over a `BlockDevice`. It reads unpartitioned cards or MBR partition 0, follows FAT long names and exFAT name entries (UTF-16, including surrogate pairs), matches path components exactly by code point and ASCII letters in either case, and reads at any offset. FAT files follow a per-file cluster cursor; exFAT files marked NoFatChain are contiguous and skip the FAT. Cluster walks and directory scans are bounded, so a corrupt chain can't hang the player
- `platform/device/board` is device-only. It holds the register helpers, GPIO and pin mux, startup (the vector tables and its start-up steps), the linker script, a minimal `memcpy`/`memset`, and the HAL implementations.
- `platform/device/core1` is the program for the second core: its own startup, `main` and linker script (code at core 1 address 0; the MP3, AAC and Opus programs keep data at `0x01021000` with the stack top at `0x0102E000`, the FLAC program keeps both in code RAM, see FLAC blocks below; each linker script sets `core1_stack_top`). It builds to `core1.bin`, which is linked into the core 0 image as read-only data. `device/core1_control` holds the power-up, start and stop sequences and the shared-block layout, tested on the Mac; `board/core1.c` runs them.
- **Build:** `cmake --preset device && cmake --build --preset device` cross-compiles to `build/device/platform/device/echo_device.elf`. Then `tools/make_image.py` packs it into `build/device/HIFIEC90.IMG`. The outer header is written from format constants (magic `0x76543210` at `0x00C`, `4` and four `0x200` words at `0x050`–`0x06C`, `1` at `0x19C`, the fw size at `0x1F4`) plus our date, brand, build tag, fw1 end at `0x080` and `ECHO_FIRMWARE_VERSION` (major << 24 | minor << 16 at `0x004`, patch at `0x008`), with an empty part chain and zero marker bytes, so the image builds from the repo alone.
- **Release build:** `cmake --preset release && cmake --build --preset release` builds the same image into `build/release/HIFIEC90.IMG` with `ECHO_RELEASE=ON`, which links `src/app/diagnostics_menu_release.c` (Key test, Firmware, Battery, Last start, Last step, Last battery, Last USB, USB errors, Jack 3.5, Jack 4.4, Panel, Clock, Last update, Last stack, Stack, Power, Savings) instead of the full developer menu in `diagnostics_menu.c`. The rows both menus share live in `diagnostics_rows.c`. `tests/app/test_release_diagnostics.c` checks the short menu.
- **Code size:** the code window is `0x2666C` (157,292) bytes. `tools/size_report.py --build build/release` (or `cmake --build --preset release --target echo_size_report`) reads the linker map and the ELF and lists the bytes per object, per library and the biggest functions, tables and `.bss` objects, with the free bytes against every limit below; every image build prints the limit lines. Three things keep the window from filling: `-Os` on cold code, link-time optimisation, and the resident tables.
  - **Link-time optimisation:** the libraries only the core 0 link uses (`app`, `ui`, `fonts`, `gfx`, `settings`, `playback`, `sound`: `echo_lto` in `cmake/project_options.cmake`) and the board sources compile with `-flto` (fat objects, with `-g` so the size report can name their files) and `echo_device` links with `-flto -flto-partition=one`. GCC streams each function's optimisation level, so the per-file `-O2`/`-Os` below survive the link. `core`, `codec`, `dsp`, `library` and `device_logic` are LTO libraries too (2026-11-06, about 2.8 KB more). Core 1 shares `core`, `codec` and `device_logic`, and `-flto` changes the regular code GCC puts in a fat object (the same `flac.c` at `-O2` compiles to different bytes with and without it), so cross builds also have `echo_core_plain`, `echo_codec_plain`, `echo_dsp_plain`, `echo_device_logic_plain` and the `echo_hal_plain` interface, built from the same sources without LTO; the core 1 programs and the USB overlay link those, and the core 1 binaries are byte for byte the ones built before. The rescan overlay links the fat objects' regular code. `third_party` stays out of LTO, and the core 1 and overlay links pass `-fno-lto`. Functions the overlays call in these libraries are in `ECHO_OVERLAY_IMPORTS` like the board's (see USB overlay), since LTO would otherwise make them local, and the overlay would quietly link its own copy (more code, and for a module with state such as `i18n`, a second state). `tools/make_image.py` refuses an overlay that defines a function or table the main program also has (by name, ignoring LTO's `.isra`/`.lto_priv` suffixes), naming what to add to the list. `libc.c` and `startup.c` stay out too, and the two handlers reached from inline asm (`board_systick_handler`, `device_fault_handler`) are marked `used` so LTO keeps them. Saved about 5 KB.
  - **Resident tables:** read-only tables marked `ECHO_RESIDENT` (`core/resident.h`; the attribute is on in cross builds of the libraries that define it: `fonts`, `app`, and since 2026-11-06 `codec`, `device_logic`, `library` and `sound`, but never the plain twins core 1 links) are linked into `.resident` at `0x0309A800` (18 KB, the top of High RAM, taken from the glyph cache) instead of the code window. The ELF keeps the section, `tools/make_image.py` takes it out and stores it at image offset `0x238200` behind a 16-byte header (`ERES`, size, CRC of the rest, CRC of the code it was built with; the section starts with 16 zero bytes for it), and `board/resident.c` loads it into place at boot (`board_glyphs_start`, before the Battery low check, so every notice has its glyphs) through `board_overlay_load`, like the overlays: an intact copy already in RAM, else slot 1, else slot 2, each checked for the magic, the size, the CRC and the code CRC (so tables from another build, whose layout could differ, are never used); on any failure the region is zeroed, and text draws nothing rather than garbage. Only libraries that neither core 1 nor the rescan overlay link may use it (the overlay would place such a table in its own window). The built-in font tables (15 KB) live there, and since 2026-11-06 the FLAC CRC-8 and CRC-16 tables, the AAC sample rates, the MP3 probe's bitrate tables, the sort initials and the equalizer preset shapes (about 1.3 KB more). Nothing that runs before `board_glyphs_start` (the panel init streams, the key ladder, the battery tables, the stall screen's font) may move there. If the tables don't load, internal storage didn't answer, so the language pack and the glyph faces are missing too, and FLAC frames then fail their CRC checks. Saved about 14.5 KB, then 1.3 KB.
  - **USB overlay:** everything a USB session does after the host's bus reset (the mass-storage session with `msc`, `usb_device`, `usb_fallback` and `vbus_debounce`; the DAC session with `usb_audio`, `usb_audio_sink` and `stream_drift`; the update check and install with `updater`; and the DWC2 transfer code, `board/usb_port.c`) is linked as `echo_usb_overlay` at `0x0307A000`, like the rescan overlay, and stored at image offset `0x43C000` (up to 64 KB, `EUSB` header with the code CRC). Its entry table (`UsbOverlayEntry`: magic, storage session, DAC session) follows the header at `0x0307A010`. Unlike the rescan overlay it has a `.bss` (the 32 KB mass-storage write buffer, the update's FAT volume, the ports, the sink: about 41 KB), which the loader zeroes after the code; code and `.bss` must fit the `0x15000` window, which `usb_overlay.ld` and `make_image.py` check. The window overlaps the core 0 FLAC decoder's `.high_ram`, so `board/main.c` calls `app_release_audio` and `board_audio_shut_down` before it loads the overlay. What stays resident: listening (`board/usb.c`: VBUS, PHY power, the core reset and connect, the bus-reset check; `board/usb_listen.c`: the state shared with the overlay, `UsbShared`, which keeps the high-speed fallback, Last USB, the DAC level and the restart-pending flag across sessions), the plug-in prompt and the failed-start report, since they run while music plays. The overlay calls back into the main program by symbol (`--just-symbols`); because LTO would make those functions local or inline them away, `platform/device/CMakeLists.txt` lists them in `ECHO_OVERLAY_IMPORTS` and links the main program with `--require-defined` for each, so they stay global; a function missing from the list fails the overlay's link. If the overlay can't be loaded (no intact copy in RAM and neither slot holds one built with the running code, or internal storage doesn't start), the session shows "USB code missing: restart the player" ("Restart the player to finish the update" after an install), waits for a key and powers USB down; music stays paused. Saved about 12.4 KB of code and 21 KB of the loaded total.
  - Libraries in `src/` that link `echo_compact` and the cold device files listed in `platform/device/CMakeLists.txt` and `platform/device/logic/CMakeLists.txt` (start-up records, the updater, the image CRC, card file creation, the Bluetooth protocol, the DAC set-up sequence, the USB descriptors and requests, the USB sessions, and since the equalizer the audio driver's control code in `board/audio.c`, `board/dac.c`, the MP3 probe, the FAT layout, mass-storage commands, the battery gauge, clock switching, core 1 start-up, the panel init streams, the PLL words, SD card start-up, the key tracker and a few other set-up files) are compiled with `-Os` in cross builds; the per-sample path (the engine, the equalizer, its sources, core 1's decoders), FAT reads and card transfers, the panel push, the clock and SysTick, the USB transfer code (`board/usb_port.c`, in the USB overlay) and the USB audio sink stay at `-O2`; `board/usb.c`, which now only powers, resets and connects the core, is at `-Os`. At 0.10.0 the release build had 3,488 bytes of the window free and the developer build 1,712; with LTO and the resident tables (2026-11-05) the release build has about 23 KB free and the developer build about 21 KB, and the loaded totals in the image rules below are about 398 and 400 KB. After the power work (2026-11-06) the release build had 3,572 bytes free and the developer build 1,644; with the USB overlay the release build has 15,992 free (loaded total 404,320) and the developer build 14,060 (406,348); with LTO on the shared libraries, the new resident tables and `board/usb.c` at `-Os`, the release build has 20,188 free (loaded total 400,124) and the developer build 18,348 (402,060). To get there the developer Diagnostics menu dropped its Fonts, Long names, Stopwatch, Test tone, DMA tone, Tone 192k, Tone 176k, Boot clocks, Boot PLL, Loop cycles, Stall test, Watchdog test, High RAM and USB register rows (2026-10-31); the HAL calls behind them remain, but the descriptions below that name those rows refer to builds before that date.
- **Image rules,** enforced by the linker script and the builder:
  - `.data` holds only the 8-byte entry vector; no initialised mutable globals.
  - Code stays below the row-0 end (`0x030771D4`).
  - `.bss` ends below `0x0304C000`.
  - Code, `.data` and `.bss` together stay within 437,600 bytes. On the player, images totalling 439,792 and 440,372 bytes stayed black before EchoPod's first instruction (not even a backlight blink at entry), while 437,600 and below started, whether the extra was code or `.bss` (2026-10-31). Each limit above held on its own; only the total failed. The cause isn't known; the boot ROM's loader, which moves the code and clears `.data` and `.bss` from the row table, is the likely place.
  - Nothing loaded is left out of the image. The resident tables, the rescan overlay and the USB overlay aren't loaded by the boot ROM: they sit beyond the fw1 end and the firmware reads them itself.
- **Run model:** the main loop polls the drivers; the 1 ms SysTick interrupt keeps time and runs the stall watch (see below). The display driver samples the keys before and after every strip it pushes, so key presses aren't missed during slow frames.
- **Storage:** `board/mmc` drives the DW-MMC controller (commands, polled single- and multi-block reads and writes, CMD12, the card clock); `board/sd` and `board/emmc` write through `device/card_write` and `board/sd` powers the SD slot and checks card detect. Every SD read and write goes through `sd_card_retry`: resuming is one CMD13, and if the card isn't in the transfer state a CMD12 and up to 1,000 more CMD13s within 2 s; restarting is the whole start-up (controller reset, CMD0 onwards, a new RCA). A card that isn't present or didn't start is tried again whenever it is next needed (the file HAL's first mount after a reset, or a USB session) instead of once per boot. `sd_health` keeps the retry counts, the number of successful starts and the controller step and status of the last failed card transfer. Internal storage has no retries. `board/emmc` starts internal storage (8-bit bus at 24 MHz) on first use and refuses any write outside what `emmc_layout` allows. The file HAL mounts the card (FAT16, FAT32 or exFAT) on the first open, and the internal storage's user volume on the first `/:internal` path (see Internal storage music), and can hold 8 files open at once on the two together. Writes go in place or through `fat_reserve` (see Settings and favorites).
- **USB:** the main loop watches VBUS. When the cable is plugged in, `board/usb_session` powers the PHY and the polled DWC2 core (`board/usb`) and connects, without touching audio or the screen. It asks for high speed (DCFG speed 0) unless high speed already failed since power-on; at enumeration done it reads DSTS and uses 512-byte bulk packets at high speed and 64 at full speed, on the core's reset FIFO sizes (RX 147 words, shared TX 128), one packet per bulk OUT transfer. If a high-speed session isn't working (configured and through two SCSI commands) 10 s after the first bus reset (`device/usb_fallback`), it reconnects at full speed and stays there until the next power-on. The main loop then keeps running and checks GINTSTS for a bus reset on every pass, for up to 3 s, with the CPU clock held at 96 MHz or more. No reset means a charger: USB powers down quietly and the player carries on, playing and charging. Listening runs from resident code (`board/usb.c`, `board/usb_listen.c`); once a host's reset arrives, the session itself runs from the USB overlay (see Code size), loaded after the music is released. With a host:
  - the app shows "Computer found" and its steps pause. Before the audio power pins are silenced, `app_release_audio` saves the bookmarks and unloads the player's track (it stays paused at its position) and `board_audio_shut_down` stops the DMA and powers the DAC path down through `board/audio.c`. Silencing the pins behind the audio driver's back used to leave it believing the path was still up, so nothing played after the session until a restart
  - LUN 0 is the internal-storage user volume and LUN 1 is the SD card, both read/write. Sense data is kept per LUN. At the start of the session `sd_prepare` checks that a card started earlier still answers (CMD13 with its RCA, in the transfer state) and starts it again if not, so a card taken out and put back while the player was on gets a new RCA instead of failing every read; a card that wasn't there or didn't start at boot is tried again. If the card was started again during the session, the app reloads from it afterwards as if it had been written
  - the session ends when the cable has read absent for 100 ms (`device/vbus_debounce`; a single low VBUS reading used to end it). The backlight goes off after 30 s without a new counter notice or a key press (keys are read and dropped during the session, and any press lights it); the CPU clock is left alone, since the card and USB run during the session. A session that ended as unplugged while VBUS is back right afterwards (a dip, not a pull) skips the "USB unplugged" key wait and listens again at once in Storage mode without the plug-in prompt; before, the player stayed a charger until the cable was replugged
  - if the controller fails to start, `board/usb_report` shows four notices (a key press moves on): the core ID and OTG control after power-up; the failed init step (with `0x10` set when internal storage started) and GHWCFG4; then GINTSTS and OTG control after the wait. This is temporary, while USB is brought up on hardware
  - the session ends when every LUN that was present has been ejected, or the cable is pulled. If the session wrote to the card or to internal storage, the file HAL forgets both mounts and its open files, and `app_start` reloads the app from the changed card. If the cable was pulled while a drive was still mounted, a notice says recent changes may be lost. Diagnostics → Last USB shows how the last session ended (ejected, or unplugged with how many drives still up), the sectors written to each drive and any writes refused after an eject. Diagnostics → USB errors shows `None` or, for the last session: `E<internal>/<card>` failed commands per LUN, `r<n>` SD transfers retried, `i<n>` SD card starts during the session (including `sd_prepare`'s), `s<step>:<RINTSTS low 16 bits>` from the last failed card transfer (`MmcStep` numbering), `b<n>` bus resets while configured (`UsbPort.configured_resets`: the host resetting a working port), `v<n>` VBUS dips that were ignored, and `FS` when the high-speed fallback fired in the session or `fs` when it started at full speed because it had fired earlier Then `board/update` opens the highest-numbered `/HIFIECnn.IMG` (00–97, stock's rule) on internal storage and installs it if it's valid and differs from slot 1, or if it's FiiO's stock image, showing progress and the result (a key press dismisses it). Whatever the check decided (installed, failed at the last 5 % mark shown, refused with the refusal code, or already installed), `board/update.c` then reads the eMMC's status (CMD13) and keeps the outcome twice: in the start record (Last start's `.noinit` RAM, so it survives RST and a power-off on a cable) and in `/.echo/update.bin` on the card (`app/update_record`, 16 bytes: `EUPD`, result, detail, whether the eMMC answered, its status word, a checksum; written after `storage_reset`, since the host may have rewritten the card), so it survives a battery power-off. Diagnostics → Last update shows the file if it reads back, else the RAM record: "Installed, eMMC ready" (ready-for-data in the transfer state), "Installed, eMMC state 6", "Failed at 35%, eMMC no reply", "Refused E3", "Already installed" or "None". Finally `app_wake` restarts the screen timeout. The new firmware starts at the next power cycle, because a warm reboot doesn't work on this hardware
- **USB DAC mode** (untested on hardware): Settings → USB mode chooses Storage (the default, the session above) or DAC; `settings_store_apply_hardware` passes it to `hal_system_set_usb_mode`, and `board/main.c` reads it when the cable goes in, so a change takes effect at the next plug-in. Listening for a host, the 3 s wait and the charger case are the same as for mass storage. With a host, `board/usb_dac_session` runs instead of the mass-storage session:
  - **Class and speed:** USB Audio Class 1.0, full speed only (`usb_device_allow_high_speed(false)`, DCFG speed 1), so it needs no driver on Windows 10 and later, macOS, Linux, Android or iOS. Interface 0 is Audio Control: an input terminal (USB streaming, 2 channels) into a feature unit (ID 2: master mute and volume) into an output terminal (headphones). Interface 1 is Audio Streaming: alternate setting 0 has no endpoint, 1 is 16-bit stereo PCM, 2 is 24-bit stereo PCM (3-byte subframes), both at 44.1 and 48 kHz, on isochronous OUT endpoint 1 (adaptive, 1 ms interval) with room for 49 frames (196 and 294 bytes). 88.2 and 96 kHz are left out because their largest packet (up to 582 bytes at 24-bit) doesn't fit the RX FIFO (see FIFOs below). Android's USB audio picks the highest rate a device offers, and some Windows setups do too, so offering them meant silence on those hosts. The device descriptor says USB 1.1 and has no serial number.
  - **Synchronisation:** adaptive, by ring level, with no feedback endpoint. The I2S clock runs from the player's MCLK, so the computer's rate and the DAC's drift apart slowly (a few frames per second). `device/usb_audio_sink` converts each packet into the music ring (16-bit samples to the top half of the word, 24-bit samples shifted up by 8, two words per frame, the same format as music) and measures the fill as frames written minus frames the DMA has played. `device/stream_drift` keeps it near 20 ms: when the fill is more than 4 ms off, one packet in eight drops its last frame (too full) or repeats it (too empty) until the fill is back within 1 ms of the target, or past it. One frame every 8 ms (2,600 ppm at 48 kHz) is still far faster than any clock drift, and a lone dropped or repeated frame isn't audible; until 0.11 every packet was corrected, a 2 % change for the length of the correction. A clock offset of n ppm therefore shows as about 2.9 × n dropped or repeated frames a minute at 48 kHz, in bursts of about 145 a little over a second long. At 44.1 kHz the I2S divider is rounded (11,288,960 / 256 = 44,097.5 Hz, if the MCLK in the rate table is exact), so the player runs about 57 ppm slow and should drop roughly 150 frames a minute on top of the computer's own offset; not measured. The sink also keeps the 20 ms after the newest frame silent, so if packets stop the DMA plays silence rather than old audio; if the DMA overtakes the writer (packets lost for longer than the buffer) or the ring would overflow, writing restarts 20 ms ahead of the DMA after a short silence. An asynchronous feedback endpoint would avoid the dropped frames, but it needs a second (IN) isochronous endpoint, a measured rate in 10.14 or 16.16 format and per-host quirks, none of which can be checked without hardware.
  - **Rates and formats:** the host's SET_CUR on the endpoint's sampling-frequency control (3 bytes, either of the two rates; others stall) or a new alternate setting stops the output, restarts the DAC path at the new rate through `board_audio_stream_open` (the same `dac_path_start` as music, with its ACODEC row and divider), and primes the ring again: the DMA starts once 20 ms is buffered. 100 ms without packets (the computer stopped playing) also stops the output until packets come back. GET_CUR reads the rate back.
  - **Volume:** the feature unit's volume runs from −64 dB to 0 dB in 0.5 dB steps (GET_MIN `0xC000`, GET_MAX 0, GET_RES `0x0080`). While a stream is open the DAC's PCM volume registers stay at the level-50 value of the jack's curve (`stream_hardware_value`, set at `board_audio_stream_open`; `dac_path_set_fades(false)` makes the mute and unmute around a DMA start or stop single register writes instead of 2 ms fades), and the volume is applied in software: `board_audio_stream_attenuation` gives the player's DAC-mode level as half-decibels below that top value (the curve table, so level 30 is the same loudness as in music), the session adds the host's attenuation (mute from either side mutes) and `usb_audio_sink_set_attenuation` turns the sum into a Q24 gain from a 40-entry half-decibel table (one decade per 40 units). Each frame is scaled by that gain, which moves 1/128 of the way to its target per frame, so a step settles in about 20 ms without zipper noise and every stream start fades in from silence. Before 0.11 each step went through `fade_to`'s I2C writes (2.4 ms with the endpoint unserved per step), which dropped packets and left `stream_drift` repeating frames until the ring recovered. The trade-off is resolution: at −60 dB the 24-bit samples keep about 14 bits, the same loss the DAC's own digital volume has. The DAC-mode level starts at `SETTINGS_DEFAULT_DAC_VOLUME` (30), is kept in the settings when it changed, and the music level comes back after the session.
  - **Keys:** `app_dac_keys_start`, `app_dac_next_key` and `app_dac_keys_stop` lend the session the app's input path: transitions go through the same `oriented_key` as the screens (so Swap volume buttons and a portrait orientation turn the rocker the same way), a `KeyTracker` with the DAC timings (1 s holds on the rocker and Back, 400/120 ms repeats) and `now_playing_command_with` with the Volume buttons setting, so a tap is volume and a 1 s hold is next or previous (or the other way round with *Tap: skip, hold: volume*), a held rocker keeps changing the volume for 2.5 s after a volume tap as on Now Playing, Play is play/pause, Menu is next when it is set to Next track, and Back held for 1 s leaves the session. Power does nothing.
  - **Media keys:** interface 2 is a HID consumer control (class 3, no boot protocol): a 29-byte report descriptor with Play/Pause (0xCD), Scan Next Track (0xB5) and Scan Previous Track (0xB6) as bits 0–2 of a 1-byte input report, on interrupt IN endpoint 2 (8-byte packets, 10 ms). `usb_audio` answers GET_DESCRIPTOR for the HID (`0x21`) and report (`0x22`) descriptors on interface 2, SET_IDLE and SET_PROTOCOL with a status, GET_IDLE (0), GET_PROTOCOL (1) and GET_REPORT (the last report sent), and SET_INTERFACE 2 alt 0; bcdDevice is 1.01 (1.00 before the interface) so hosts that cache descriptors by VID/PID/bcdDevice read them again. At SET_CONFIGURATION `board/usb.c` programs DIEPCTL2 with MPS 8, USBActEP, EPType 11 (interrupt), TxFNum 1 and SetD0PID and unmasks DAINTMSK bit 2; `usb_send_report` writes one report through TX FIFO 1 (unused by the DAC configuration until now, so the FIFO layout and the RX room for a 294-byte isochronous packet are unchanged) and `report_busy` holds until that endpoint's transfer complete. The session queues a press report and a zero release report per key and sends one per completed transfer. Whether stock sends media keys, and which, hasn't been checked.
  - **Audio driver:** `board/audio.c` has a stream mode for this: `board_audio_stream_open` stops music (`board_audio_shut_down`), clears the music ring and starts the path at a rate; `_play` starts DMA channel 5 over the ring as for music and fades up; `_pause` clears the ring and fades down and stops the DMA; `_consumed` gives frames played; `_close` shuts the path down. While the stream is open, `hal_audio_service` and the DAC's fade waits call the session's USB service instead of the engine, so drawing a notice or fading keeps the isochronous endpoint served. The session starts with `app_release_audio()` and `board_audio_shut_down()` and ends with `board_audio_stream_close()`, so music works as before afterwards. The audio power pins are never touched directly. The CPU runs at 200 MHz: the session's first notice turns the screen on, which raises the clock as in a mass-storage session, and opening the stream raises it too if needed.
  - **DWC2 in polled mode:** the session loop polls the core (four `usb_poll` calls per pass), the audio service (jack sense) and the keys. The changes in `board/usb.c`, cited against the DWC2 register map:
    - FIFOs: the same layout as mass storage (RX FIFO 0x120 words, TX FIFO 0 0x20 words at 0x120, TX FIFO 1 at 0x140). The core accepts an isochronous OUT packet only when the RX FIFO has room for a maximum-size packet (582 bytes, 146 words) plus its status entries, so the reset size of 147 words (`GRXFSIZ` `0x93`) drops every packet: on the player that showed as no packets received, an incomplete-ISO interrupt every frame and NAKIntrpt (DOEPINT bit 13) on endpoint 1. An earlier build computed its own split from the reset values, skipped it on this chip's layout, and so stayed at 147 words. The endpoint is therefore armed for 294 bytes (`USB_AUDIO_MAX_PACKET`, 49 frames of 24-bit stereo, proven on the player), the largest packet of any offered format.
    - Endpoint: at SET_CONFIGURATION, DOEPCTL1 gets MPS 294 (bits 10:0), USBActEP (bit 15) and EPType 01, isochronous (bits 19:18); DAINTMSK bit 17 and GINTMSK bit 21 are set (the core isn't wired to an interrupt, but the status bits are polled). A streaming alternate setting arms it: DOEPTSIZ1 = PktCnt 1 (bit 19) | XferSize 294, the same for every format and rate (a shorter packet ends the transfer), so it doesn't matter whether the host sends SET_CUR for the rate before or after SET_INTERFACE, then DOEPCTL1 EPEna (31) | CNAK (26) | SetOddFr (29) when DSTS bit 8 (the low bit of SOFFN, the current frame number) is 0, otherwise SetEvenFr (28), so the endpoint takes the next frame's packet. Each transfer complete (DOEPINT1 bit 0) re-arms it the same way while streaming.
    - Missed frames: GINTSTS bit 21 (incompISOOUT) means an armed isochronous OUT endpoint got no packet in a frame. If DOEPCTL1 is still enabled and its EO_FrNum (bit 16) matches the current frame's parity, the endpoint is switched to the other parity, then the bit is cleared.
    - Packets: GRXSTSP is popped once per poll; PktSts (bits 20:17) 2 with EPNum 1 is a packet for the sink, read into the port's 128-word packet buffer (the larger of a high-speed bulk packet and `USB_AUDIO_MAX_PACKET`); 3 and 4 are skipped as before.
    - Control OUT with data (SET_CUR): the request is held until its data packet (PktSts 2, EPNum 0) arrives on EP0, which `arm_setup` keeps enabled; then the reply is applied and the status stage sent (a zero-length IN, or a stall).
    - Control IN longer than 64 bytes (the 184-byte configuration descriptor): sent as 64-byte packets, each after DIEPCTL0 EPEna clears from the previous one (up to 100 ms each). Replies of 64 bytes or less go out exactly as before.
    - Mass storage is unchanged: these paths only run when the port has an audio device, and with one the bulk endpoint and MSC calls are skipped.
  - **Screen:** "USB DAC" with "Computer found. Starting...", then "Choose EchoPod as the sound output · Volume 30" while the host has no stream open, "48 kHz 24-bit · Volume 30 · Missed 0, dropped 0, repeated 0, restarts 0" while it has, or "The audio output didn't start.", each followed by "Battery 64%, charging" or "Battery 64%" (`hal_power_battery`: the charge pin is read, charging itself is hardware). Missed counts packets whose frame numbers (DSTS SOFFN, taken as each packet is popped, `usb_audio_sink_count_frame`) weren't consecutive while the output ran: the endpoint is armed for one packet at a time, so a polling gap that runs into the next frame re-arms it too late and loses that frame's packet. At full speed SOFFN holds the 11-bit frame number, which wraps from 2047 to 0; until 0.11 the gap was taken modulo 2^14, so every wrap (each 2.048 s of playing) added 14,336 to Missed. Dropped, repeated and restarts are the sink's counters, so a volume press that costs no audio leaves all four unchanged. While the output plays, the notice is redrawn only on a format or volume change; when it isn't playing (the computer paused or stopped), once a second when its text changed. Drawing has to leave the endpoint served at least once a frame: the audio service (which runs the session's USB polls) is called before each strip is hashed and after every 4 rows sent to the panel, notices are drawn in 6-row strips, and the message screen wraps its text once instead of for every strip. Measured on the PC (an optimised host build, scaled to the player by the frame hash loop, about 70 times slower there), the slowest 6-row strip of the DAC notice should take roughly 0.5 ms to draw, against 1.5 ms for the slowest 34-row strip with the text wrapped for each strip. The first report from a player, on the build that redrew the counters every second (Missed 158,091, repeated 12,266, with cracks and a changed sound), fits 11 wraps plus about 400 real misses in about 23 s of playing, so about 17 packets lost a second, with the repeats making up for them; that reading is an inference from the counters. None of this is measured on the player yet.
  - **Ending:** pulling the cable, or holding Back for 1 s (the player then stays a charger until the next plug-in). The session powers USB down and `app_wake` restarts the screen timeout. Nothing touches the card, so there's no rescan or update check. Diagnostics → Last USB isn't updated.
  - **Memory:** no new buffers: the music ring holds the stream. The port, the audio state and the sink take about 1 KB of the USB overlay's zeroed memory.
- **Plug-in prompt** (Settings → Ask when connected, `OPTION_USB_PROMPT`, On by default, passed to the board through `hal_system_set_usb_prompt` when it changes and at start): the board still listens in the saved USB mode when VBUS appears, because only a host's bus reset tells a computer from a charger, and a charger must never ask. When the reset arrives with the prompt on, `board/main.c` powers USB down (the class can't change once the host has enumerated; the host sees a short attach and then a new device, as with a replug), shows a choice of Storage, DAC and Charge only with the saved mode selected (`app_choice_show`, `app_choice_step`, `app_choice_close`: a `ChoiceScreen` the board loop steps instead of `app_step`, which keeps the audio and Bluetooth served, lights the screen and renders each pass), and after the answer, or 5 s without one, listens again in the chosen mode and waits up to 3 s for the host's reset as before; Back and the timeout keep the saved mode, and Charge only doesn't connect (the player keeps playing and charging). Pulling the cable closes the prompt.
- **Firmware tag:** `hal_system_version` (`hal/system.h`) reads the build tag from slot 1's header on the device and returns "simulator" in the simulator. Diagnostics shows it as Firmware.
- **CPU clock:** `hal_system_clock_mhz` and `hal_system_set_clock_mhz` (`hal/system.h`). On the device, `board/clock_switch.c` follows stock's PLL order with the register words from `device/pll` (96 and 200 MHz). It waits up to 200 ms for lock and stays at 24 MHz without it. After a switch it rescales the SysTick clock (`tick_clock_set_rate`). The device switches to 96 MHz right after reading the boot clocks (see Device playback). Diagnostics → CPU clock switches between 24 and 96 MHz, and Diagnostics → Stopwatch counts seconds to check the rate against a phone. CPU clock cycles 24 → 96 → 200 → 24 MHz.
- **Test tone:** `hal_audio_test_tone` (`hal/audio.h`) blocks for about 5 s. On the device, `board/dac.c` runs the SoC side of the audio path (gates, I2C0 through `board/i2c.c`, ACODEC mux, I2S1, polled FIFO feed) and `device/dac_sequence` runs the CS43131 side (power pins, probe, register sequence, output on and off) through a `DacBus`. It plays one sine period of 100 samples (441 Hz at a true 44.1 kHz) at amplitude 9000 (ReChord's level, about −11 dBFS): 2 s with the I2S divider from the formula (MCLK / (64 × rate) − 1, truncated, which gives 2), then 2 s with it rounded (3). It reports No DAC, Setup failed, Not ready or I2S stalled when a step fails; No DAC adds the I2C step (s1 start, s2 send, s3 NAK, s4 stop, s5 receive) and the I2C pending bits in hex. Diagnostics → Boot clocks shows the low halves of CRU `+0x10`, `+0x14` and `+0x18` as the ROM left them, read first thing in `board_main`. The simulator returns Played.
- **Jack pins:** `hal_audio_jack_pins` (`board/jack.c`) records how the ROM left GPIO0.13 and GPIO2.8 (function, direction, pull), then makes both GPIO inputs and reads them. Diagnostics → Jack 3.5 and Jack 4.4 show the live level and the boot state (GPIO0.13 high = 3.5 mm, GPIO2.8 low = 4.4 mm; the 3.5 mm pin is confirmed on hardware). `hal_audio_jack` gives the debounced jack: `device/jack_sense` names it (GPIO2.8 low wins) and takes a change after 7 matching readings, one every 10 ms from `hal_audio_service`. With Output set to Auto, the volume curve follows the jack (4.4 mm: `7D` − ⌊12n/5⌋, stock's table B; 3.5 mm: `7A` − ⌊12n/5⌋); a fixed Output setting overrides it. Both jacks are driven by the same two CS43131s (one per channel), and no switch between them is known, so Output can't route sound to one jack: it only chooses the volume table, 1.5 dB apart at the top. Settings shows the detected jack next to Auto ("Auto (4.4 mm)"), and choosing an option says what it does. The player pauses when the jack goes from plugged to none and doesn't resume on its own.
- **Clock:** `hal_time_read` (`hal/time.h`) reads the real-time clock chip and fills a `HalTime`: `present` (the chip answered), `valid` (present, not flagged as having lost power, not stopped, and every field in range: a real calendar date, hours 0–23, minutes and seconds 0–59, weekday 0–6), the chip's `low_voltage`, `stopped` and `century` bits, and the local civil year, month, day, hour, minute, second and weekday (0 = Sunday). The year is 2000 plus the chip's two-digit year; the century bit is only reported. `hal_time_write` sets the chip from a `HalTime`: `A2 00 00` (control 1 cleared, so STOP is clear), then `A2 02` and the seven time registers from `pcf8563_encode` (BCD, VL clear, the century bit clear, the two-digit year); it returns false when either send isn't acknowledged. The simulator keeps the written time as a shift from the host's clock, and the fake HAL as the time it then reads back. On the device, `board/rtc.c` reads registers `0x00`–`0x08` of a PCF8563-type chip at I2C address `0xA2` on I2C1 (`0x40050000`), pin group C (`docs/hardware.md`): each read gates the controller (CRU gate `0x84`), resets it (`0x1B`), selects GPIO2.12/2.13 function 3 and GRF `+0xBC` bits 3:2 = 2 (`0x000C0008`), sets 100 kHz from `board_pclk_hz`, sends `A2 00` and receives 9 bytes from `A3`; every bus stage times out after 2 ms, so an absent chip costs about 10 ms and `present` is false. `board/i2c.c` holds the Rockchip I2C transaction code that `board/dac.c` used for I2C0 (start, send, stop, receive, the first failed stage and the pending bits), with the controller base and timeout in an `I2cPort`, so the DAC path runs unchanged with a 10 ms timeout and the clock with 2 ms. `device/pcf8563` (host-tested) decodes the registers: BCD digits, the VL bit in seconds, STOP in control 1, the century bit in months, the unused bits masked, and the validity rule above. Diagnostics → Clock (release and developer menus) reads the chip the first time the row is drawn and again each time it's pressed, so a second press 5 s later shows the seconds advance; it shows `YYYY-MM-DD HH:MM:SS`, then ` VL` (the chip lost power since it was last set), ` STOP` (the clock is halted), ` C` (century bit set) and ` ?` when a field is out of range, or "No reply" when nothing answered. The simulator returns the host's local time; `--clock-unset` sets VL, `--no-clock` answers nothing, and `--clock-date YYYY-MM-DD` starts it on that date at the host's time of day (as a stale chip would). `tests/app/fake_hal.c` returns whatever `fake_hal_set_time` set (nothing by default). The chip, bus and pins come from other firmware for this player and haven't been confirmed on EchoPod yet.
- **Power:** `hal_system_power_info` (`hal/system.h`) reports the core 0 clock in MHz, the share of the last 2 s core 0 spent in WFI (`device/sleep_meter`, host-tested: the main loop times each WFI with `hal_clock_microseconds` and the meter publishes the share once per 2 s window), core 1's busy share (`StreamControl.load_percent`, the same figure as `c` on the frame overlay; 0 while core 1 is off), whether the panel, the DAC path, the headphone amplifier pin and core 1 are powered, and the output underruns counted since start-up. Diagnostics → Power (release and developer menus) shows it as `200 MHz s37% c45% PDaC u0`: `s` is the WFI share, `c` core 1's load, then one letter each for panel, DAC path, amplifier and core 1, upper case when powered, and `u` the underrun count. `hal_system_set_power_savings` takes a bit mask of the savings (`HAL_SAVING_*`); all but the amplifier one are on at start-up and the choice isn't saved. Diagnostics → Savings shows the current preset and each press moves to the next: All, No core 1 sleep, No 96 MHz, No pause stop, No panel sleep, None, All + amp off. The amplifier saving (only in the All + amp off preset) holds the headphone amplifier pin (GPIO1.4, `DAC_PIN_AMP`) low while audio is routed to Bluetooth and drives it as the DAC sequence wants again when routing ends or the saving is turned off (`dac_path_follow_route`). It is off by default because nothing shows the Bluetooth module's input doesn't pass through that stage: the register dumps in `docs/hardware.md` show stock keeps the pin as EchoPod does while streaming. The simulator and the fake HAL keep the mask and report only the clock.
- **Device playback:** `board/audio.c` implements the audio HAL with `device/audio_engine` (host-tested). The engine opens a track through the file HAL and takes decoded frames from an `AudioSource`. `board/audio.c` picks the source from the file's first 12 bytes, not its name: `fLaC` goes to FLAC, `RIFF`…`WAVE` to `device/wav_source` (PCM or extensible PCM, 1–2 channels, 8/16/24/32-bit, any chunk order before `data`, 4,096-frame blocks read on core 0 into buffers that share memory with core 0's FLAC decoder), an ID3 tag or an MPEG audio frame header to MP3, `ftyp` at byte 4 to MP4 (ALAC, or AAC with object type 2, AAC-LC; anything else is refused as an unsupported file type), `OggS` to Ogg (Opus only, channel mapping family 0), anything else is refused as an unsupported file type. For MP4, core 0 runs `codec/mp4`: it reads the first sound track's `stsd` (the ALAC cookie or the AAC `esds` config), `stts`, `stsc`, `stsz`, `stco`/`co64` and the first non-empty `elst` edit (the lead trim), and streams into the core 1 ring not the file's bytes but a record stream: a 4-byte little-endian length and the codec config, then each frame as length and bytes, starting at the frame that holds the seek target. The sample tables are read through three 96-byte caches, and opening walks `stsz` once to size the stream. The FLAC core 1 program also decodes ALAC: `StreamControl.codec` picks the decoder per track, the ALAC decoder sits in the FLAC decoder's second bank (below), and the FLAC path sets the accelerator hook again before each FLAC track. `device/core1_alac` waits until a whole record is in the ring before decoding it. AAC runs on its own core 1 program (`core1/aac_main.c`, about 58 KB, at image offset `0x2A0200`, between the FLAC slot and the glyph table) with FAAD2 2.11.4 (`third_party/faad2`, pinned in `VERSION`, built with `FIXED_POINT`, `LC_ONLY_DECODER` and `DISABLE_SBR`; its ARM multiply macros need GNU C). FAAD2's decode path needs about 46 KB of stack (the channel-pair element alone is 24 KB), so `core1/core1_aac.ld` keeps `.bss` below `0x01022000` and the whole of core 1's data RAM is stack; FAAD2's few non-const tables are linked into the code area. Its `malloc` is a bump allocator over the unused tails of the four output-slot rows (each row holds 4,608 samples, an AAC frame 1,024), about 31 KB of the 57 KB there for stereo, reset at each track; `device/core1_aac` refuses a frame of more than 1,024 samples so output never reaches it. FAAD2 outputs interleaved 24-bit samples, so `Core1Block` has a stride. FAAD2 outputs nothing for the first frame it decodes, so core 0 starts an AAC stream one frame before the one that holds the seek target, and core 1 numbers frame k as starting at k × 1,024. Opus streams the file's own bytes, as MP3 does: core 0 runs `codec/ogg` to read `OpusHead` (channels, pre-skip), find the first audio page after `OpusTags`, and take the length from the last page's granule, found by scanning back from the end in 512-byte reads; a seek bisects the file by page granule and starts on the page after the last one that ends at least 80 ms plus one longest packet (120 ms) before the target. `Core1Source.play_from` then drops what core 1 decodes before the target, so the pre-roll isn't heard and the position is exact. The Opus core 1 program (`core1/opus_main.c`, about 81 KB, at image offset `0x218000`, between the overlay and the MP3 slot) runs libopus 1.6.1 (`third_party/opus`, pinned in `VERSION`, built with `FIXED_POINT`, `DISABLE_FLOAT_API` and `USE_ALLOCA`) behind `codec/ogg`'s packet reader, which follows the first serial it sees, rebuilds packets that span pages and works out each packet's first sample from the page granules and the packets' TOC bytes (looking ahead past pages where no packet ends). An Opus stream uses only the first 96 KB of the input ring (`StreamControl.ring_bytes`, which core 0 sets for every stream and core 1 adopts with it), and the 27 KB decoder state sits in the top 32 KB (`CORE1_OPUS_STATE`); the 4 KB packet buffer and the 60 ms output buffer sit in the unused end of core 1's code RAM, addressed through `0x01000000` (`.core1_big`, not loaded), so data RAM is left to the stack. FAAD2 and libopus are built with `-O2` on the device, and core 1 runs the AAC and Opus programs at the full 200 MHz (divider 1, which also selects the fast bus setting) instead of the 100 MHz the other programs use; the ALAC decoder reads its Golomb codes 32 bits at a time and has unrolled predictors for orders 1 to 8, which took it from 3.6 times libmad's cost to below it. Every core 1 program times its decoding with SysTick and publishes the busy share every 50 million ticks (`StreamControl.load_percent`), shown as `c` on the frame overlay. While streaming, core 1's SysTick interrupts every 100,000 ticks (0.5 ms at 200 MHz, 1 ms at 100 MHz) and its handler (`core1/startup.c`) counts the periods, so `core1_ticks` is a 32-bit count; when `core1_stream_step` finds nothing to do (no free output slot, too little input, or no stream) and `StreamControl.sleep_allowed` is set, `core1_stream_serve` waits with WFE. Core 0 runs DSB + SEV after every change core 1 may be waiting for (a slot freed or dropped, input written, a stream opened or stopped: `Core1Source.wake`), so core 1 wakes at once if this SoC routes core 0's events to core 1, and otherwise at its next SysTick. `test_core1_stream` plays FLAC, MP3 and ALAC with a core 1 that only wakes on those events and checks the output is still exact. Core 0 sets `sleep_allowed` from the core 1 sleep saving when core 1 starts and whenever the savings change. Whether SEV reaches core 1 is unknown; either way the wake comes within one SysTick period, far inside the ring's 73 ms at 192 kHz. libopus outputs interleaved 16-bit samples, so `Core1Block` also carries 16-bit channels. MP3 is decoded on core 1 by libmad (`third_party/libmad`, 0.16.4 pinned in `VERSION`, built with 64-bit fixed point and `OPT_ACCURACY`; on the device `third_party/libmad_libc` stands in for the missing C headers and `core1/no_heap.c` makes `malloc` always fail, since `device/mp3_decoder` hands libmad static main-data and overlap buffers before its first frame). Core 0 runs `device/mp3_probe` (ID3v2/ID3v1/APE tags skipped, the first frame confirmed by the next one, length from Xing/Info or VBRI, else from size and bitrate; seeking through the Xing table or proportionally) and streams the file into the same core 1 ring; `device/core1_mp3` turns each frame into a block of 24-bit samples. Core 1 runs one program at a time, as stock does: both programs are packed by `tools/make_image.py`, MP3 (about 73 KB) at image offset `0x240000` and FLAC (about 20 KB) at `0x280000` (a 512-byte header with `EC1M`, size and CRC, then the program) and read from slot 1 on eMMC straight into core 1's RAM through a 4 KB staging buffer, with the CRC checked on the way. Switching between a FLAC and an MP3 track restarts core 1 with the other program; after an update, until the restart, both programs are refused like the rescan overlay (FLAC then decodes on core 0). On core 1 the FLAC decoder can hand LPC subframes of order 3 and up to the hardware accelerator (`device/flac_accel`) through `flac_set_lpc_hook`, but only for the classes (narrow or wide accumulator) that passed its self-test; a timeout turns the hook off. Core 0 runs the self-test once per boot, before the first FLAC stream, and passes the passing classes to every later core 1 FLAC run. The self-test runs twice, over the second bank in data RAM and over the first bank in code RAM (`CORE1_ACCEL_CODE_NARROW`/`_WIDE`), and the hook sends a buffer below `0x01020000` to the accelerator only for the classes that passed there, since whether its DMA reaches code RAM hasn't been seen on hardware; Diagnostics shows the data RAM result. libmad's `III_decode` keeps a 7 KB frame on the stack, so `core1/core1_mp3.ld` keeps the program's `.bss` below `0x0102B000`, leaving 12 KB of stack. The engine records why it refused a track (unreadable, or the sample rate with the rate), `hal_audio_refusal` reports it, the player counts refusals, and the app shows a toast such as "192 kHz isn't supported yet". On the device that is `device/core1_stream`: core 0 opens and seeks with its own decoder, streams the file into a 128 KB ring in core 1 RAM, and core 1 decodes frames into two slots; if core 1 doesn't start, `device/flac_source` decodes on core 0, with a 4,608-sample buffer (`FlacBlockBuffer`), so a file whose STREAMINFO allows larger blocks is then refused. Each frame is copied into a 28,000-word ring in data RAM as two words, left then right, each a 24-bit sample shifted to the top of its word (stock's music mode, TXCR `0x401F`; 16-bit sources are shifted up, nothing is rounded). Volume is set in the DAC's PCM volume registers; the engine's software gain stays at unity on the device. The engine keeps a list of segments (token, start frame, start position, rate) so the token and position follow what the DMA has played. DMA channel 5 loops over the ring through seven linked items of 4,000 words (a DW block holds at most 4,088 items; `device/dma_loop` refuses more); the HAL turns its read address into a running count of consumed frames. The app calls `hal_audio_service()` at the start of each step and after each strip, so drawing can't starve the ring (14,000 frames is 73 ms at 192 kHz, 146 ms at 96 kHz and 317 ms at 44.1 kHz). Every start (play, seek, a resume after the pause-stop, a rate change) leads with silence: `audio_engine_lead_in` writes 20 ms of zero frames (60 ms when the DAC path was just powered up or restarted at a new rate) ahead of the track and moves the segment's start past them, so the position only counts from the first real sample. Playback starts once that silence plus 100 ms of audio is buffered (at most three quarters of the ring) or after 1 s. The DAC path powers up with the mute pin (GPIO2.0) still high and the PCM volume muted; once the DMA has played 6 ms of the silence (40 ms after a power-up) the mute pin is released and the PCM volume set straight to its level while silence is still playing, so the music starts at full level instead of fading up from mute (which used to leave the first ~100 ms nearly inaudible). The engine ramps the first samples up instead (`ramp_chunk`, linear): 2 ms when the track starts from its beginning, 10 ms when it starts part-way (a seek, a resume position). A pause, resume or stop while the DMA is still inside that silence (with 4 ms to spare) mutes or unmutes at once instead of fading. Supported rates are 44.1, 48, 88.2, 96, 176.4 and 192 kHz, each with its ACODEC row and the rounded I2S divider. A queued track at the same rate follows without a gap; a different rate waits for the ring to drain (the engine writes silence after the last track's end meanwhile, so the DMA never loops over old audio), then the path restarts at the new rate. Volume changes fade on the DAC: 6 PCM-volume units (3 dB) every 2 ms (`dac_ramp_next`), jumping between −96 dB (register `0xC0`) and mute instead of stepping through the inaudible end, and `board/dac.c` keeps the ring fed between steps through a service hook, so a fade never starves the ring. Stopping, pausing, seeking and skipping fade down to mute before the channel stops; a resume from pause fades up. A seek while paused stays silent. Pause fades out, mutes the DAC and suspends the channel (nesting with the clock switch's suspend). After 30 s paused (`PAUSE_REST_MS`, the pause-stop saving), `board/audio.c` closes the source (`audio_engine_close_source`: the engine stays paused with its token and position), powers the DAC path down and stops core 1, so the output reads as idle and the clock can drop as it does when stopped; resume then seeks to the saved position, which starts core 1 and the path again and fades in, so it takes about as long as a seek. A seek queues again a next track the engine had already opened (or was waiting to change rate for), so the track after still follows. Seek and play restart the ring. Three seconds after playback stops, the DAC path powers down. `hal_audio_service` polls the I2S underrun flag (INTSR bit 1, cleared through INTCR bit 2; INTCR keeps TXUIE set with the NVIC line off) and counts it in the stats, shown as `o` on the frame overlay. Diagnostics → Tone 192k plays the DMA tone at 192 kHz. The ring must stay in data RAM (`0x03004000`–`0x0304C000`): High RAM (`0x0307A000`) shares its SRAM with the code at `0x03050000`, and with the screen on core 0's instruction fetches starve the DMA's ring reads at 192 kHz (I2S underruns, an audible crackle). Core 0's FLAC header and seek decoder, which shares its memory with the WAV buffers, sits in High RAM instead (`.high_ram`, no-load): only the CPU touches it, and the two overlays and the High RAM diagnostic stop audio before they overwrite it. The device starts at 96 MHz (`START_CLOCK_MHZ`) right after reading the boot clocks.
- **FLAC blocks:** FLAC's subset allows blocks of up to 16,384 samples above 48 kHz, and ffmpeg writes 8,192 at 88.2/96 kHz and 16,384 at 176.4/192 kHz. A 16,384-sample stereo block needs 128 KB as 32-bit samples, more than either RAM region of core 1 has in one piece, so the FLAC program lays core 1's RAM out its own way: its code, `.bss` and stack (`core1.ld`, stack top `0x01010000`, at least 8 KB of stack) stay below `0x01010000`, the first bank (64 KB, `CORE1_FLAC_BANK_0`) fills the rest of code RAM up to the shared block, the second bank (64 KB, `CORE1_FLAC_BANK_1`) takes data RAM from `0x01021000`, and its two output slots sit above that at `0x01031000`, 3,840 samples per channel (`CORE1_FLAC_SLOT_SAMPLES`), ending at the input ring, which keeps its 128 KB so a whole frame (up to 98 KB for 24-bit stereo stored verbatim) always fits. A stream whose STREAMINFO says its blocks are at most 8,192 samples puts both channels in the second bank, as the decoder buffer was before; anything else uses one bank per channel (`core1_flac_decoder`'s `Core1FlacBanks`). The decoder writes each block in its bank, and `core1_stream` hands it to core 0 in pieces of at most one slot (`Core1Stream.pending` and `emitted`): each piece is copied into the next free slot, widened and equalized there, and numbered from the block's first sample plus what went before, and the input bytes of the block are released as soon as it is decoded. The next frame is decoded once the last piece is in a slot, so up to two slots and core 0's ring keep playing while it decodes. Every program publishes its slot layout when it adopts a stream (`StreamControl.slot_offset` in words from `CORE1_STREAM_SAMPLES`, and `slot_samples`); the MP3, AAC and Opus programs keep the old one (offset 0, 4,608 samples, which the AAC heap's slot tails rely on), and core 0 reads each slot through the published layout, refusing one that doesn't fit the 72 KB slot area. The ALAC decoder (41 KB with its 4,608-sample frame buffer) lives in the second bank, which FLAC doesn't use while ALAC plays. The unused bench command that decoded a file copied to `0x0102E000` is gone, since the banks cover that memory. `test_flac` decodes and seeks 16,384-sample files made by `tests/codec/flac_writer.c` (a small encoder: fixed order-2 subframes, left/side stereo, Rice partitions), and `test_core1_stream` plays them, 8,192-sample files and ALAC through the FLAC program's slots, checks the piece sizes, the bank choice, a start part way, sleeping, and the equalizer across pieces bit for bit.
- **DMA tone:** `hal_audio_dma_tone_start`, `_stop` and `_status`. On the device it checks COMP_TYPE at `0x600003F8`, brings up the same audio path with the rounded divider and INTCR `0x01F00100` and without XFER, then runs DMA channel 5 (`board/dmac.c`) over the music ring filled with a sine (16-bit samples in the top half of each word, two words per frame, the same format as music) through the same seven linked items as music (`device/dma_loop`), with every channel interrupt masked. Then DMACR = `0x110` and XFER = 1. The call returns at once, and Diagnostics → DMA tone shows "Playing" with channel 5's read position, "Ended" if the channel stopped by itself, or the failed step. Pressing it again suspends the channel, disables it, and closes the audio path. A clock switch suspends and resumes the channel around it.
- **Last start:** `hal_system_start_info` (`hal/system.h`). On the device, `device/start_record` keeps a record in `.noinit` RAM: the start count, the uptime (every 5 ms), a power-off mark, fault registers (or, after a stall, the stalled PC and LR, the exception frame's address, the three stack words above the frame and the stack's high-water mark), the last battery reading (every second), the last risky step (backlight on or off, clock switch, core 1 start or stop, card write) with its start time and whether it finished, and the last update's outcome (see USB). Diagnostics → Last start, Last step, Last battery and Last stack show what the previous run left, for example "#3 reset after 41 s", "Fault at 0305ABCD", "Stall 03051994 03053FC3", "In clock switch at 41 s", "3712 mV" and "03003D80 03051995 0307A010" (SP, then the two words above the frame). "#3 after power-off" means the record survived a power-off: the power never went away (a cable, or the hold pin didn't cut it).
- **Stall and fault screen:** a power loss wipes the Last start record, so a freeze that ends in a power cut reads Cold start. On the device the main loop beats a `device/stall_watch` each pass, and the 1 ms SysTick checks it every 5 ms. A loop silent for 10 s (paused during start-up, USB sessions, updates and power-off) trips it once: `board_stall_report` saves the interrupted PC and LR, the frame address, the three stack words above the frame and the stack high-water mark in the start record, then the interrupt silences the audio pins, clears the panel, turns the backlight full on and draws, in a 5×7 font scaled ×2 (`device/panic_text`), "STALL", "PC <pc> LR <lr>", "CFSR <cfsr> SP <sp>", two lines of three stack words above the exception frame, and "UP <s> STEP <n> [U] MV <mV>" (U = the step never finished; step numbers follow `HalStartStep`). PC, LR and SP come from SysTick's exception frame via `device_systick_entry`, SP being the frame's address, so the stack words are what the stalled code had pushed. A fault draws "FAULT" with the same lines (`board_panic_show`), and saves CFSR, HFSR and the PC. After either, holding Power for 2 s cuts power from the interrupt, which on battery also wipes the start record; on a USB cable GPIO2.6 low doesn't cut power, so the record survives into the next start if RAM stays powered. Pressing RST instead keeps RAM, so Diagnostics → Last start and Last stack then show the stall. The first stall report from the field (0.10.0, after a Mac echo-sync, "PC 03051994 LR 03053FC3 UP 69 STEP 6"): the LR is the return address of `bl image_crc_update` in `hal_system_load_rescan_code`, so the overlay had just been read and CRC'd; the PC is inside `run_accel_test` (`board/core1.c`), 0xA4 bytes in, right after a struct copy that uses LR as a scratch register, so the two can't be one live frame. `image_crc_update` returns with `pop {r4-r7, pc}`, and the pair fits a return through a stack slot that held `0x03051995` instead of the saved LR; what wrote it isn't known (the static stack depth is far below 16 KB, the overlay region holds nothing live, core 1 is held in reset while its RAM is borrowed, and the stack region has no DMA writer). The 0.11 overlay check against the running code closes the one way a wrong overlay could have run. A second report (0.10.x, "PC 030513A8 LR 00000000 UP 165 STEP 6") is one live frame, unlike the first: in both the 0.10.0 and 0.10.1 release builds that PC is the `pop {r4, pc}` that ends `hal_clock_milliseconds`, the first instruction after it unmasks interrupts, which is where a SysTick that came due while the clock was being read gets taken, and LR 0 is what `tick_clock_milliseconds` leaves in LR, which it uses as a scratch register for a quotient that is almost always 0. So the main loop had spent 10 s in a loop that polls the clock (a card or internal storage wait, a delay, a USB or audio wait); which one isn't known, since 0.10.x showed no stack words. In 0.11 the second word above the frame (the second stack word on the stall screen, and the last value of Last stack) is then the return address into the function that called it. The SD card's waits that could run for minutes (1,000 CMD13s or 100 ACMD41 tries, each command waiting up to 1 s for a busy card) now also stop after 2 s. There is no Diagnostics row to freeze the loop on purpose any more (`hal_system_stall_test` is kept but unused). A loop stuck with interrupts masked isn't caught.
- **Power taps:** Diagnostics → Power taps (Normal/Ignored, not saved) makes the app drop Power taps so a test can tell an electrical effect of the press from the app's reaction to it; a long Power press still shuts down.
- **Switching on:** Settings → Power on (`OPTION_POWER_ON`, Press by default) can ask for a held Power key (issue #5, a tap in a bag shouldn't start the player). `app_start` calls `hal_power_confirm_start` right after loading the settings; on the device (`board/power.c`) it does nothing unless Hold is chosen, the start is cold (`hal_system_start_info().warm` false: a restart, RST or watchdog reset keeps the start record and always starts) and there is no USB power, either at boot or now (with USB power GPIO2.6 low doesn't cut power, and plugging in always starts). Otherwise it waits until the firmware has been running 1 s (`START_HOLD_MS`, counted from the SysTick clock's start, so the boot ROM's own time comes on top and isn't known) and, if Power was released before then (or wasn't down when `board_power_hold` read it), turns the backlight off and drops GPIO2.6. If the power is still there 1 s later, it raises GPIO2.6 again and carries on starting, so a hold pin that doesn't cut can't leave the player dark. `board/input.c` ignores a Power key that has been down since boot until it is first released, so the hold that started the player is never read as a press or a 2 s switch-off.
- **Switching off:** `hal_power_off` and `board_power_cut` drive the Bluetooth module's power and UART pins low before dropping GPIO2.6; a powered module otherwise kept the player from switching off after an update, so Power did nothing until RST.
- **Charge screen:** with USB power, GPIO2.6 low doesn't cut power (`hardware.md`), so a switch-off on a cable used to leave the player dark and deaf until RST. Now the app's shut-down checks `hal_power_battery().usb_power` and, when it's set, enters charge mode instead of `hal_power_off`: it pauses and releases the output, puts Bluetooth to sleep and draws `screens/charge_screen` (a large battery, the bolt while charging, "Charging 64%" or "Charged", "Hold Power to turn on"). The screen goes dark after 5 s and any key lights it; holding Power for 2 s leaves charge mode (Bluetooth restarts, the splash plays); losing USB power calls `hal_power_off`, which now cuts power. A USB session still runs as usual and returns to the charge screen. `board_power_hold` records VBUS and the Power key level at boot (shown in Diagnostics → Boot hold as "· USB" and "· key"); `hal_power_take_usb_start` reports, once, a start with VBUS present, the key up and GPIO2.6 not left driven high by the ROM, and the app then opens charge mode straight after `app_start`. The backlight stays off from boot until the app's first frame, so the panel's power-on noise never shows, and `board_display_service` also runs inside the USB, DAC, update and wait-for-key loops, and in `hal_system_keep_alive` (called for every folder and entry of a card walk or rescan), so a backlight fade-in started there finishes: in 0.11.0 rc1 the notice before the first start's music check stayed at the fade's 1 % until the walk ended, which looked like a black screen.
- **High RAM:** Diagnostics → High RAM writes and reads back a pattern over `0x0307A000–0x0309EFFF` (HIGHRAM0, 148 KB, where the rescan overlay runs and the glyph cache lives) and calls a 4-instruction function copied there. Afterwards it restarts the glyph pack reader and reloads the resident tables, since the test overwrote both. It shows "OK 148 KB, call works", "Bad at <address>" or "Call gave <value>".
- **Bluetooth:** `hal/bluetooth.h` powers the module, scans, connects to a device, turns the stream on and off and reports the module's state, the devices found, link counters and counts of the headphones' button presses. On the device, `board/bluetooth.c` follows stock's sequence: GPIO2.7, 2.16 and 2.17 are driven low at boot; power-on opens UART1 (group A, 115,200 8N1, divisor 13, FIFOs on, no UART interrupt) and drives GPIO2.7 high; power-off drives all three low again, as does a module that never sends `CV1`. While the module is powered, `board_bluetooth_tick`, called from the 1 ms SysTick handler (`board/clock.c`), drains the RX FIFO into a 256-byte ring (up to 64 bytes a tick), counts line-status overruns and ring overflows and records the FIFO's peak level; at 115,200 baud a byte arrives every 87 µs, so a FIFO drained every millisecond can't overrun however long the main loop blocks (core 1 start and stop, the playback prefill, cover decoding, settings writes and clock switches all block it for tens to hundreds of milliseconds, and before 2026-11-05 the FIFO was only read from the main loop, so it overran in a few milliseconds and a garbled `CQ` answer dropped the link: the "works on and off" reports). `hal_bluetooth_service` runs where `hal_audio_service` does (each step and after each strip): it feeds the ring into `device/bt_module`, copies the overrun count and peak level into the status (the depth is read at power-on), and sends any frame the protocol asks for. Diagnostics → Bluetooth's overrun count should now stay at 0; a FIFO peak near the depth means the SysTick handler was held off that long. `bt_module` connects with `CL06` + the address, `CH06` after 4 s and `CT00` and a failure after 30 s, polling `CQ00` every second meanwhile so a link the module reports only as `CQO` (a remembered device sends no `CLOK`, and headphones may connect on their own) shows within a second; a paired reply (`CLOK`) waits for the next `CQ00` answer to report the link (`CQO`). It sends `CY0 00` on connect, `CY0 1E`/`CY0 00` to start and stop the stream, and stock's `C 86`/`C 87` play notices. The module's `CP`/`CC` (pause/play, sent by the headphones' taps and in-ear sensors) and `CA`/`CB` (previous/next) only count presses in `HalBluetoothRemote`; polling pauses for 50 s after a `CP`/`CC`, as stock does. While streaming, the board routes audio to the module: the first time it applies the stock start-up settings listed in `hardware.md`, then GPIO2.0 goes high and GPIO2.14 low (and back 1 s after the stream stops, so the switch doesn't land while the module may still be sending; the 1 s is a guess), and the DAC driver keeps those two pins while routed. While routed, `board/audio.c`'s `output_curve` picks the DAC volume table from Settings → Bluetooth level (`OPTION_BLUETOOTH_LEVEL`, applied through `hal_audio_set_bluetooth_level` with the other hardware settings): Standard is `DAC_CURVE_BLUETOOTH`, top `87` − ⌊12n/5⌋ with no raised floor, the curve since 0.9.1, which sits 13 register units (6.5 dB at the CS43131's 0.5 dB steps) below the 3.5 mm table and is the "too quiet over Bluetooth" of issue #28; Louder is `DAC_CURVE_BLUETOOTH_LOUD`, the 3.5 mm top `7A` − ⌊12n/5⌋ (no raised floor either). The module takes the DAC's analogue output, so Louder sends it the same level a wired 3.5 mm headphone would get at that volume; whether its input clips at the top steps is not known and has to be listened for on hardware. `STREAM_ON_LEVEL` = `1E`, the byte after `CY0` in the stream-on command, may be a module-side volume (stock sends `1E`); nothing else has been tried, so changing it is a hardware experiment for later, not part of this setting. `app/bluetooth_link` runs every step after `player_update`. It keeps the On/Off choice and up to 6 devices, most recently connected first (stock also keeps 6), in `/.echo/bluetooth.bin` (`BT`, version 2, the On byte, the count, then 6 × the 6-byte address and 32-byte name; version 1 files, with one device, still load), written only when they change. When Bluetooth is on it powers the module at start and connects to the first device as soon as the module is ready, retrying 5 s after each failed attempt. It connects only from Ready or from a scan that found a remembered device: never while a connect is running or while a paired reply waits for `CQO`. A pairing that hasn't reported the link 10 s after `CLOK` is dropped with `CT00` and tried again 2 s later, which brings up a link the module left half-made. With the Bluetooth screen open, each failed attempt is followed by one scan to list nearby devices. Stock only ever scans a freshly powered module (its rescan power-cycles it first), so a scan after the module has paged a device power-cycles it too: off for 500 ms, on, wait for `CV1`, then `CS00`; the first scan after a power-on goes straight out, and the screen says Searching… throughout. A scan that finds a remembered device connects to it at once with `CL06` while the scan still runs, as stock's screen does when an entry is picked (one try per scan), unless the user disconnected or chose Pair new device; then its row shows "Nearby". Each new connection moves its device to the front of the list and shows "Connected to <name>"; a dropped link pauses playback and shows "Disconnected from <name>". A device the user disconnects stays disconnected (no automatic reconnect) until it or another device is chosen, Bluetooth is turned off and on, or the player restarts. Choosing another device while one is connected disconnects it and connects the chosen one 2 s later; "Pair new device" disconnects too, then scans. It streams while connected, playing and nothing is in either jack. Each time the stream starts (a play, a resume, or a link that comes up while playing) it pauses the audio output with `hal_audio_pause` for `BLUETOOTH_LINK_OPEN_MS` (600 ms) and resumes it, so the opening isn't played while the headphones are still taking the stream; the hold ends early if the player pauses (the player's own pause then holds the output, and `hal_audio_pause`/`hal_audio_resume` ignore a repeat, so the DMA suspend count stays balanced) or the stream stops for wired headphones. The 600 ms is a guess at how long the Buds take after `CY0` `1E`; not measured. The jack can't be read while audio is routed to the module (the readings fake a plugged headphone), so `board/jack.c` holds its last state then and for 500 ms after each routing change: headphones plugged in while paused take the sound, and Bluetooth waits for the next pause and play before taking it again. The headphones' next and previous skip. Their pause pauses and their play resumes only what they paused, and both are ignored for 3 s after a connection, a stream change or a play or pause on the player, because the module sends the same `CP`/`CC` reports then on its own; a pause the headphones cause shows "Paused by <name>". With no connection and the Bluetooth screen closed, the module switches itself off after 5 minutes (Bluetooth stays on for the next start); opening the screen wakes it, and so does a play that starts (the player going from paused or idle to playing) with nothing in either jack while a device is remembered, so headphones that went out of range for a while reconnect on the next play instead of only from the Bluetooth screen; it dozes again after 5 more minutes without a link. Settings → Bluetooth (third, after Shuffle and Repeat) shows the link's state as its value: Off, Starting…, Searching…, Connecting…, the connected device's name, Not connected or On. It opens `screens/bluetooth_screen`: a Bluetooth On/Off row; the remembered devices, each with its state (Playing, Connected, Connecting… or nothing); a "Pair new device" row (Searching… while scanning); then, while not connected, the devices a scan found that aren't remembered; and a hint for the selected row at the bottom. ▶ toggles Bluetooth, disconnects the connected device or connects a remembered one, starts a search, or pairs with a found device (which shows Connecting… or Didn't connect); holding ▶ on a remembered device forgets it. Diagnostics → Bluetooth opens the same screen with four more lines: the module state (version, status letter, pairing result, streaming), the link counters and, over two lines, the module's last 12 messages: frames other than `CS` and repeated `CQ` answers, shown as `C` + two letters (a new `CQ` letter shows as `CQ` + it), plus the `CS`, `CP`, `CL`, `CH` and `CT` commands EchoPod sent, shown as `>S`, `>P`, `>L`, `>H`, `>T` (`CQ00` polls aren't listed); each is followed by `+n` when n seconds passed since the one before. The log and the devices found survive Bluetooth off and on, so one photo after a failed or slow attempt shows the whole exchange. The status bar shows a Bluetooth mark next to the play icon, dim while on and bright while connected. The simulator reports ready after 300 ms, finds two devices over 3 s, keeps them across a power cycle and connects 1.5 s after a pick.

## Simulator audio

- Windowed mode plays through SDL audio. dr_flac, dr_mp3 and dr_wav decode (vendored, pinned in `third_party/dr_libs/COMMIT`). Each track feeds an `SDL_AudioStream` that resamples to the 48 kHz device rate. Two decoder slots (current and queued) make the hand-over gapless.
- Headless mode uses a silent virtual backend that advances on the simulated clock, so scripted runs, track transitions and resume are deterministic.
- `SDL_AUDIODRIVER=dummy` runs the real-time path without sound.
- Third-party code lives in `third_party/` and compiles without our warning flags. The comment and format checks skip it.

## Simulator storage

`--card DIR` maps the card root `/` to a host folder, which is only ever read. Open files are read unbuffered, because `hal_file_write_at` writes through its own handle: on Windows a buffered reader kept serving the old bytes, so the scan's scratch file read back stale data and every rescan stopped with "Library too big for the player's memory". `hal_file_write` writes a `.tmp` file and renames it over the old one, removing the old one first on Windows, where `rename` won't replace a file. `--system-dir DIR` maps `/.echo/` to a separate folder, so the database, covers, resume file, settings and favorites can live in `build/` without touching your music folder. `--internal DIR` maps `/:internal` to a third folder that stands in for internal storage (listed last in `/`); it is only ever read. Writes are refused outside `--system-dir`:

```sh
.venv/bin/python tools/library_index.py --music ~/Music --output build/library/library.db
build/dev/platform/sim/echo_sim --card ~/Music --system-dir build/library
```

## Simulator power and display

- `hal_display_set_power(false)` blanks the window. Brightness dims the window (level 1 is about a quarter of full), but screenshots hold the undimmed panel.
- The battery is fixed: 80 % by default, or `--battery N` and `--charging`.
- Gain and output are stored but don't change the sound.
- `hal_power_off()` ends the run loop, and the simulator exits normally.

## Simulator automation

In headless mode the simulator uses a virtual clock (16 ms per frame), so runs are deterministic. `--keys` plays a comma-separated script (`up`, `down`, `play`, `menu`, `back`, `power`, each optionally `:long`) for driving screens in screenshot runs. For example:

```sh
build/dev/platform/sim/echo_sim --headless --frames 120 --keys down,down,down,play --screenshot shot.bmp
```
