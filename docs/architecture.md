# Architecture

EchoPod, replacement firmware for the Snowsky Echo Mini. The app layer is portable C. It runs in a desktop simulator (macOS and Windows) during development and on the device on top of a thin hardware layer.

## Layers

```
platform/sim        platform/device
        \                  /
         implement  hal  (interfaces only)
                     |
                    app          composition root: theme, screens, player, stores, main step
           /     /       \        \
         ui   fonts    settings   hal
           \   /           |
            gfx        playback
              \            |
               \        library
                \         |    \
                 \        |   image
                   \      |    /
                      core
```

| Layer | Path | May depend on | Purpose |
|---|---|---|---|
| core | `src/core` | nothing | Pure logic: deadlines, key gestures, frame stats, UTF-8, string building, formatting, hashing, seeded random, the power policy |
| gfx | `src/gfx` | core | RGB565 colors and blending, rectangles, clipped canvases, strip rendering, 4-bit anti-aliased text, images drawn into perspective quads |
| fonts | `src/fonts` | gfx | Generated glyph tables (see Generated code) |
| ui | `src/ui` | core, gfx | Screen interface and stack, navigation intents, list view, menus, choice screens, messages, toasts, header and status icons, labels, marquee, fades, Cover Flow layout and motion, theme type |
| image | `src/image` | core | Cover decoding for the rescan: a bump arena, a buffered reader, the 112 px area-average grid, inflate, PNG and JPEG (see Covers on the device) |
| library | `src/library` | core, image | Byte sources, a 4×512 B block cache, the library database reader, browse queries, the favorites set and the covers file reader (see `docs/library-format.md`) |
| codec | `src/codec` | core | FLAC decoding (up to 2 channels, 24 bits, 4,608-sample blocks) from a read callback, with header and frame CRC checks, and seeking by bisection on frame headers; ALAC decoding (up to 2 channels, 16/20/24 bits, frames up to 4,608 samples); and an MP4 reader that finds the sound track and turns its sample tables into a stream of length-prefixed records (see Device playback) |
| playback | `src/playback` | core, library | Play queue (list order, songs shuffle, album shuffle, repeat, gapless look-ahead) and the resume file format |
| settings | `src/settings` | core, playback | The settings values, their defaults and option tables, and the settings file format |
| dsp | `src/dsp` | nothing | The equalizer: fixed-point peaking filters, their design for a sample rate, and the automatic preamp (see Equalizer) |
| sound | `src/sound` | core, dsp | The equalizer presets, the Custom bands and the `equalizer.bin` format |
| hal | `src/hal` | core, dsp (types only) | Hardware interfaces: display (with power and brightness), input, clock, files, audio (with gain and output), power (battery, power off), system (firmware tag, CPU clock), Bluetooth (module power, scan, pair, disconnect, status) |
| app | `src/app` | core, gfx, fonts, ui, library, playback, settings, sound, hal | Default theme, screen tree, library, settings and favorites stores, cover cache, player controller, browse, Cover Flow, Settings and Now Playing screens, frame overlay, the main step |
| platform | `platform/*` | app, hal, codec, the OS or SDL | Implements hal and owns `main()` |

The CMake targets enforce these rules. Each module exposes only its own `include/<module>/` directory, and a module can only include headers from targets it links. Anything in a module's own directory, outside `include/`, is private.

## Screens and input

- A `Screen` is a title plus callbacks: `enter`, `handle_key`, `update` and `draw`. `handle_key` returns a `ScreenAction` (none, push, pop, or pop to root), and the app applies it to the `ScreenStack`. Screens never reach into the stack themselves.
- Raw key transitions come from `hal`. `core/key_tracker` turns them into gestures (press, long press, repeat), and `ui/navigation` maps gestures to intents (previous, next, select, back, home). Remapping buttons is a change in one place.
- Each key has a gesture type: tap-or-hold, repeat (press on down, then repeats), or tap-hold-repeat (tap on release, long press, then repeats). The volume keys repeat, except on screens that set `hold_volume_keys` (Now Playing), where they're tap-hold-repeat so a hold can skip tracks. The app switches the type whenever the top screen changes.
- Screen instances are static and owned by the app's `AppScreens`. There is no heap.
- A long Play is `NAVIGATION_OPTIONS`. Lists hand it to their `hold` action; in browse lists it toggles an album's favorite.
- Smart Play: in a browse list, ▶‖ on the track the player already has loaded (playing or paused) pushes Now Playing without restarting it. ≡ pushes Now Playing from any screen while the player has a track, and does nothing on Now Playing itself.
- Lists draw the selected row as a highlight line over a gradient, a › chevron on rows that open another screen (`ListModel.opens`), and a slim inset scrollbar thumb. Menu items can be hidden by a `shown` callback, and a menu can give the right of its content to a side panel (`MenuPanel`). Home uses that for `home_art`: the playing album's cover with a reflection, or library covers cycling every 5 s when nothing is loaded; Home lists Now Playing last and only while the player has a track.
- Settings is a menu whose rows show their current value. Every row opens the same `ChoiceScreen`, re-initialized from a table of `SettingChoice` entries (title, options, current, choose), and the current option gets a ✓.

## Power

- `core/power_policy` decides what keys mean for power. A tap of Power turns the screen off or on, and a long Power asks for shutdown. With the screen off (after a tap or a timeout), ▶‖ and vol± are background keys: the app maps them as on Now Playing (tap vol± for volume, hold vol± to skip, ▶‖ to pause) and runs them without waking the screen. ≡ and ↩ do nothing. While the screen is off, the volume keys use tap-hold-repeat on every screen, so a hold skips. The policy also owns the screen timeout and the sleep timer.
- The app runs each key event through the policy before the screen sees it. When the policy turns the display on or off, the app calls `hal_display_set_power` and stops rendering while the screen is off. Settings are saved each time the screen goes off.
- Shutdown (long Power, or the sleep timer running out) saves the resume file and settings, turns the screen off and calls `hal_power_off()`. The simulator then quits; the device cuts power.
- Battery level (`device/battery_gauge`): the battery is read once a second, and the percent comes from the average of the last 64 readings (about a minute) through RECHO's 11-point curve (3450 mV = 0 %, 4200 mV = 100 %; stock shows only 5 bars, full above 3830 mV), so short dips under load (a song starting, card reads, the backlight) don't show. While charging it reads 50 mV lower and never shows more than 99 %, since the charging current lifts the terminal voltage most near full (stock shows full on the cable only at 4250 mV or once the charger reports done). The average restarts from the latest reading when USB power comes or goes, so the charger's lift doesn't linger after unplugging. The low-battery check and Diagnostics → Battery use the last 8 readings. The shown percent follows the power source: on USB power it rises with any 2-point change but only falls by 10 points or more, on battery the other way round. Plugging in or unplugging therefore can't make the number jump; earlier builds used a 100 mV correction made it drop about 10 % on plugging in.
- Low battery (`core/low_battery`, stock's rule): every 250 ms the app reads the battery, and if it stays below 3450 mV for 2 s without USB power, it shuts down the same way with "Battery low" in place of "Goodbye".
- CPU clock (stock's rule: the clock follows the work, never the screen): 200 MHz while the screen is on or audio is up, 96 MHz (stock's floor) only with the screen off and `HalAudioStatus.idle` true (output and core 1 down, 3 s after playback stops). The device's audio HAL raises the clock to 200 MHz before it starts core 1, so a screen change never parks core 1. A USB session runs at 96 MHz at least.
- Waking draws the first frame before the backlight comes on (stock waits for 4 frames), and on the device the backlight then fades in over 200 ms (`device/backlight` ramp, from 1 % to the level's duty on the PWM, advanced by the main loop), so the backlight's switch-on current doesn't land at once on top of the drawing and the audio load.
- With the screen off, the device's main loop runs WFI once per pass, as stock does; SysTick (1 ms) wakes it, and the audio ring holds over 80 ms.
- Auto off (Settings, stock's options: Off, 1, 5, 10 min, default 5): `core/power_policy` counts from the last key press; the app holds it off each step while a track plays or USB power is present. When it runs out, the app shuts down as for a long Power press. Settings file version 2 adds the option at byte 14; version 1 files still load, with the default. Version 3 adds USB mode (Storage or DAC, see USB DAC mode) at byte 15; version 1 and 2 files load with Storage.
- Brightness 1–10 maps to a backlight duty of 8, 12, 17, 23, 30, 39, 50, 63, 80 and 100 % (`device/backlight`). Below 100 % GPIO2.4 runs stock's 10 kHz PWM, whose period follows PCLK and is reprogrammed after every clock switch. The PWM runs as the Rockchip SDK sets it up (`PWM_CTRL` `0x10003`: continuous, duty polarity negative), so the duty register counts the part of the period the pin is **low**: `backlight_duty` writes `period − period × percent / 100`. The SDK's own backlight table works the same way (rate 10 is its brightest, 85 its dimmest). Writing the lit share there instead inverted the levels (level 1 lit the panel at 92 %, level 9 at 20 %), which is why brightness looked broken in 0.1.0.

## Settings and favorites

- `app/settings_store` loads `/.echo/settings.bin` (defaults if it's missing or invalid), applies brightness, gain and output through the HAL, and only writes when the encoded bytes changed.
- `hal_dir_open`, `hal_dir_next` and `hal_dir_close` list a folder: name (UTF-8, up to 767 bytes), folder or file, size, and a hidden flag (the FAT/exFAT hidden attribute on the device, a leading dot in the simulator). `.` and `..` are never listed. On the device, `fat_open_directory` and `fat_next_entry` walk FAT16/FAT32 entries (long names, or 8.3 names with the lowercase flags) and exFAT entry sets; up to 16 folders can be open at once. macOS's `._` files are listed like any other file.
- Folder entries are read in runs of up to 8 sectors, like file data, and writes of whole sectors go out as one multi-block write without reading them first. `fat_open` remembers the last folder it found (path and entry, up to 255 bytes of path) and starts the next lookup there when the parent path matches, so opening the tracks of one album walks only the album's folder. Mounting or reserving a file forgets it. On a 1,563-track card this took opening files from 40 s to 1.8 s, and the track scan from 61 s to 19 s.
- On the device, `hal_file_write` overwrites an existing file in place from offset 0 (`fat_write`, FAT16, FAT32 and exFAT) and fails if the file is missing or too short; it never allocates clusters or changes a directory entry. Every reader checks its magic and accepts a longer file, so a zero-filled file reads as missing.
- The player makes its own files. On every `app_start`, `app/card_files` calls `hal_file_reserve` for `/.echo/settings.bin`, `resume.bin` and `favorites.bin` (4 KB each), `library.db` (4 MB) `covers.bin` (80 MB) and `scan.bin` (4 KB, the music fingerprint), in that order. A file that exists is left alone, whatever its size. A missing one is created at its size, along with `/.echo` if needed; its first 4 KB read as zero and the rest is left as the card had it, so creating 80 MB costs a few hundred writes rather than 163,840. When `library.db` was just created the app asks for a rescan, so a new card is scanned on its first start. If any file doesn't fit, the app toasts "The card is full". `tools/save_files.py` is now only a development helper.
- On the device, `fat_reserve` (`device/fat_reserve.c`, `fat_create.c`, `exfat_create.c`) creates the missing folders and the file as one contiguous run of clusters, first fit. Names are printable ASCII up to 64 characters. FAT16/FAT32 get an 8.3 entry with the lowercase flags when the name fits (`settings.bin`), otherwise long-name entries plus a `~N` short name that's unique in the folder (`.echo` → `ECHO~1`, `favorites.bin` → `FAVORI~1.BIN`); the chain goes into every FAT copy and FAT32's FSInfo free count and next-free hint are updated. exFAT gets a File, Stream (NoFatChain, valid length = size) and Name entry set with its name hash and set checksum, and the clusters are marked in the allocation bitmap. The write order keeps a cut-off write harmless: clusters are marked used first, then the start of the data is cleared (a new folder's whole cluster, with `.` and `..` on FAT), and the directory entry goes last (on exFAT the secondary entries before the File entry). A folder whose entries are full isn't grown; that reserve fails. Dates are 2026-01-01, since the player has no clock. While it runs, every card read beats the stall watch. `test_fat_create` creates files on all three fixture cards and saves them, and `created_cards_pass_fsck` checks the results with macOS's `fsck_msdos` and `fsck_exfat` (through `diskutil image attach --noMount`).
- At start-up the saved volume, shuffle and repeat go to the player first, and then a valid resume file overrides them. The current volume, shuffle and repeat are copied back into the settings before every save.
- The start screen setting pushes the matching path at start-up (for example Home → Music → Albums), so Back still leads home.
- `app/favorites_store` loads and saves `/.echo/favorites.bin` and toggles albums by key, and counts a revision on every load and toggle. Music → Favorites is a browse screen over the Albums view that only shows the positions of favorite albums, collected in album order. The browse pool keeps the collected list and only collects again when the revision changed. Collecting reads every album's key from the card, so it calls a `between_albums` hook every 8 albums (`favorites_collect`), and the browse screen uses it to run `hal_audio_service`: before this, opening Favorites while playing starved the DMA ring for a second or two and the ring's last 0.3 s played over and over. Favorite albums show ★ before their year.
- Toasts are app-owned. Screens get a pointer to the one `Toast` and show short messages such as "Added to Favorites". The app draws the toast on top of every screen.

## Audiobooks and podcasts

- `playback/spoken` decides what is spoken word from the path alone: a track whose first folder is `Audiobooks`/`Audiobook` or `Podcasts`/`Podcast` (ASCII case-insensitive). Both indexers sort spoken word after the music and record music counts in the library header (format version 3, see `docs/library-format.md`), so the Music lists leave it out while the shelves browse its folders. The rule itself lives in `library/spoken_path`. `spoken_shelf_folder` finds those folders among the root folder's children.
- Bookmarks are keyed by FNV-1a hashes of paths, so they outlive a rescan, like favorites: a book's key is its folder's path (`Audiobooks/<Book>`), and a book that is a single file, or a podcast episode, is keyed by its own path. Each bookmark also keeps the track's path hash, its chapter (its place among its folder's tracks), the position and a finished flag. `playback/bookmarks` keeps the 128 most recent, newest first, in `/.echo/bookmarks.bin` (4 KB, reserved by `card_files`; see `docs/library-format.md`).
- The player marks a track spoken when it starts it (`player->spoken`), after a gapless hand-over and after a restore. For a spoken track:
  - a start from 0 asks `PlayerResume.position_for`, which `app/spoken_store` answers from the bookmark when its track hash matches and it isn't finished;
  - `player_skip` becomes `player_jump`: +30 s or −15 s, and a jump past the end starts the next track. Now Playing's hold-vol± and the screen-off keys go through `player_skip`, so both follow;
  - the queue is built in order (`PlayerListStart.in_order`), and `player_set_shuffle` keeps it in order, while `player->shuffle` keeps the music setting.
- `app/spoken_store` follows the player every step: when a spoken track starts it notes its keys and chapter, puts the bookmark every 5 s and on every play/pause change, and when the track ends or changes it marks the bookmark finished if it was in its last tenth (at most 30 s). The file is written when playback stops, when the track changes, every 30 s while playing, at shutdown and before a USB session.
- Home lists Audiobooks and Podcasts after Music, shown only when the folder exists (checked once when the screens are built). Both are browse screens in shelf mode over the folder: rows get "N chapters"/"Chapter n of N"/"Finished" or "N episodes", and tracks "mm:ss left"/"Played". In Audiobooks, ▶ on a book plays its folder from the bookmarked chapter (the chapter is checked against the track hash and looked up again if the files moved); a book that is already loaded is resumed and Now Playing opens. Hold ▶ on a book or show opens its tracks.

## Equalizer

- **Presets.** Off, Retro, Bass, Heavy, Pop, Jazz, Unique and Custom, in the order and with the names of FiiO's menu. The bands and gains come from the tables in stock 3.7.0's music overlay (scatter row 66, data row 67: eight 62-byte entries at `0x030464A8`, IMG `0xC11B4`), values only. Stock runs a 31-band graphic EQ on the ISO third-octave centres (20 Hz to 20 kHz, 25 levels per band, level 12 flat, 1 dB steps) and each preset sets a few bands: Retro +1 dB at 100, 315 Hz and 1 kHz, −6 dB at 10 kHz; Bass +5 dB at 63 Hz, +3 dB at 125 Hz; Heavy +3 dB at 315 Hz and 1 kHz, −3 dB at 3.15 kHz; Pop +4 dB at 100 Hz, −3 dB at 3.15 kHz, +3 dB at 10 kHz; Jazz +4 dB at 100 Hz, −6 dB at 315 Hz, +4 dB at 1 kHz, +1 dB at 3.15 kHz, +6 dB at 10 kHz; Unique +3 dB at 100 Hz, −3 dB at 1 kHz, +3 dB at 3.15 kHz. Stock's filter coefficients live in a resource (#36) that wasn't extracted, so EchoPod uses its own filters at those centres, one octave wide (Q 1.4). Stock's Custom has 5 bands (100, 315 Hz, 1, 3.15 and 10 kHz, ±12 dB); EchoPod's has 7, 1⅓ octaves apart (63, 160, 400 Hz, 1, 2.5, 6.3 and 16 kHz, Q 1.0, ±12 dB in 1 dB steps). Stock applies its EQ only to sources under 24 bits; EchoPod applies it at any depth.
- **Filters** (`dsp/equalizer`). One bell filter per band that isn't flat, as Andrew Simper's linear trapezoidal state-variable filter: g = tan(πf/fs), k = 1/(Q·A), a1 = 1/(1 + g(g + k)), m1 = k(A² − 1), and per sample `v1 = a1·(band + g·(x − low))`, `v2 = low + g·v1`, `band = 2v1 − band`, `low = 2v2 − low`, `y = x + m1·v1`: four products. Its coefficients map to frequency, width and gain with unit sensitivity, so Q14 (16-bit) coefficients hold every band centre within 0.12 dB (0.21 dB off centre) of the exact design at 44.1–96 kHz, where the direct-form biquad it replaced needed Q30 and 64-bit multiply-accumulates. Each product splits the 32-bit signal into 14 low and 18 high bits so the Cortex-M3's 1-cycle `MUL`/`MLA` give it exactly; the long multiplies (`SMULL`/`SMLAL`) take up to 7 cycles on this core and audio values never end them early. The two integrator products carry their dropped low bits into the next sample (first-order error feedback), so silence after loud bass comes out as exact zeros and the filter's own noise stays near −128 dBFS at worst (−145 dBFS typical) with a −60 dBFS tone; the biquad left up to −66 dBFS of DC after boosted bass at 96 kHz. Samples enter as 24-bit values shifted up 4 bits and states stay bounded (about Q·A times the signal, 2.5× headroom over the harshest test), so the loop needs no clamp; the result is rounded back to 24 bits and saturated (`SSAT`, helped by `-fno-move-loop-invariants` on `equalizer.c`). m1 is computed from the quantised a1 and g so the centre gain is exact, Q is at least 0.5, and coefficients are capped below 4. The preamp, minus the largest audible boost (0 to −12 dB), scales the input before the first band, so a boost never clips a full-scale signal. The design needs no maths library: sine and cosine of half the angle come from Taylor series in Q30, and 10^(dB/40) from a 37-entry table. A band is skipped when its centre is at or above 0.45 of the sample rate. Above 96 kHz (`EQUALIZER_MAX_RATE`) no band runs. Changing only gains keeps each band's state, so moving a slider doesn't click; a different set of centres clears it. Audio goes through the equalizer in chunks of 32 frames, one band and one channel at a time, so coefficients and state stay in registers.
- **Where it runs.** FLAC and ALAC go through core 1's FLAC program, which runs the equalizer itself: core 0 writes the curve into the shared block at `CORE1_SHARED_EQUALIZER` (`Core1EqualizerShare`: a version, an enable flag and the `EqualizerCurve`, written by `board_core1_set_equalizer` at every change and before core 1 starts), core 1 designs the filters for the stream's rate whenever the version changes, and `core1_stream` widens each decoded block to 24 bits and filters it in its slot before marking the slot full, with `StreamSlot.equalized` set. Core 0 hands such a block on as a 24-bit `AudioFrame` with `equalized` set, and `device/audio_engine` skips its own equalizer for it. The enable flag is set only when core 1 runs at the full 200 MHz: `board/core1.c` starts the FLAC program at divider 1 whenever the curve has a band away from 0 dB (as it already does for AAC and Opus), and a track start with a different speed wanted restarts core 1, so turning the equalizer on or off moves the work at the next track. Until then, and for MP3, AAC, Opus and WAV, `device/audio_engine` runs the equalizer on core 0 as it copies each 32-frame chunk into the music ring, after `to_output`; both paths hear Bluetooth too. A rate change redesigns it. A change reaches the ears once the slots and the ring have played out (up to about 300 ms at 44.1 kHz). Measured on core 0 with the frame overlay on a 96 kHz 24-bit FLAC with all 7 Custom bands moved, before the move to core 1: the audio share (`L`) went from 29 % (equalizer off) to 72 % with either filter (about 60 cycles per band per channel-sample: the Loop cycles diagnostic reads `r4.00 m14.02` during playback, against about 3 and 9–10 for a Cortex-M3 with no wait states, so memory adds 1.3–1.5× to every instruction), and the frame time from 28 to 66 ms. Core 1 at 100 MHz showed 45 % (`c`) decoding the same track, so at 200 MHz decoding plus the equalizer should fit with room to spare; not yet measured. With the equalizer off, batching the engine copy and the unity-gain fast path took the same track from 61 % to 29 %. `test_core1_stream` checks that core 1's output is bit-identical to `equalizer_process` on the same samples. The simulator runs the same code on its float chunks at the track's own rate. USB DAC mode bypasses the engine and has no equalizer.
- **Saving.** `app/equalizer_store` keeps the choice in `/.echo/equalizer.bin` (reserved at 4 KB by `card_files`): `EMEQ`, version 1, a zero byte, the preset at byte 6, the seven Custom gains + 12 at bytes 7–13, and an FNV-1a checksum of bytes 0–15 at byte 16. A missing or invalid file means Off and flat. It is written when an Equalizer screen is left and with the settings (screen off, shutdown), only when the bytes changed, and applied through `hal_audio_set_equalizer` at start-up. It is a separate file so the settings format doesn't change.
- **Screens** (`screens/equalizer_screen`). Settings → Equalizer (value: the preset name) and a long ≡ on Now Playing open the preset list. The equalizer follows the highlighted row, so each preset plays as the selection moves; ↩ or ▶ keeps it and saves. ▶ on Custom opens the editor: seven columns with a track, a bar from the 0 dB line and a knob, the selected column highlighted, "1 kHz   +3 dB" and "Preamp −3 dB" above, the band labels and a key hint below (or "EQ is off for tracks above 96 kHz"). It has two modes, so a band missed is one press away in either direction: picking, where Vol± move the highlighted column (stopping at the ends), and adjusting, entered with ▶, where the column turns blue and Vol± change its level by 1 dB (the volume keys repeat here). ▶ or ↩ leaves adjusting; ↩ while picking leaves the screen, and a long ↩ always saves and goes home. A long ▶ sets the highlighted band to 0 dB in either mode. The editor always opens in picking.

## Library rescan on the device

- Settings → Rescan library sets a flag; on the device, the end of a USB session in which the computer wrote to the card sets a second flag that first runs a music check, under a "Music / Checking for changes..." notice. macOS writes `.fseventsd` and `.Spotlight-V100` on every mount, so a write alone means little: `library/music_fingerprint` walks the card from `/` with one open folder per level (each folder is opened and listed once; a folder that can't be opened counts as empty; a card deeper than 32 levels gives an incomplete fingerprint), skipping names that start with `.`, and folds every entry's path, kind, size and modification stamp into two FNV-1a hashes plus a count. On FAT the stamp is the raw write date and time and the size is the directory entry's. On exFAT the stamp is the last-modified time converted to UTC with the entry's own UTC offset byte (`fat_exfat_utc_stamp`, in 2-second units since 1970; no valid offset counts as UTC), and the size is the stream's data length, not its valid data length; files of 4 GiB or more aren't listed. That is what Windows, macOS and Linux report for the same file, so `tools/echo_sync.py` can match it without guessing time zones: on one card, 9 files written with a wrong offset (−5:30 instead of +5:30) and 3 incompletely copied files (valid length short of the size) had made every PC fingerprint differ. It is compared with the fingerprint kept in `/.echo/scan.bin` (4 KB, made by `card_files`; the bytes `MESC`, the two hashes, the count), and only a difference (or no record, or a walk that failed) asks for a rescan. Every successful rescan stores the fingerprint taken just before it. A requested rescan the next `app_step` runs `library_rescan_run`, shows "Scanning library" with the track count every 250 ms, then restarts the app on the new library and toasts "Library: N tracks" or the reason it failed (no card, no room, too big, a folder too big, a path too long, a write failure, or missing rescan code).
- `app/library_rescan` checks for a music root (`/`) and a reserved `/.echo/library.db` (its size is the capacity), then asks `hal_system_load_rescan_code` for the indexer's `LibraryScanEntry` and `hal_system_borrow_scratch` for working memory, and runs the scan with the HAL adapted to `ScanFileSystem`. The database goes out through `hal_file_write_at` and is never written unless it fits.
- The indexer is its own library (`echo_library_scan`). The simulator and the tests link it and return its entry table directly. On the device it doesn't fit the 157 KB code window, so it's built as `echo_rescan_overlay`: linked at `0x0307A000` against the main ELF's symbols (`--just-symbols`, plus libgcc for the double helpers), with a 16-byte header (magic `EOVL`, size, CRC of the rest, reserved) before the entry table. `tools/make_image.py --overlay` stores it at image offset `0x200000`, beyond the `fw1 end` the header records and inside the area the trailer CRC covers and our updater writes. `board/overlay.c` reads it from firmware slot 1 into HIGHRAM0 on every rescan and checks the magic, the size and the CRC before calling it. It may be at most `0x18000` bytes: the top of HIGHRAM0 holds the glyph cache.
- On the device the scratch memory is core 1's RAM (`0x01000000–0x0105FFFF`, 384 KB): playback is stopped, core 1's domain is powered up with the core held in reset, and it's powered down again afterwards.

## Covers on the device

- After a rescan writes `library.db`, `library_rescan_run` asks the same entry table for `covers` (`library/cover_build`) and passes the scan's scratch memory, the file adapters, `library.db` to read back and `/.echo/covers.bin` to write in place. It shows "Finding covers" with "N of M albums". The toast then reads "Library: N tracks, M covers", or ", no covers" if `covers.bin` is missing or the cover pass failed.
- For each album (in album order) it takes the first art it finds, as `tools/cover_export.py` does: the embedded picture of the album's first track (a front cover wins over any other picture, `track_tags_read`), otherwise `cover`, `folder`, `front` or `albumart` with `.jpg`, `.jpeg` or `.png` (any case, the first by name when several share a stem) in the album's folders in track order. An embedded picture that fails to decode leaves the album without a cover, as on the PC. Unlike the PC, MP4 `covr` art counts; Ogg's base64 pictures still don't. A key already stored is skipped.
- Covers are kept between rescans. Before the pass, the builder reads the old index and its art stamps into the scratch memory, keeps the entries whose album key is still in the library and frees the records of the rest. For each album it then finds the art as above and hashes where it came from into a stamp: FNV-1a over the path (`/` plus the library's path for embedded art, the folder plus the listed name for a cover file), then three little-endian `u32`s: for embedded art the track's size, the picture's length and 1; for a cover file its size, its modification stamp (the same value the music fingerprint uses, from the folder listing it already reads) and 2. A stored stamp of 0 means unknown and never matches. An album whose stamp matches keeps its record without decoding; changed art is decoded again into the album's own record, and a new album goes to the first free record. A rescan after adding a few albums therefore decodes only those albums.
- The file has a fixed layout for its size: the 16-byte header, an index with room for every record (`(capacity − 16) / (8 + 4 + 31,360)`, 2,673 for 80 MB; a 32 MB file made by an earlier build keeps working with 1,069, since an existing file is never resized), a table of 4-byte stamps parallel to the index, then the records. Header bytes 12–15 hold the stamp table's offset. echo-sync writes the same layout and stamps (see `docs/library-format.md`), so the first rescan after it keeps its covers. A file without stamps (made by an earlier build or an older echo-sync), with another layout, or with an index that isn't sorted or points outside the records is ignored, and every cover is decoded again. The header is zeroed before the first record is written, and the sorted index, the stamps and the `EMCV` header go last, so an interrupted pass reads as no covers and the next rescan decodes everything.
- `image/cover_image` sniffs JPEG or PNG and decodes into `image/cover_grid`: the centred square crop is area-averaged into 112 × 112 cells per channel with 9-bit fractional weights (each source sample adds `value × wx × wy`, sums wrap without undefined behaviour), and the 56 px half is the exact average of 2 × 2 cells. Per-channel sample sizes let chroma at half resolution sit on the same grid; YCbCr converts to RGB (JFIF) per cell, then to RGB565 like the PC.
- PNG: every colour type and depth (1–16 bits, palette, grey, alpha ignored as Pillow's `convert("RGB")` does), Adam7, all five filters, IDAT across chunks, zlib through `image/inflate` (32 KB window, 9-bit fast tables). Rows below the crop stop the decode. A row up to 64 KB is allowed.
- JPEG: baseline and progressive Huffman (SOF0, 1, 2), 1 or 3 components, sampling factors that divide the maximum, restart intervals, Adobe RGB. It decodes at 1/1, 1/2, 1/4 or 1/8 scale (the largest that keeps the crop at 112 px or more); each reduced sample is the exact area average of its pixels (cosines averaged over the sample, all 64 coefficients), and 1/8 is the DC term alone. Baseline scans stop below the crop. Progressive decoding needs no coefficient store: every scan's contribution is linear, so DC first and refinement scans and AC first scans add straight into the grid; AC refinement scans, and AC bands that can't change the reduced samples, are skipped. CMYK, 12-bit, lossless and arithmetic-coded files are refused. More than 8 bytes of padding past a marker fail the scan, so a truncated or lying file can't spin through millions of empty blocks.
- Memory comes from the scan's scratch (384 KB): the builder's state with one record (about 35 KB), the index (a key, a stamp, a 16-bit record number and a claimed bit per entry, for the larger of the album count and the old file's count, plus a bit per record: about 27 KB at 2,673 albums), then the decoder's arena: the grid (154 KB), a 4 KB reader and up to 168 KB for PNG rows, the inflate window and tables (JPEG needs about 13 KB). The worst PNG (64 KB rows) needs about 327 KB of arena, which still fits beside a full index. Nothing is static, so it runs from the overlay.
- `test_cover_grid` checks the averaging, `cover_decode_matches_pillow` (`tools/check_cover_decode.py`) makes 28 images with Pillow and a hand-written PNG encoder and compares the decoder with an exact area average of Pillow's decode (PNG within one RGB565 step; JPEG mean ≤ 3 and 99 % ≤ 40, the rest is libjpeg's smoothed chroma upsampling against our block chroma), checks that broken and unsupported files are refused, and fuzzes every image (truncations and byte changes) under UBSan. `cover_build_matches_reference` builds a music folder with each art rule and checks `covers.bin` end to end, then writes `covers.bin` as echo-sync does and checks that the player's cover pass keeps every cover. `test_cover_build` runs the scan and the cover pass over an in-memory card with generated PNG covers and checks what a rescan reuses: everything when nothing changed, only the new album, a replaced cover file, a removed album's record going to a new one, and a full rebuild for a file without stamps or with a damaged index.

## Library

- The player builds the database on the card (see Library rescan on the device); `tools/library_index.py` writes the same format on a PC.
- On the device, `app/library_store` opens the database through `hal_file_*`, puts a block cache in front, and validates it with `library_open`.
- Browse queries (`library/library_browse`) answer three questions for any view: how many rows there are, what row N is, and what selecting it opens. They read records and strings on demand and never load the database into RAM.
- Browse screens come from a fixed pool of 6 levels. They share one cache of the visible rows' text, which is refreshed in `update` (never during `draw`) whenever the visible rows change.

## Playback

- `hal/audio.h` is high level: `play(path, start, token)`, `queue_next(path, token)`, pause, resume, seek, volume and status. The backend decodes; on the device that's `board/audio.c` (see Device playback).
- Gapless: when a track starts, the player queues the next one with a new token. The backend switches without a gap and reports the new token, and `player_update` then moves the queue on and queues the following track.
- Shuffle is seeded (`core/random`). The resume file (`/.echo/resume.bin`, `playback/resume_state`) stores the queue plan (source list, anchor track, shuffle mode, seed), the cursor, the track and the position, so the exact same queue is rebuilt after power-off. A library fingerprint rejects resume files from an older index.
- The player saves on start, on track change, on pause, every 15 s while playing, and in `app_stop()`.

## Cover Flow

- Now Playing shows the playing album's full cover (112 px) on the left, below the header, with the text, progress and times in a column to its right. It loads the cover through the same `CoverCache` full slot in `update`. Without a cover it keeps the full-width text layout.

- Albums run by album artist, then by year, the same order as Album Artists. The screen reads each position straight from the album artists' links (`docs/library-format.md`), so it holds no album list and shows every album.
- `ui/cover_flow` holds the geometry and the motion, in fixed point (256 = one cover). The center cover is flat and 112 px. Neighbours are 42 px wide trapezoids, 84 px tall on the side facing the center and 64 px on the far side, spaced 32 px apart. Between those positions, every measure is interpolated, so a cover grows and flattens as it slides in. The position eases toward the selected album with a 70 ms time constant, at no less than about 4 covers per second, and never overshoots.
- Covers are drawn farthest first, so nearer covers overlap them. `gfx/image` draws a cover column by column with nearest-neighbour sampling, clipped to the current strip.
- `app/cover_cache` holds 7 half-size covers (56 px, 6,272 B each) for the center ±3, in slot `position % 7`, plus one full-size cover (112 px, 25,088 B) for the center, about 69 KB in total.
- Covers load in `update`, one per frame: the nearest missing half cover first, then the full cover once the motion has stopped. A cover is drawn from the full image when that's loaded for its album, otherwise from the half image, otherwise as a placeholder. Beyond ±3, covers that aren't loaded aren't drawn.
- Play opens the album's track list, a long Play toggles the favorite, and Back leaves. The screen is full screen: no header or status icons, and the title (★ for favorites) and album artist go under the cover. The first time it opens, it starts at the playing album, or at the first album.
- Position 0, before the first album, is **Random album**: its cover is a 48 px shuffle mark drawn once into a static image (white crossing arrows on dark slate), and its text is "Random album" / "Play any album". Play there picks one of the music albums with `core/random` seeded from the microsecond clock, plays it from its first track in track order (shuffle off for that queue), moves the flow to that album and opens Now Playing. The albums sit at positions 1 and up, so the cover cache slots and the playing-album lookup are offset by one.

## Rendering

The panel keeps its own image memory, so we never hold a full framebuffer. The strip renderer clears a 320×34 buffer, asks the current screen to draw into it, pushes it to the display, and moves on to the next strip. Before pushing, `gfx/frame_diff` compares a hash of every row (FNV-1a over pixel pairs) with the previous frame's (680 bytes for 170 rows), and only the span of changed rows in each strip goes to the display. An unchanged frame sends nothing, and moving a selection sends a few rows. `app_start` forgets the hashes, so the first frame is always sent whole. After the screen, the app draws the status icons (play state on the left of the header, battery on the right, both inside the header insets), the toast and the frame overlay. The overlay shows the average frame time and its split: u (input, player and screen update, including card reads), d (drawing and hashing) and s (sending to the panel). The renderer clears every strip to the theme background, so screens don't fill it again. Screens marked `full_screen` (the key test) get no status icons. While the start-up or goodbye fade runs, the app draws only the fade (centred text in the title font, blended from the background to the text colour) and drops key events. `app_show_splash` starts the 1.1 s "EchoPod" fade after `app_start`. While a track plays, turning the screen on pushes Now Playing, unless the top screen sets `stays_on_wake`. Idling in a menu never leaves it. Pushing or popping a screen by key slides it (`ui/slide`, 240 ms, cubic ease-out): the title bar stays and switches its title halfway, and both screens are drawn shifted below it through `canvas_shifted`; if either screen is full screen, the whole screen slides. Waking into Now Playing doesn't slide. Browse levels keep two row caches so both sides of a slide have their text. A long Power press saves the session at once, shows "Goodbye" fading out over 1 s, then turns off. With the screen off it turns off straight away. Drawing uses screen coordinates and clips to the strip. Lists skip rows outside the strip, and glyphs outside the clip are culled. This saves ~85 KB of RAM compared with a full framebuffer.

## Generated code

- `src/library/sort_fold_table.{c,h}` is generated by `tools/fold_table.py` from Python's `unicodedata`: for each code point in Latin, IPA, Greek, Cyrillic, Latin Extended Additional, Greek Extended, punctuation, letterlike and number forms, enclosed alphanumerics, kana, CJK compatibility ideographs, ligatures and fullwidth/halfwidth forms, the NFKD-decomposed, mark-stripped, case-folded text the PC indexer's `sort_key` gives it. `library/sort_key` applies it (plus Hangul syllable decomposition and ASCII lowercasing), trims Unicode whitespace and drops a leading "the ". Regenerate with `.venv/bin/python tools/fold_table.py --output src/library --style .clang-format`; `sort_fold_up_to_date` checks it.
- `src/fonts/` is generated by `tools/font_build.py` from `assets/fonts/fonts.json` and the TTFs in `assets/fonts/`, and `src/fonts/packs/` by `tools/glyph_pack.py` from `assets/fonts/glyph_pack.json`. Never edit either by hand.
- Fonts are Inter (SIL OFL 1.1, license in `assets/fonts/inter/OFL.txt`), pre-rendered to 4-bit coverage. The built-in tables in `fonts.c` hold ASCII and common punctuation only. Everything else comes from glyph packs, read on demand (below).
- Regenerate with:

  ```sh
  .venv/bin/python tools/font_build.py --config assets/fonts/fonts.json --output src/fonts --style .clang-format
  .venv/bin/python tools/glyph_pack.py --config assets/fonts/glyph_pack.json --output src/fonts/packs
  ```

- The `fonts_up_to_date` and `glyph_packs_up_to_date` tests fail if the committed output differs from a fresh build. `glyph_pack.py` skips a face whose font file is missing (the CJK font isn't in the repository yet), in both modes.
- **Glyph packs:** `assets/fonts/glyph_pack.json` lists the faces in face order (face 1 first): `cjk_16` and `cjk_12` (Noto Sans CJK SC, SIL OFL 1.1: the 2,350 Hangul syllables of KS X 1001, the 6,763 hanzi of GB 2312, the kanji of JIS X 0208, kana, CJK punctuation and fullwidth forms, 12,478 glyphs, about 1.64 MB and 1.01 MB), then the Latin-1 letters (U+00A0–U+00FF) of each Inter font (about 5–8 KB each). Each `Font` has two 1-based `pack_faces`: the first for codepoints below U+2E80, the second for the rest (0 for none). `font_find_glyph` tries the built-in table, then that pack face, then `?`.
  - A face is one blob: a 32-byte header (`EGLF`, version 1, entry size 12, 42 entries per index sector, glyph count, directory, index and data offsets, size, and the image CRC of the rest), then at `0x200` a directory with the first codepoint of every index sector, then index sectors of 42 sorted 12-byte entries (codepoint, width, height, left, top, advance, 0, bitmap offset) padded to 512 bytes, then the bitmaps, packed as in `fonts.c`. A glyph whose bitmap passes 144 bytes is dropped (only the vertical kana repeat marks U+3031–U+3035 at 16 px, which the config leaves out anyway).
  - `gfx/font_pack` reads them through a `FontPackReader` (face, byte offset, length) into memory the platform hands over: the face headers and directories (up to 320 index sectors each), one index sector, and a 4-way set-associative cache of 160-byte slots (a glyph plus its bitmap). A lookup costs the index sector and the bitmap on a miss (the header and directory once per face), and nothing on a hit. Misses are cached too, so a character no face has is read once. A glyph from a pack stays valid until the next lookup; text drawing resolves its bitmap once per glyph (`font_glyph_bitmap`), not per pixel. The memory must be 4-byte aligned; the number of sets is a power of two.
  - Device: `tools/make_image.py --glyph-face` (one per face, in face order; a missing file is an empty face) places the faces largest first into the image's free space (`0x30000`–`0x200000`, `0x2C0200`–`0x44C000`, `0x218000`–`0x240000`, `0x260200`–`0x280000`), sector-aligned, and writes a table at `0x2C0000` (`EGPT`, count, then offset and size per face). `board/glyphs.c` reads the table from slot 1 at boot, before `app_start`, and reads faces through a one-sector buffer. Its table, sector buffer and the 51 KB cache memory (3.7 KB of face state, then 64 sets of 4 slots: 256 glyphs) sit in `.glyph_ram` (`0x03092000`–`0x0309EFFF`, the top of High RAM): `board/overlay.c` and `rescan_overlay.ld` cap the rescan overlay at `0x18000` bytes (it is about 79 KB), so a rescan never overwrites the cache, and the High RAM diagnostic restarts the reader after its test. After an update, until the restart, reads are refused (glyphs already cached still draw; others show `?`), like the rescan overlay and the core 1 programs.
  - Simulator: `platform/sim/sim_glyphs.c` loads `src/fonts/packs/<face>.bin` (paths from `glyph_pack.json`, through CMake) into memory and hands the same 52 KB of cache over. `test_sim_glyphs` checks the committed packs through it.

## Memory

- No heap in `src/`. Every buffer is static and sized at compile time.
- `src/` is freestanding C11 and includes only `<stdint.h>`, `<stdbool.h>` and `<stddef.h>`.
- The `target_audit` test cross-compiles `src/` for Cortex-M3 and reports flash and static RAM per module. It fails on any heap symbol and when static RAM exceeds `ECHO_APP_RAM_BUDGET_BYTES`.
- No recursion and no VLAs. The device stack is 16 KB.

## Code rules

- No comments in any code: C, CMake or Python. Names and small functions carry the intent. Prose belongs in `docs/`.
- Names:

  | Kind | Style | Example |
  |---|---|---|
  | Types | `PascalCase` | `KeyTracker`, `FrameStats` |
  | Functions and variables | `snake_case`; public functions prefixed with the module | `key_tracker_update` |
  | Constants and enum values | `UPPER_SNAKE_CASE`, prefixed | `KEY_GESTURE_PRESS`, `FONT_INTER_REGULAR_16` |
  | Files | `snake_case`, named after the module | `key_tracker.c` |

- Functions:
  - do one thing
  - stay short (aim for under 20 lines)
  - take at most 4 parameters; group anything more into a struct (`Label`, `TextStyle`, `MenuConfig`)
- Pass small value types by value and anything larger by pointer. Use `const` wherever data is read-only.
- No mutable globals in `src/`, except state owned by the composition root (`app.c`). Platform singletons live in `platform/`.
- Every rule in `core`, `gfx` and `ui` has a unit test. Test names describe the behaviour.
- `clang-format` (`.clang-format`) defines formatting. Warnings are errors (`cmake/project_options.cmake`).

## Device platform

`docs/hardware.md` summarises the hardware these drivers talk to.

- `platform/device/logic` holds the driver logic that doesn't touch hardware, so it builds and is tested on the host too:
  - `key_ladder`: ADC bands to keys
  - `key_scanner`: debounce over two samples, a transition queue, and ignoring the Power press still held from switching on
  - `panel`: the init streams for both panel variants, and the window and pixel commands, sent through a `PanelBus`
  - `tick_clock`: milliseconds and microseconds from the 24-bit SysTick down-counter
  - `sd_card`: the SD setup protocol (v1 and v2 cards, the ACMD41 retries, the RCA, capacity from the CSD register, the 4-bit bus), driven through an `SdHost`
  - `emmc_layout`: finds the firmware slots (from the IDB's system size) and scans for the user volume on internal storage. It also answers which internal-storage writes are allowed: only the user volume and the two firmware slots, never the IDB, the SAVE block or the gap
  - `bt_module`: the Bluetooth module's command protocol. It waits up to 5 s for the `CV1` ready report, sends `CS00` to scan (once more after 4 s if nothing answers, `CP00` after 30 s), collects `CS` scan results until `CSEN` (dropping unnamed ones; a new scan keeps the earlier results, marks in `found_now` the ones it finds again, and past 6 drops the oldest; `CP00` stops a scan early), and sends `CQ00` every 3 s while ready, scanning or connected, every second while a connect runs and every 0.5 s while a paired reply waits for the link (stock's Bluetooth screen polls in every state). Connecting sends `CL06` + the picked address, from Ready or during a scan (once more as `CH06` after 4 s if nothing but `CQ` answers arrived, `CT00` and a failure after 30 s); `CLOK` means paired, `CLER`/`CHER` failed, `CHOK` connected, `CQO` + address + name connected in any state, including while a connect runs, any other status letter while connected or `CT`/`CTOK` means the link dropped. Disconnecting sends `CT00`. While connected, starting the stream sends `CY0` + `1E` + 0 and stopping it `CY0` + `00` + 0. As in stock, the `C` `86`/`87` notices only answer the module's own reports: the play state is what the module last reported (`CP` paused, `CC` playing; nothing on a new link). Starting the stream after a `CP` sends the play notice `C` `86` `30 30` 0 first and `CY0` + `1E` + 0 100 ms later; stopping it after a `CC` sends the pause notice `C` `87` `30 30` 0 first and `CY0` + `00` + 0 100 ms later; otherwise only the `CY0` frame goes out. (Sending a notice on every pause and resume, with the play notice after `CY0` `1E`, left the headphones silent a moment after some resumes.) Every new link first gets `CY0` + `00` + 0. The module's `CP`/`CC` (pause/play) and `CA`/`CB` (previous/next) reports count presses in `HalBluetoothRemote`; a `CP`/`CC` after `CLOK` also counts as the link coming up (the Buds send them as soon as they're in the ears), and while connected `CQ00` polling pauses for 50 s after one, as in stock. A dropped link, `CT` or `CTOK` ends the stream and clears the pairing result. While the stream is on, `board/bluetooth.c` holds GPIO2.0 high and GPIO2.14 low on every service pass, as stock does on connect, and restores them when the stream stops or the module powers off. Received bytes are split into frames as soon as a frame is complete; an incomplete frame is dropped after 2 ms of silence. It also keeps the last 12 bytes, counts bytes and frames, and logs the last 12 messages (frames other than `CS` and repeated `CQ` letters, plus the `CS`, `CP`, `CL`, `CH` and `CT` commands it sent) with the seconds between them; the log and the devices found survive a power-off and power-on, so a restart keeps the evidence
  - `usb_device`: the descriptors and standard requests for a bulk-only mass-storage device (`1209:0001`, the pid.codes test ID), plus GET_MAX_LUN and the mass-storage reset. Full speed only (64-byte bulk packets; the device qualifier and other-speed configuration stall) until the board allows high speed; then it serves a device qualifier and an other-speed configuration (type 7, the opposite speed's configuration), and the configuration's bulk packet size follows the speed the board reports (512 at high speed, 64 at full speed; EP0 stays 64)
  - `usb_audio`: the USB Audio Class 1.0 device for DAC mode (`1209:0002`, the next pid.codes test ID, so hosts don't mix up its cached descriptors with mass storage's): the device and configuration descriptors, interface alternate settings, the sampling-frequency and feature-unit class requests, and the FIFO split. Everything else (address, configuration, status, strings) goes to `usb_device`. See USB DAC mode
  - `usb_audio_sink` and `stream_drift`: USB audio packets into the music ring, and the ring-level controller that keeps it near 20 ms of audio (see USB DAC mode)
  - `msc`: the bulk-only transport and SCSI commands over up to two LUNs. A reply shorter than the host asked for is padded with zeros and reported in the residue instead of stalling. Ejecting a LUN marks only that LUN absent. Given a buffer (`msc_use_write_buffer`), WRITE(10) data collects there and reaches the drive in one write call per full buffer, plus one for the rest; a failed call fails the whole command. Without one, each sector is its own write. READ(10) uses the same buffer the other way: when the next sector isn't loaded, one drive read fetches as many sectors as the command still needs, up to the buffer (64 sectors, 32 KB: one multi-block CMD18 on the card), and the bulk IN packets are served from it. Reading one sector per command held reads over USB at about 1.2 MB/s
  - `usb_fallback`: when to give up on high speed: watching starts at the first bus reset of a high-speed session, a working session (configured and through two SCSI commands) stops it, and 10 s without one asks for a full-speed reconnect, once
  - `card_write`: the order of a card write through a `CardWriter`: one block is CMD24 then a wait for the tran state; several are one CMD25, then CMD12 (sent even after a failed transfer, so the card leaves the receive state), then the wait, which is skipped if the stop failed
  - `image_crc` and `updater`: the image check and the slot writer. The check accepts our 5 MiB shape (size, magic, fw size `0x44C000`, header copy, trailer CRC, fits a slot) and reports an image already in slot 1 as installed. It also accepts FiiO's 8 GB stock image as `UPDATE_STOCK` (33,554,436 bytes, magic, brand "Rockchip", a sector-aligned fw size whose header copy fits below 32 MiB and matches, trailer CRC, fits a slot, and the 8 GB marker) and refuses the 512 MB model's. The fw size doesn't tell the models apart: it was `0x01FC4000` for the 8 GB images up to 3.9.0 and `0x01FCC000` for the 512 MB ones, but FiiO's 8 GB 4.0.0 uses `0x01FCC000` too. Instead, each stock image holds the 8.3 names its own updater looks for: the 8 GB images (3.7.0–4.0.0) contain `HIFIEC00IMG` and never `MINIV100IMG`, the 512 MB ones (3.9.0, 4.0.0) the reverse. The CRC pass scans every 8 KiB chunk for both, including a marker split across two chunks, and an image is stock only with the 8 GB marker and without the other; a stock install writes `[0, 32 MiB)` the same way, as stock's own writer does. The install fills slot 2, then copies slot 2 into slot 1. For each slot it first writes `0xFF` over the first 8 KiB, then every other 8 KiB chunk, then the first chunk last. Chunks that already match are skipped, and every write is read back. One slot is complete at every moment
  - `fat`: a read-only FAT16, FAT32 and exFAT reader over a `BlockDevice`. It reads unpartitioned cards or MBR partition 0, follows FAT long names and exFAT name entries (UTF-16, including surrogate pairs), matches path components exactly by code point and ASCII letters in either case, and reads at any offset. FAT files follow a per-file cluster cursor; exFAT files marked NoFatChain are contiguous and skip the FAT. Cluster walks and directory scans are bounded, so a corrupt chain can't hang the player
- `platform/device/board` is device-only. It holds the register helpers, GPIO and pin mux, startup (the vector tables and its start-up steps), the linker script, a minimal `memcpy`/`memset`, and the HAL implementations.
- `platform/device/core1` is the program for the second core: its own startup, `main` and linker script (code at core 1 address 0, data at `0x01021000`, stack top `0x0102E000`). It builds to `core1.bin`, which is linked into the core 0 image as read-only data. `device/core1_control` holds the power-up, start and stop sequences and the shared-block layout, tested on the Mac; `board/core1.c` runs them.
- **Build:** `cmake --preset device && cmake --build --preset device` cross-compiles to `build/device/platform/device/echo_device.elf`. Then `tools/make_image.py` packs it into `build/device/HIFIEC90.IMG`. The outer header is written from format constants (magic `0x76543210` at `0x00C`, `4` and four `0x200` words at `0x050`–`0x06C`, `1` at `0x19C`, the fw size at `0x1F4`) plus our date, brand, build tag, fw1 end at `0x080` and `ECHO_FIRMWARE_VERSION` (major << 24 | minor << 16 at `0x004`, patch at `0x008`), with an empty part chain and zero marker bytes, so the image builds from the repo alone.
- **Release build:** `cmake --preset release && cmake --build --preset release` builds the same image into `build/release/HIFIEC90.IMG` with `ECHO_RELEASE=ON`, which links `src/app/diagnostics_menu_release.c` (Key test, Firmware, Battery, Last start, Last step, Last battery, Last USB, Jack 3.5, Jack 4.4) instead of the full developer menu in `diagnostics_menu.c`. The rows both menus share live in `diagnostics_rows.c`. `tests/app/test_release_diagnostics.c` checks the short menu.
- **Code size:** the code window is `0x2666C` (157,292) bytes and the `device` build fills most of it. Libraries in `src/` that link `echo_compact` and the cold device files listed in `platform/device/CMakeLists.txt` and `platform/device/logic/CMakeLists.txt` (start-up records, the updater, the image CRC, card file creation, the Bluetooth protocol, the DAC set-up sequence, the USB descriptors and requests, the USB sessions, and since the equalizer the audio driver's control code in `board/audio.c`, `board/dac.c`, the MP3 probe, the FAT layout, mass-storage commands, the battery gauge, clock switching, core 1 start-up and a few other set-up files) are compiled with `-Os` in cross builds; the per-sample path (the engine, the equalizer, its sources, core 1's decoders), FAT reads and card transfers, the panel push, the clock and SysTick, `board/usb.c` and the USB audio sink stay at `-O2`. With the equalizer the developer build leaves about 240 bytes of the window free, the release build about 7.8 KB.
- **Image rules,** enforced by the linker script and the builder:
  - `.data` holds only the 8-byte entry vector; no initialised mutable globals.
  - Code stays below the row-0 end (`0x030771D4`).
  - `.bss` ends below `0x0304C000`.
  - Nothing loaded is left out of the image.
- **Run model:** the main loop polls the drivers; the 1 ms SysTick interrupt keeps time and runs the stall watch (see below). The display driver samples the keys before and after every strip it pushes, so key presses aren't missed during slow frames.
- **Storage:** `board/mmc` drives the DW-MMC controller (commands, polled single- and multi-block reads and writes, CMD12, the card clock); `board/sd` and `board/emmc` write through `device/card_write` and `board/sd` powers the SD slot and checks card detect. `board/emmc` starts internal storage (8-bit bus at 24 MHz) on first use and refuses any write outside what `emmc_layout` allows. The file HAL mounts the card (FAT16, FAT32 or exFAT) on the first open and can hold 8 files open at once. Writes go in place or through `fat_reserve` (see Settings and favorites).
- **USB:** the main loop watches VBUS. When the cable is plugged in, `board/usb_session` powers the PHY and the polled DWC2 core (`board/usb`) and connects, without touching audio or the screen. It asks for high speed (DCFG speed 0) unless high speed already failed since power-on; at enumeration done it reads DSTS and uses 512-byte bulk packets at high speed and 64 at full speed, on the core's reset FIFO sizes (RX 147 words, shared TX 128), one packet per bulk OUT transfer. If a high-speed session isn't working (configured and through two SCSI commands) 10 s after the first bus reset (`device/usb_fallback`), it reconnects at full speed and stays there until the next power-on. The main loop then keeps running and checks GINTSTS for a bus reset on every pass, for up to 3 s, with the CPU clock held at 96 MHz or more. No reset means a charger: USB powers down quietly and the player carries on, playing and charging. With a host:
  - the app shows "Computer found" and its steps pause. Before the audio power pins are silenced, `app_release_audio` saves the bookmarks and unloads the player's track (it stays paused at its position) and `board_audio_shut_down` stops the DMA and powers the DAC path down through `board/audio.c`. Silencing the pins behind the audio driver's back used to leave it believing the path was still up, so nothing played after the session until a restart
  - LUN 0 is the internal-storage user volume and LUN 1 is the SD card, both read/write. Sense data is kept per LUN
  - if the controller fails to start, `board/usb_report` shows four notices (a key press moves on): the core ID and OTG control after power-up; the failed init step (with `0x10` set when internal storage started) and GHWCFG4; then GINTSTS and OTG control after the wait. This is temporary, while USB is brought up on hardware
  - the session ends when every LUN that was present has been ejected, or the cable is pulled. If the session wrote to the card, the file HAL forgets its mount and open files, and `app_start` reloads the app from the changed card. If the cable was pulled while a drive was still mounted, a notice says recent changes may be lost. Diagnostics → Last USB shows how the last session ended (ejected, or unplugged with how many drives still up), the sectors written to each drive and any writes refused after an eject. Then `board/update` opens the highest-numbered `/HIFIECnn.IMG` (00–97, stock's rule) on internal storage and installs it if it's valid and differs from slot 1, or if it's FiiO's stock image, showing progress and the result (a key press dismisses it). Finally `app_wake` restarts the screen timeout. The new firmware starts at the next power cycle, because a warm reboot doesn't work on this hardware
- **USB DAC mode** (untested on hardware): Settings → USB mode chooses Storage (the default, the session above) or DAC; `settings_store_apply_hardware` passes it to `hal_system_set_usb_mode`, and `board/main.c` reads it when the cable goes in, so a change takes effect at the next plug-in. Listening for a host, the 3 s wait and the charger case are the same as for mass storage. With a host, `board/usb_dac_session` runs instead of the mass-storage session:
  - **Class and speed:** USB Audio Class 1.0, full speed only (`usb_device_allow_high_speed(false)`, DCFG speed 1), so it needs no driver on Windows 10 and later, macOS, Linux, Android or iOS. Interface 0 is Audio Control: an input terminal (USB streaming, 2 channels) into a feature unit (ID 2: master mute and volume) into an output terminal (headphones). Interface 1 is Audio Streaming: alternate setting 0 has no endpoint, 1 is 16-bit stereo PCM, 2 is 24-bit stereo PCM (3-byte subframes), both at 44.1 and 48 kHz, on isochronous OUT endpoint 1 (adaptive, 1 ms interval) with room for 49 frames (196 and 294 bytes). 88.2 and 96 kHz are left out because their largest packet (up to 582 bytes at 24-bit) doesn't fit the RX FIFO (see FIFOs below). Android's USB audio picks the highest rate a device offers, and some Windows setups do too, so offering them meant silence on those hosts. The device descriptor says USB 1.1 and has no serial number.
  - **Synchronisation:** adaptive, by ring level, with no feedback endpoint. The I2S clock runs from the player's MCLK, so the computer's rate and the DAC's drift apart slowly (a few frames per second). `device/usb_audio_sink` converts each packet into the music ring (16-bit samples to the top half of the word, 24-bit samples shifted up by 8, two words per frame, the same format as music) and measures the fill as frames written minus frames the DMA has played. `device/stream_drift` keeps it near 20 ms: when the fill is more than 4 ms off, each packet drops its last frame (too full) or repeats it (too empty) until the fill is back within 1 ms of the target, or past it. One frame per millisecond is far faster than any drift, and a single dropped or repeated frame isn't audible. The sink also keeps the 20 ms after the newest frame silent, so if packets stop the DMA plays silence rather than old audio; if the DMA overtakes the writer (packets lost for longer than the buffer) or the ring would overflow, writing restarts 20 ms ahead of the DMA after a short silence. An asynchronous feedback endpoint would avoid the dropped frames, but it needs a second (IN) isochronous endpoint, a measured rate in 10.14 or 16.16 format and per-host quirks, none of which can be checked without hardware.
  - **Rates and formats:** the host's SET_CUR on the endpoint's sampling-frequency control (3 bytes, either of the two rates; others stall) or a new alternate setting stops the output, restarts the DAC path at the new rate through `board_audio_stream_open` (the same `dac_path_start` as music, with its ACODEC row and divider), and primes the ring again: the DMA starts once 20 ms is buffered. 100 ms without packets (the computer stopped playing) also stops the output until packets come back. GET_CUR reads the rate back.
  - **Volume:** the feature unit's volume runs from −64 dB to 0 dB in 0.5 dB steps (GET_MIN `0xC000`, GET_MAX 0, GET_RES `0x0080`); `board_audio_set_attenuation` adds it to the player's own level on the DAC's PCM volume registers (0.5 dB per unit), and mute sets them to mute. The volume keys still change the player's level by one step per press (no repeat while held) and the screen doesn't show it; the level from before the session comes back afterwards.
  - **Audio driver:** `board/audio.c` has a stream mode for this: `board_audio_stream_open` stops music (`board_audio_shut_down`), clears the music ring and starts the path at a rate; `_play` starts DMA channel 5 over the ring as for music and fades up; `_pause` clears the ring and fades down and stops the DMA; `_consumed` gives frames played; `_close` shuts the path down. While the stream is open, `hal_audio_service` and the DAC's fade waits call the session's USB service instead of the engine, so drawing a notice or fading keeps the isochronous endpoint served. The session starts with `app_release_audio()` and `board_audio_shut_down()` and ends with `board_audio_stream_close()`, so music works as before afterwards. The audio power pins are never touched directly. The CPU runs at 200 MHz: the session's first notice turns the screen on, which raises the clock as in a mass-storage session, and opening the stream raises it too if needed.
  - **DWC2 in polled mode:** the session loop polls the core (four `usb_poll` calls per pass), the audio service (jack sense) and the keys. The changes in `board/usb.c`, cited against the DWC2 register map:
    - FIFOs: the same layout as mass storage (RX FIFO 0x120 words, TX FIFO 0 0x20 words at 0x120, TX FIFO 1 at 0x140). The core accepts an isochronous OUT packet only when the RX FIFO has room for a maximum-size packet (582 bytes, 146 words) plus its status entries, so the reset size of 147 words (`GRXFSIZ` `0x93`) drops every packet: on the player that showed as no packets received, an incomplete-ISO interrupt every frame and NAKIntrpt (DOEPINT bit 13) on endpoint 1. An earlier build computed its own split from the reset values, skipped it on this chip's layout, and so stayed at 147 words. The endpoint is therefore armed for 294 bytes (`USB_AUDIO_MAX_PACKET`, 49 frames of 24-bit stereo, proven on the player), the largest packet of any offered format.
    - Endpoint: at SET_CONFIGURATION, DOEPCTL1 gets MPS 294 (bits 10:0), USBActEP (bit 15) and EPType 01, isochronous (bits 19:18); DAINTMSK bit 17 and GINTMSK bit 21 are set (the core isn't wired to an interrupt, but the status bits are polled). A streaming alternate setting arms it: DOEPTSIZ1 = PktCnt 1 (bit 19) | XferSize 294, the same for every format and rate (a shorter packet ends the transfer), so it doesn't matter whether the host sends SET_CUR for the rate before or after SET_INTERFACE, then DOEPCTL1 EPEna (31) | CNAK (26) | SetOddFr (29) when DSTS bit 8 (the low bit of SOFFN, the current frame number) is 0, otherwise SetEvenFr (28), so the endpoint takes the next frame's packet. Each transfer complete (DOEPINT1 bit 0) re-arms it the same way while streaming.
    - Missed frames: GINTSTS bit 21 (incompISOOUT) means an armed isochronous OUT endpoint got no packet in a frame. If DOEPCTL1 is still enabled and its EO_FrNum (bit 16) matches the current frame's parity, the endpoint is switched to the other parity, then the bit is cleared.
    - Packets: GRXSTSP is popped once per poll; PktSts (bits 20:17) 2 with EPNum 1 is a packet for the sink, read into the port's 128-word packet buffer (the larger of a high-speed bulk packet and `USB_AUDIO_MAX_PACKET`); 3 and 4 are skipped as before.
    - Control OUT with data (SET_CUR): the request is held until its data packet (PktSts 2, EPNum 0) arrives on EP0, which `arm_setup` keeps enabled; then the reply is applied and the status stage sent (a zero-length IN, or a stall).
    - Control IN longer than 64 bytes (the 159-byte configuration descriptor): sent as 64-byte packets, each after DIEPCTL0 EPEna clears from the previous one (up to 100 ms each). Replies of 64 bytes or less go out exactly as before.
    - Mass storage is unchanged: these paths only run when the port has an audio device, and with one the bulk endpoint and MSC calls are skipped.
  - **Screen:** "USB DAC" with "Computer found. Starting...", then "Connected. Choose EchoPod as the computer's sound output." while the host has no stream open, "Playing from computer · 48 kHz 24-bit" while it has, or "The audio output didn't start." The notice is drawn only when the format changes, because drawing delays the polling (the audio service is called after each strip, so the endpoint is still served between strips).
  - **Ending:** pulling the cable, or holding Back for 1 s and releasing it (the player then stays a charger until the next plug-in). The session powers USB down and `app_wake` restarts the screen timeout. Nothing touches the card, so there's no rescan or update check. Diagnostics → Last USB isn't updated.
  - **Memory:** no new buffers: the music ring holds the stream. The port, the audio state and the sink add about 1 KB of `.bss`.
- **Firmware tag:** `hal_system_version` (`hal/system.h`) reads the build tag from slot 1's header on the device and returns "simulator" in the simulator. Diagnostics shows it as Firmware.
- **CPU clock:** `hal_system_clock_mhz` and `hal_system_set_clock_mhz` (`hal/system.h`). On the device, `board/clock_switch.c` follows stock's PLL order with the register words from `device/pll` (96 and 200 MHz). It waits up to 200 ms for lock and stays at 24 MHz without it. After a switch it rescales the SysTick clock (`tick_clock_set_rate`). The device switches to 96 MHz right after reading the boot clocks (see Device playback). Diagnostics → CPU clock switches between 24 and 96 MHz, and Diagnostics → Stopwatch counts seconds to check the rate against a phone. CPU clock cycles 24 → 96 → 200 → 24 MHz.
- **Test tone:** `hal_audio_test_tone` (`hal/audio.h`) blocks for about 5 s. On the device, `board/dac.c` runs the SoC side of the audio path (gates, I2C0, ACODEC mux, I2S1, polled FIFO feed) and `device/dac_sequence` runs the CS43131 side (power pins, probe, register sequence, output on and off) through a `DacBus`. It plays one sine period of 100 samples (441 Hz at a true 44.1 kHz) at amplitude 9000 (ReChord's level, about −11 dBFS): 2 s with the I2S divider from the formula (MCLK / (64 × rate) − 1, truncated, which gives 2), then 2 s with it rounded (3). It reports No DAC, Setup failed, Not ready or I2S stalled when a step fails; No DAC adds the I2C step (s1 start, s2 send, s3 NAK, s4 stop, s5 receive) and the I2C pending bits in hex. Diagnostics → Boot clocks shows the low halves of CRU `+0x10`, `+0x14` and `+0x18` as the ROM left them, read first thing in `board_main`. The simulator returns Played.
- **Jack pins:** `hal_audio_jack_pins` (`board/jack.c`) records how the ROM left GPIO0.13 and GPIO2.8 (function, direction, pull), then makes both GPIO inputs and reads them. Diagnostics → Jack 3.5 and Jack 4.4 show the live level and the boot state (GPIO0.13 high = 3.5 mm, GPIO2.8 low = 4.4 mm; the 3.5 mm pin is confirmed on hardware). `hal_audio_jack` gives the debounced jack: `device/jack_sense` names it (GPIO2.8 low wins) and takes a change after 7 matching readings, one every 10 ms from `hal_audio_service`. With Output set to Auto, the volume curve follows the jack (4.4 mm: `7D` − ⌊12n/5⌋, stock's table B; 3.5 mm: `7A` − ⌊12n/5⌋); a fixed Output setting overrides it. Both jacks are driven by the same two CS43131s (one per channel), and no switch between them is known, so Output can't route sound to one jack: it only chooses the volume table, 1.5 dB apart at the top. Settings shows the detected jack next to Auto ("Auto (4.4 mm)"), and choosing an option says what it does. The player pauses when the jack goes from plugged to none and doesn't resume on its own.
- **Device playback:** `board/audio.c` implements the audio HAL with `device/audio_engine` (host-tested). The engine opens a track through the file HAL and takes decoded frames from an `AudioSource`. `board/audio.c` picks the source from the file's first 12 bytes, not its name: `fLaC` goes to FLAC, `RIFF`…`WAVE` to `device/wav_source` (PCM or extensible PCM, 1–2 channels, 8/16/24/32-bit, any chunk order before `data`, 4,096-frame blocks read on core 0 into buffers that share memory with core 0's FLAC decoder), an ID3 tag or an MPEG audio frame header to MP3, `ftyp` at byte 4 to MP4 (ALAC, or AAC with object type 2, AAC-LC; anything else is refused as an unsupported file type), `OggS` to Ogg (Opus only, channel mapping family 0), anything else is refused as an unsupported file type. For MP4, core 0 runs `codec/mp4`: it reads the first sound track's `stsd` (the ALAC cookie or the AAC `esds` config), `stts`, `stsc`, `stsz`, `stco`/`co64` and the first non-empty `elst` edit (the lead trim), and streams into the core 1 ring not the file's bytes but a record stream: a 4-byte little-endian length and the codec config, then each frame as length and bytes, starting at the frame that holds the seek target. The sample tables are read through three 96-byte caches, and opening walks `stsz` once to size the stream. The FLAC core 1 program also decodes ALAC: `StreamControl.codec` picks the decoder per track, the two decoders share memory, and the FLAC path sets the accelerator hook again before each FLAC track. `device/core1_alac` waits until a whole record is in the ring before decoding it. AAC runs on its own core 1 program (`core1/aac_main.c`, about 58 KB, at image offset `0x2A0200`, between the FLAC slot and the glyph table) with FAAD2 2.11.4 (`third_party/faad2`, pinned in `VERSION`, built with `FIXED_POINT`, `LC_ONLY_DECODER` and `DISABLE_SBR`; its ARM multiply macros need GNU C). FAAD2's decode path needs about 46 KB of stack (the channel-pair element alone is 24 KB), so `core1/core1_aac.ld` keeps `.bss` below `0x01022000` and the whole of core 1's data RAM is stack; FAAD2's few non-const tables are linked into the code area. Its `malloc` is a bump allocator over the unused tails of the four output-slot rows (each row holds 4,608 samples, an AAC frame 1,024), about 31 KB of the 57 KB there for stereo, reset at each track; `device/core1_aac` refuses a frame of more than 1,024 samples so output never reaches it. FAAD2 outputs interleaved 24-bit samples, so `Core1Block` has a stride. FAAD2 outputs nothing for the first frame it decodes, so core 0 starts an AAC stream one frame before the one that holds the seek target, and core 1 numbers frame k as starting at k × 1,024. Opus streams the file's own bytes, as MP3 does: core 0 runs `codec/ogg` to read `OpusHead` (channels, pre-skip), find the first audio page after `OpusTags`, and take the length from the last page's granule, found by scanning back from the end in 512-byte reads; a seek bisects the file by page granule and starts on the page after the last one that ends at least 80 ms plus one longest packet (120 ms) before the target. `Core1Source.play_from` then drops what core 1 decodes before the target, so the pre-roll isn't heard and the position is exact. The Opus core 1 program (`core1/opus_main.c`, about 81 KB, at image offset `0x218000`, between the overlay and the MP3 slot) runs libopus 1.6.1 (`third_party/opus`, pinned in `VERSION`, built with `FIXED_POINT`, `DISABLE_FLOAT_API` and `USE_ALLOCA`) behind `codec/ogg`'s packet reader, which follows the first serial it sees, rebuilds packets that span pages and works out each packet's first sample from the page granules and the packets' TOC bytes (looking ahead past pages where no packet ends). An Opus stream uses only the first 96 KB of the input ring (`StreamControl.ring_bytes`, which core 0 sets for every stream and core 1 adopts with it), and the 27 KB decoder state sits in the top 32 KB (`CORE1_OPUS_STATE`); the 4 KB packet buffer and the 60 ms output buffer sit in the unused end of core 1's code RAM, addressed through `0x01000000` (`.core1_big`, not loaded), so data RAM is left to the stack. FAAD2 and libopus are built with `-O2` on the device, and core 1 runs the AAC and Opus programs at the full 200 MHz (divider 1, which also selects the fast bus setting) instead of the 100 MHz the other programs use; the ALAC decoder reads its Golomb codes 32 bits at a time and has unrolled predictors for orders 1 to 8, which took it from 3.6 times libmad's cost to below it. Every core 1 program times its decoding with SysTick and publishes the busy share every 50 million ticks (`StreamControl.load_percent`), shown as `c` on the frame overlay. libopus outputs interleaved 16-bit samples, so `Core1Block` also carries 16-bit channels. MP3 is decoded on core 1 by libmad (`third_party/libmad`, 0.16.4 pinned in `VERSION`, built with 64-bit fixed point and `OPT_ACCURACY`; on the device `third_party/libmad_libc` stands in for the missing C headers and `core1/no_heap.c` makes `malloc` always fail, since `device/mp3_decoder` hands libmad static main-data and overlap buffers before its first frame). Core 0 runs `device/mp3_probe` (ID3v2/ID3v1/APE tags skipped, the first frame confirmed by the next one, length from Xing/Info or VBRI, else from size and bitrate; seeking through the Xing table or proportionally) and streams the file into the same core 1 ring; `device/core1_mp3` turns each frame into a block of 24-bit samples. Core 1 runs one program at a time, as stock does: both programs are packed by `tools/make_image.py`, MP3 (about 71 KB) at image offset `0x240000` and FLAC (about 9 KB) at `0x280000` (a 512-byte header with `EC1M`, size and CRC, then the program) and read from slot 1 on eMMC straight into core 1's RAM through a 4 KB staging buffer, with the CRC checked on the way. Switching between a FLAC and an MP3 track restarts core 1 with the other program; after an update, until the restart, both programs are refused like the rescan overlay (FLAC then decodes on core 0). On core 1 the FLAC decoder can hand LPC subframes of order 3 and up to the hardware accelerator (`device/flac_accel`) through `flac_set_lpc_hook`, but only for the classes (narrow or wide accumulator) that passed its self-test; a timeout turns the hook off. Core 0 runs the self-test once per boot, before the first FLAC stream, and passes the passing classes to every later core 1 FLAC run. libmad's `III_decode` keeps a 7 KB frame on the stack, so `core1/core1_mp3.ld` keeps the program's `.bss` below `0x0102B000`, leaving 12 KB of stack. The engine records why it refused a track (unreadable, or the sample rate with the rate), `hal_audio_refusal` reports it, the player counts refusals, and the app shows a toast such as "192 kHz isn't supported yet". On the device that is `device/core1_stream`: core 0 opens and seeks with its own decoder, streams the file into a 128 KB ring in core 1 RAM, and core 1 decodes frames into two slots; if core 1 doesn't start, `device/flac_source` decodes on core 0. Each frame is copied into a 28,000-word ring in data RAM as two words, left then right, each a 24-bit sample shifted to the top of its word (stock's music mode, TXCR `0x401F`; 16-bit sources are shifted up, nothing is rounded). Volume is set in the DAC's PCM volume registers; the engine's software gain stays at unity on the device. The engine keeps a list of segments (token, start frame, start position, rate) so the token and position follow what the DMA has played. DMA channel 5 loops over the ring through seven linked items of 4,000 words (a DW block holds at most 4,088 items; `device/dma_loop` refuses more); the HAL turns its read address into a running count of consumed frames. The app calls `hal_audio_service()` at the start of each step and after each strip, so drawing can't starve the ring (14,000 frames is 73 ms at 192 kHz, 146 ms at 96 kHz and 317 ms at 44.1 kHz). Playback starts once 100 ms of audio is buffered (at most three quarters of the ring) or after 1 s. Supported rates are 44.1, 48, 88.2, 96, 176.4 and 192 kHz, each with its ACODEC row and the rounded I2S divider. A queued track at the same rate follows without a gap; a different rate waits for the ring to drain, then the path restarts at the new rate. Volume changes fade on the DAC: 6 PCM-volume units (3 dB) every 2 ms (`dac_ramp_next`), and `board/dac.c` keeps the ring fed between steps through a service hook, so a fade never starves the ring. Starting output fades up from mute after the DMA starts; stopping, pausing, seeking and skipping fade down to mute before the channel stops. A seek while paused stays silent. Pause fades out, mutes the DAC and suspends the channel (nesting with the clock switch's suspend). Seek and play restart the ring. Three seconds after playback stops, the DAC path powers down. `hal_audio_service` polls the I2S underrun flag (INTSR bit 1, cleared through INTCR bit 2; INTCR keeps TXUIE set with the NVIC line off) and counts it in the stats, shown as `o` on the frame overlay. Diagnostics → Tone 192k plays the DMA tone at 192 kHz. The ring must stay in data RAM (`0x03004000`–`0x0304C000`): High RAM (`0x0307A000`) shares its SRAM with the code at `0x03050000`, and with the screen on core 0's instruction fetches starve the DMA's ring reads at 192 kHz (I2S underruns, an audible crackle). Core 0's FLAC header and seek decoder, which shares its memory with the WAV buffers, sits in High RAM instead (`.high_ram`, no-load): only the CPU touches it, and the rescan overlay and the High RAM diagnostic stop audio before they overwrite it. The device starts at 96 MHz (`START_CLOCK_MHZ`) right after reading the boot clocks.
- **DMA tone:** `hal_audio_dma_tone_start`, `_stop` and `_status`. On the device it checks COMP_TYPE at `0x600003F8`, brings up the same audio path with the rounded divider and INTCR `0x01F00100` and without XFER, then runs DMA channel 5 (`board/dmac.c`) over the music ring filled with a sine (16-bit samples in the top half of each word, two words per frame, the same format as music) through the same seven linked items as music (`device/dma_loop`), with every channel interrupt masked. Then DMACR = `0x110` and XFER = 1. The call returns at once, and Diagnostics → DMA tone shows "Playing" with channel 5's read position, "Ended" if the channel stopped by itself, or the failed step. Pressing it again suspends the channel, disables it, and closes the audio path. A clock switch suspends and resumes the channel around it.
- **Last start:** `hal_system_start_info` (`hal/system.h`). On the device, `device/start_record` keeps a record in `.noinit` RAM: the start count, the uptime (every 5 ms), a power-off mark, fault registers, the last battery reading (every second) and the last risky step (backlight on or off, clock switch, core 1 start or stop, card write) with its start time and whether it finished. Diagnostics → Last start, Last step and Last battery show what the previous run left, for example "#3 reset after 41 s", "In clock switch at 41 s" and "3712 mV".
- **Stall and fault screen:** a power loss wipes the Last start record, so a freeze that ends in a power cut reads Cold start. On the device the main loop beats a `device/stall_watch` each pass, and the 1 ms SysTick checks it every 5 ms. A loop silent for 10 s (paused during start-up, USB sessions, updates and power-off) trips it once: the interrupt silences the audio pins, clears the panel, turns the backlight full on and draws, in a 5×7 font scaled ×2 (`device/panic_text`), "STALL", the interrupted PC and LR (from SysTick's exception frame via `device_systick_entry`), and "UP <s> STEP <n> [U] MV <mV>" (U = the step never finished; step numbers follow `HalStartStep`). A fault draws "FAULT" with PC, LR and CFSR the same way. After either, holding Power for 2 s cuts power from the interrupt. Diagnostics → Stall test freezes the main loop on purpose to check the screen. A loop stuck with interrupts masked isn't caught.
- **Power taps:** Diagnostics → Power taps (Normal/Ignored, not saved) makes the app drop Power taps so a test can tell an electrical effect of the press from the app's reaction to it; a long Power press still shuts down.
- **Switching off:** `hal_power_off` and `board_power_cut` drive the Bluetooth module's power and UART pins low before dropping GPIO2.6; a powered module otherwise kept the player from switching off after an update, so Power did nothing until RST.
- **Charge screen:** with USB power, GPIO2.6 low doesn't cut power (`hardware.md`), so a switch-off on a cable used to leave the player dark and deaf until RST. Now the app's shut-down checks `hal_power_battery().usb_power` and, when it's set, enters charge mode instead of `hal_power_off`: it pauses and releases the output, puts Bluetooth to sleep and draws `screens/charge_screen` (a large battery, the bolt while charging, "Charging 64%" or "Charged", "Hold Power to turn on"). The screen goes dark after 5 s and any key lights it; holding Power for 2 s leaves charge mode (Bluetooth restarts, the splash plays); losing USB power calls `hal_power_off`, which now cuts power. A USB session still runs as usual and returns to the charge screen. `board_power_hold` records VBUS and the Power key level at boot (shown in Diagnostics → Boot hold as "· USB" and "· key"); `hal_power_take_usb_start` reports, once, a start with VBUS present, the key up and GPIO2.6 not left driven high by the ROM, and the app then opens charge mode straight after `app_start`. The backlight stays off from boot until the app's first frame, so the panel's power-on noise never shows, and `board_display_service` also runs inside the USB, DAC, update and wait-for-key loops so a backlight fade-in started there finishes.
- **High RAM:** Diagnostics → High RAM writes and reads back a pattern over `0x0307A000–0x0309EFFF` (HIGHRAM0, 148 KB, where the rescan overlay runs and the glyph cache lives) and calls a 4-instruction function copied there. Afterwards it restarts the glyph pack reader, since the test overwrote its cache. It shows "OK 148 KB, call works", "Bad at <address>" or "Call gave <value>".
- **Bluetooth:** `hal/bluetooth.h` powers the module, scans, connects to a device, turns the stream on and off and reports the module's state, the devices found, link counters and counts of the headphones' button presses. On the device, `board/bluetooth.c` follows stock's sequence: GPIO2.7, 2.16 and 2.17 are driven low at boot; power-on opens UART1 (group A, 115,200 8N1, divisor 13, FIFOs on, polled, no interrupts) and drives GPIO2.7 high; power-off drives all three low again, as does a module that never sends `CV1`. `hal_bluetooth_service` runs where `hal_audio_service` does (each step and after each strip): it drains the RX FIFO into `device/bt_module`, counts overruns, records the FIFO's peak level and depth, and sends any frame the protocol asks for. `bt_module` connects with `CL06` + the address, `CH06` after 4 s and `CT00` and a failure after 30 s, polling `CQ00` every second meanwhile so a link the module reports only as `CQO` (a remembered device sends no `CLOK`, and headphones may connect on their own) shows within a second; a paired reply (`CLOK`) waits for the next `CQ00` answer to report the link (`CQO`). It sends `CY0 00` on connect, `CY0 1E`/`CY0 00` to start and stop the stream, and stock's `C 86`/`C 87` play notices. The module's `CP`/`CC` (pause/play, sent by the headphones' taps and in-ear sensors) and `CA`/`CB` (previous/next) only count presses in `HalBluetoothRemote`; polling pauses for 50 s after a `CP`/`CC`, as stock does. While streaming, the board routes audio to the module: the first time it applies the stock start-up settings listed in `hardware.md`, then GPIO2.0 goes high and GPIO2.14 low (and back on stop), and the DAC driver keeps those two pins while routed. `app/bluetooth_link` runs every step after `player_update`. It keeps the On/Off choice and up to 6 devices, most recently connected first (stock also keeps 6), in `/.echo/bluetooth.bin` (`BT`, version 2, the On byte, the count, then 6 × the 6-byte address and 32-byte name; version 1 files, with one device, still load), written only when they change. When Bluetooth is on it powers the module at start and connects to the first device as soon as the module is ready, retrying 5 s after each failed attempt. It connects only from Ready or from a scan that found a remembered device: never while a connect is running or while a paired reply waits for `CQO`. A pairing that hasn't reported the link 10 s after `CLOK` is dropped with `CT00` and tried again 2 s later, which brings up a link the module left half-made. With the Bluetooth screen open, each failed attempt is followed by one scan to list nearby devices. Stock only ever scans a freshly powered module (its rescan power-cycles it first), so a scan after the module has paged a device power-cycles it too: off for 500 ms, on, wait for `CV1`, then `CS00`; the first scan after a power-on goes straight out, and the screen says Searching… throughout. A scan that finds a remembered device connects to it at once with `CL06` while the scan still runs, as stock's screen does when an entry is picked (one try per scan), unless the user disconnected or chose Pair new device; then its row shows "Nearby". Each new connection moves its device to the front of the list and shows "Connected to <name>"; a dropped link pauses playback and shows "Disconnected from <name>". A device the user disconnects stays disconnected (no automatic reconnect) until it or another device is chosen, Bluetooth is turned off and on, or the player restarts. Choosing another device while one is connected disconnects it and connects the chosen one 2 s later; "Pair new device" disconnects too, then scans. It streams while connected, playing and nothing is in either jack. The jack can't be read while audio is routed to the module (the readings fake a plugged headphone), so `board/jack.c` holds its last state then and for 500 ms after each routing change: headphones plugged in while paused take the sound, and Bluetooth waits for the next pause and play before taking it again. The headphones' next and previous skip. Their pause pauses and their play resumes only what they paused, and both are ignored for 3 s after a connection, a stream change or a play or pause on the player, because the module sends the same `CP`/`CC` reports then on its own; a pause the headphones cause shows "Paused by <name>". With no connection and the Bluetooth screen closed, the module switches itself off after 5 minutes (Bluetooth stays on for the next start); opening the screen wakes it. Settings → Bluetooth (third, after Shuffle and Repeat) shows the link's state as its value: Off, Starting…, Searching…, Connecting…, the connected device's name, Not connected or On. It opens `screens/bluetooth_screen`: a Bluetooth On/Off row; the remembered devices, each with its state (Playing, Connected, Connecting… or nothing); a "Pair new device" row (Searching… while scanning); then, while not connected, the devices a scan found that aren't remembered; and a hint for the selected row at the bottom. ▶ toggles Bluetooth, disconnects the connected device or connects a remembered one, starts a search, or pairs with a found device (which shows Connecting… or Didn't connect); holding ▶ on a remembered device forgets it. Diagnostics → Bluetooth opens the same screen with four more lines: the module state (version, status letter, pairing result, streaming), the link counters and, over two lines, the module's last 12 messages: frames other than `CS` and repeated `CQ` answers, shown as `C` + two letters (a new `CQ` letter shows as `CQ` + it), plus the `CS`, `CP`, `CL`, `CH` and `CT` commands EchoPod sent, shown as `>S`, `>P`, `>L`, `>H`, `>T` (`CQ00` polls aren't listed); each is followed by `+n` when n seconds passed since the one before. The log and the devices found survive Bluetooth off and on, so one photo after a failed or slow attempt shows the whole exchange. The status bar shows a Bluetooth mark next to the play icon, dim while on and bright while connected. The simulator reports ready after 300 ms, finds two devices over 3 s, keeps them across a power cycle and connects 1.5 s after a pick.

## Simulator audio

- Windowed mode plays through SDL audio. dr_flac, dr_mp3 and dr_wav decode (vendored, pinned in `third_party/dr_libs/COMMIT`). Each track feeds an `SDL_AudioStream` that resamples to the 48 kHz device rate. Two decoder slots (current and queued) make the hand-over gapless.
- Headless mode uses a silent virtual backend that advances on the simulated clock, so scripted runs, track transitions and resume are deterministic.
- `SDL_AUDIODRIVER=dummy` runs the real-time path without sound.
- Third-party code lives in `third_party/` and compiles without our warning flags. The comment and format checks skip it.

## Simulator storage

`--card DIR` maps the card root `/` to a host folder, which is only ever read. Open files are read unbuffered, because `hal_file_write_at` writes through its own handle: on Windows a buffered reader kept serving the old bytes, so the scan's scratch file read back stale data and every rescan stopped with "Library too big for the player's memory". `hal_file_write` writes a `.tmp` file and renames it over the old one, removing the old one first on Windows, where `rename` won't replace a file. `--system-dir DIR` maps `/.echo/` to a separate folder, so the database, covers, resume file, settings and favorites can live in `build/` without touching your music folder. Writes are refused outside `--system-dir`:

```sh
.venv/bin/python tools/library_index.py --music ~/Music --output build/library/library.db
build/dev/platform/sim/echo_sim --card ~/Music --system-dir build/library
```

## Simulator power and display

- `hal_display_set_power(false)` blanks the window. Brightness dims the window (level 1 is about a quarter of full), but screenshots hold the undimmed panel.
- The battery is fixed: 80 % by default, or `--battery N` and `--charging`.
- Gain and output are stored but don't change the sound.
- `hal_power_off()` ends the run loop, and the simulator exits normally.

## Simulator automation

In headless mode the simulator uses a virtual clock (16 ms per frame), so runs are deterministic. `--keys` plays a comma-separated script (`up`, `down`, `play`, `menu`, `back`, `power`, each optionally `:long`) for driving screens in screenshot runs. For example:

```sh
build/dev/platform/sim/echo_sim --headless --frames 120 --keys down,down,down,play --screenshot shot.bmp
```
